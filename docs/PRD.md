## 1. Vision — Clara 要带来的改变

Clara 是面向马来西亚会计事务所的 AI 原生 Accounting OS。事务所把客户资料和工作目标交给 Clara，她理解资料、完成会计工作，在确实缺少资讯、出现冲突或需要人的决定时提问。会计师与 Clara 在同一个工作空间里查看、处理和解释同一套账。

产品价值由**完成的会计结果**衡量：客户的账能对上、来源说得清、问题找得到、工作能继续。生成一段回答、识别一张文件或提出一份草稿只是可能的过程，不是价值本身。这也是现在判断一件工作是否算完成、一份报告是否仍然有效的标准。

长期方向是让事务所交付完整、可信的客户账务，把人的时间集中在判断、客户关系和专业服务上。长期目标是减少 99% 以上的手工簿记劳动——这是愿景方向，**尚未测得**，不构成已交付承诺，也不意味着消除必要的专业判断。

与这个方向一致的产品姿态是：Clara 对所有事务所和用户**默认自主执行**（agentic by default）。在当前权限和足够资料支持下，她直接完成会计处理、入账、匹配以及获准的后续影响；普通工作不需要先启用自动化模式、申请草稿权限或逐次打开入账开关。这是已经落地的产品默认，不是可选增强。

## 2. Target users & problem — 服务谁，解决什么

购买和使用产品的是**事务所**。客户企业是被服务的账务主体，目前没有独立登录入口。一个事务所可以管理多个客户；每个客户有独立的账、财年、资料、工作和知识。Firm workspace 是事务所的客户组合视角，可以跨获准客户查询或发起一批工作，但每一笔会计执行都必须明确属于一个客户，不会自然形成多个公司的合并账；client workspace 是某一个客户的工作视角。

| 用户或参与者 | 当前痛点 | Clara 带来的结果 |
|---|---|---|
| 事务所负责人 | 难以同时掌握客户进度、员工负荷和交付风险 | 在一个组合视角里看见待决事项、正在处理的工作和完成结果 |
| 会计师、簿记人员 | 重复录入、追问资料、对账和更正占用大量时间 | Clara 完成有足够依据的工作，人处理必要决定、查看来源、直接更正 |
| 复核及只读人员（Viewer） | 需要追溯结果，又不应获得修改权限 | 在获准范围内查看、解释和导出账务及依据 |
| 客户企业 | 资料交给事务所后仍需反复解释业务背景 | 提供资料和说明，由事务所维护清楚、持续积累的客户上下文 |

**为什么值得解决。** 客户送来的发票、银行月结单、收付款说明和期初资料往往零散、不完整，也未必及时。会计人员不仅要录入数字，还要判断属于哪个客户、采用什么处理、是否已经入账、应抵消哪一笔，以及会影响哪些账簿和报表。

这些工作容易在文件夹、表格、会计系统和聊天记录之间断开：记下一笔分录，并不代表应收款、银行匹配、资产登记、折旧或关账已经完整处理。发生更正时，人还要追踪后续影响、重新解释数字，并辨认哪些报告已经过时。Clara 把「一件工作」定义为它相关的全部会计结果及其波及范围，正是为了消除这种断裂。

## 3. Core experience & journeys — 入口、关键操作与结果

<a id="the-experience"></a>

### 入口

| 入口 | 用户在这里解决的问题 |
|---|---|
| Firm overview | 哪些客户需要关注、哪些工作等待人员决定、团队正在交付什么 |
| Client Home | 这个客户现在怎么样：需要我几件事、正在做什么、刚完成什么、财务情况如何 |
| Work | 筛选工作列表，进入详情理解目标、来源、结果、进度和问题，并就地回答或继续对话 |
| Documents | 上传、查看和纠正资料，理解每类文件的主要事实、处理状态及相关账务 |
| Accounting | 按日记账、银行、应收应付、资产、计划、科目和关账查看或处理业务对象 |
| Knowledge | 查看 Clara 已知什么、依据在哪里、适用哪个客户，并进行纠正 |
| Reports | 查看、解释和导出财务结果，知道期间、依据、覆盖范围及是否仍然有效 |
| Activity | 追溯谁做了什么、发生了什么变化，以及结果和依据 |
| Chat rail | 用自然语言发起、解释和继续工作；始终明确当前客户或跨客户范围 |
| Settings | 管理事务所、成员、客户配置、通知和商业账户 |

窄屏、纯键盘操作、可见焦点、缩放与减少动效同属正常使用，不是额外模式；空白、加载、没有权限、部分完成和出错都必须给出可信的说明和下一步。数字要说明期间、币种、覆盖范围和更新时间，缺失或延迟不伪装成零。Client Home 的财务摘要至少包含账面现金／银行、应收、应付、期间利润，以及收入费用、现金趋势和按到期日划分的未结金额；财务期间默认马来西亚当月月初至今并可切换，切换期间不会藏起其他期间的待决工作。对账和关账进度必须来自可核实的要求，没有资料的项不显示为已完成。

### 关键旅程

**建立事务所并开始服务客户。** 负责人完成邮箱确认、条款与资料处理声明、产品准入及结账步骤，取得自己的事务所空间；邀请同事后，成员可以接受邀请、恢复账户并按职责工作。事务所添加客户后，通过一场可继续的访谈确认企业身份、财年、报告口径和会计需求；访谈中断可以续上，答案进入该客户的知识。已有业务的客户带入期初总账、应收应付和固定资产，明细与期初余额对齐；缺资料时保留已完成的部分，并指出继续所需的内容。数据处理用途与告知必须清楚：一次事务所层面的声明不能变成无限制披露客户资料的许可（产品今天的实际行为是：accounting_work 用途的模型外发授权由事务所一次性接受 Terms 与 DPA 自动派生、覆盖该所全部活跃客户、没有逐客户开关——这条授权基础见下文「待 owner 裁定」）。

**从文件或一句话完成会计处理。** 上传发票、账单、报销单、银行月结单等即自动开始处理；也可以在对话里附文件，或者直接说明一笔没有附件的业务——明确提供的事实可以作为处理依据，但 Clara 必须保留「这来自用户说明」，不能假装有一份不存在的单据。她识别客户和资料内容，读取相关客户知识，资料足够时完成工作并展示来源、结果和相关对象；不同类型的文件呈现各自的主要事实，用户能从一个字段定位到原文位置和文件版本。需要澄清时，问题要解释缺什么、为什么需要、怎样回答；用户在原处或 Needs you 回答后，原来的工作继续，不必重新上传、重新描述或翻旧聊天。格式问题和暂时故障由 Clara 自己处理；无法自行恢复的系统故障要说明失败与恢复途径，不把技术问题伪装成用户必须回答的会计问题。

**对账、收付款与抵消。** 已入账的付款只做匹配和抵消，只有尚未记录的经济事项才产生新的会计影响；发票、贷项、费用、退款，以及不是来自银行月结单的收付款，也要被正确处理。找不到可靠付款人或发票的收款保留为待处理并提问，不猜测清账，也不默认塞进暂记科目；排除某笔银行交易需要明确、可追溯的依据和权限。资料覆盖、金额和差异都符合要求时，对账才能完成；账面现金与银行月结单余额的含义必须分清，缺少月结单不能当作已经对平的证据。

**资产、调整和持续性计划。** 用户可以通过对话、文件或 Accounting 直接处理资产购入、处置、折旧、预付款摊销、员工垫款、应计与转回等调整。购入事实足够但折旧年限不明时，先完成购入和资产登记，再询问折旧资料。已有明确政策和授权的事项可以执行；新建一条会持续产生分录的计划需要明确指令或已有的授权规则，而已有计划不需要额外的人工批准才「获得」自动执行资格。计划可以修改、暂停、结束：暂停只阻止未来接收，不取消已经接收的工作；结束是终态。到期日是 Asia/Kuala_Lumpur 的日历日；日规则只有「每月某日（1–28）」或「月末」两种，没有「每月 31 日」这种没有确定二月的写法。重复触发不会重复记账；历史补提是用户给出起止窗口的显式操作，每次至多十二个到期日，且不得早于该计划授权的生效日，扫描本身只处理最近一个到期日，绝不自行回补错过的期间。已经发生的银行定期扣款可以记账，但计划不会替用户发起银行付款。

**更正并处理后续影响。** 用户可以从日记账、银行、资产等对象直接更正，也可以要求 Clara 处理。更正要展示影响哪些账项、抵消关系、期间和输出，并保留先前记录。Clara 在有效权限内完成可以确定的影响；被锁定期间或缺少决定挡住的部分单独等待，已完成的独立部分保留。旧报告保持当时的内容，受影响时显示为过时或被新版取代，并可以比较原因。

**关账与下一期间。** 关账可以在对话或 Work 发起，也可以设置月结、年结计划。到期意味着开始准备；只有资料覆盖、对账、相关账簿和当前权限都满足，才完成关账和锁期——正常的自动关账不需要额外的「全自动」模式。首页和关账页显示真实的准备程度与缺口。某个指定的缺失证据可以由有权限的人说明理由并接受为该次关账的例外，并且始终显示为例外；Clara 不能代人接受，也不能豁免借贷平衡这类会计底线。锁期后收到迟到单据时，Clara 解释影响并提出方案，由用户决定重开或在允许的后续期间调整；结转只能完成一次。

**理解结果并交付报告。** 会计师从 Reports 或对话获取试算表、总账、管理报表、账龄和已支持的正式报表包；结果能追溯到客户、期间和依据，重新查看仍然解释出相同的数字，探索性分析与正式交付报告可以区分。完整的报告不只是一个下载按钮：用户要能判断资料是否齐全、计算是否完成、输出是否仍然有效，并在获准范围内导出。不具备完整报表、附注及适用措辞时，不得宣称符合某个报告框架。

### 必须成立的体验

- **一件工作等于它相关的全部会计结果**，不是一张分录代表一切：购入设备同时形成分录和固定资产；把已有收款抵消发票只更新抵消关系，不会再制造一笔收款。
- **更正必须处理波及范围**：受影响的未结项目、抵消金额、资产或计划，以及报告是否仍然有效。Clara 在原授权范围内可以纠正开放期间中自己造成的错误并通知用户，原始已入账历史继续保留。
- **工作持续存在，聊天只是入口**：新建对话清空的是那次聊天的上下文，正在执行的工作、账务和已确认知识继续存在；历史对话可以切换、归档、恢复，也可以真正删除普通文字——归档与删除是两个不同的动作。
- **取消只停止余下部分**：已完成的结果继续保留；若有操作正在完成，先显示「正在停止」，结算后才显示「已取消」；撤回已入账的结果需要相应的冲销或更正。
- **停止一段回复与取消一件会计工作是两个动作**：停止生成不撤回正在跑的会计工作；结果卡片打开的是相关工作的当前状态；内部推理全文、技术日志和工具名称不是理解产品的前提。
- **一批资料里的少数缺口不阻塞其余**：一批 100 份文件中 5 份缺资料，其余 95 份继续完成，用户能看到各自的结果和等待原因。
- **接手、过期或刷新页面都不会让工作消失**，但继续执行仍然必须有当前有效的权限：回答问题不会自动扩权；人员离开或权限变化后，仍有有效事务所授权的工作继续，依赖已失效个人授权的工作停下来等有权限的人接手。

<a id="autonomy-and-professional-control"></a>

### 信任与专业控制

- **事务所之间的资料保持私密**：平台支持人员处理注册、支付或运行支持，并不因此获得其他事务所的账簿；客户资料只用于获准用途，外部分析或追踪服务的披露需要独立核实。
- **每个会计结果都能回答四件事**：属于谁、谁提出或执行、依据是什么、改变了什么。名称不明确时不编造身份，数字和账簿必须一致，原始已入账历史不能被悄悄抹去。
- **文件、知识和外部内容只提供资讯，不能替用户授予权限。**
- **Clara 为客户做账时把资料送给模型的授权来自事务所层面，不是逐客户的开关**：事务所接受了当前 Terms 与 DPA 且该客户活跃，即有授权，覆盖该所全部活跃客户；新版法律文本尚未接受、客户转为非活跃或归档、owner 明确撤销、执行人失去事务所成员资格，任一发生即失效。逐客户的「AI 开关」、配额和常设授权是被刻意否决的选项，不是排期中的功能。（owner 2026-09-15 确认，#825）

### Client Knowledge

Knowledge 统一呈现客户资料、交易对方及别名、长期偏好、会计政策和有来源的处理经验；用户不必先手工登记交易对方绑定，Clara 才能开始工作。明确提供的长期资料自动保存，可以更正或撤回；来自文件的事实保留来源；Clara 的推测保留「待证实」状态；重要矛盾必须说明；同名交易对方会被区分，历史账务指向的对象继续维持。

每条知识带一个类别（已陈述事实、来自具体来源版本的提取事实、长期偏好、关于账务如何编制的政策）和一个可信级别（已陈述、来自文件、导入未核实、未核实推测）。可信级别**由来源决定，不由写入方声明**；政策只接受「已陈述」。更正与撤回是可归属的修订：记录谁改的、为什么改，被替换的值仍然可读，撤回是终局。Knowledge 界面把「成功但为空」「筛选后无结果」「来源不可读」「两条在世记录相互矛盾」「读取失败」当作五种不同状态分别说明。

对话是知识登记簿的入口：用户在聊天里说出一条长期事实，Clara 可以直接记入登记簿，写入以说话的那个人的实时权限为准，可信级别仍然由来源决定；反过来，Clara 在每个回合之前读一次该客户的知识，读不到时会直说并附上原因。在客户上下文里说「以后这样处理」，默认只适用该客户。已完成的工作和纠正会积累成可追溯的经验供后续参考，但反复采用某种做法不会自动把它变成已确认政策，也不会授权未来持续产生分录的计划。删除普通聊天仍然保留支撑已确认知识的最少、可读依据，不会偷偷留一份完整聊天记录。

## 4. Scope & non-goals — 交付什么，不做什么

### 当前版本已交付

- 事务所及成员管理、客户建立与期初导入、支持资料的接收和理解。
- 完整簿记与日记账、银行对账、应收应付与抵消、固定资产与调整、已授权的持续性计划、科目维护。
- 客户知识、关账及结转、财务报告、工作追踪，以及可恢复的人机协作。
- 已接受的场景：供应商贷项、现金购买、员工报销、非银行来源的还款与抵消、已有扣款的记账。每个客户以单一企业账簿为核心。
- 工资与存货相关会计的**记账侧**：可以记录已提供的工资法定义务和定期存货调整。期间、方法或义务种类、精确金额、科目、来源与指示都由会计师提供，产品只核对这些说明之间的一致性，不发明任何缴纳率、门槛或员工层面的计算。**这条禁止针对的是推算，不是阅读**：文件自己印出的数字可以读取并记录，并注明读自哪一份文件的哪一处；至于每一类文件能读到多深，由能力目录（产品对每种文件如实公布的可读范围）逐类决定，不在这里一概而论。表单、上传／引用和对话三个入口都可用。
- 接收已支持的电子发票资料。
- 角色与权限边界：Viewer 查看及导出获准的信息；Bookkeeper 上传、整理、匹配、回答、准备和入账，正常权限内可以处理自己准备的记录，不以金额强制增加第二人审批；Admin 在簿记职责之外还有客户与事务所配置、期初确认和关账操作；Owner 拥有所有权、成员管理和适用的法律签署，平台支持能力须另行具备资格。普通获准的手动入账，在资料和会计条件满足时，不需要默认的第二人复核或额外的声明仪式——人直接执行与 Clara 执行同一业务，后果标准一致。

当前缺少某条实现路径，不会自动把已接受的功能移出范围。

### 已接受、留待以后

- 跨整批的聚合进度（例如「95/100 已完成」）：单项各自完成或等待已经可用，整批的汇总进度尚未交付（#636）。
- 对话车道在连接失联后的完整恢复：已知仍有缺口，接手与刷新的其余保障已交付（#764）。
- 把一条客户处理方式明确推广为事务所默认规则并保留既有客户例外：晋升路径的服务器侧门与客户例外保留规则都已就绪，目前缺的是界面或对话入口（#654）。
- 依据被修正或撤回后，自动重新评估依赖它的经验：目前需要人工复核受影响的经验（#658、#663）。
- 马来西亚税务准备：SST 相关准备、税务计算草稿和资本津贴由人复核和提交，是已接受的产品方向；当前 beta 不启用税务，本轮交付不隐含税务正式上线。
- 后续合规能力：员工津贴专项、自开票义务识别、预扣税机制和法定截止日历保留为未来方向，不默认为当前核心已支持。
- 商业运营（事务所订阅、席位、活跃客户容量、共享 AI 用量及账单）：属于已接受的产品方向，现有 beta 准入不表示正式计量和收费已经完成；交付时点未定。
- 电子发票的扩展能力：主动拉取、对外开票、多币种、专门的工资单接收，各自仍需单独决定和交付。

### 明确不做

- **集团合并**：不会自然形成多公司合并账。
- **向外部 ERP 自动写账**。
- **客户企业登录**：客户企业不直接使用产品。
- **完整工资引擎、永续库存系统**。
- **实际发起银行付款、建立或取消银行扣款授权**：拥有自动记账权限不代表可以移动资金；已发生的银行扣款记账与已授权的周期会计计划仍在范围内。
- Clara 不替人作必须由本人完成的法律签署或申报，也不把「自动」解释为忽略客户隔离、有效权限、缺失依据和会计底线。

税务、法律及商业条件在对应功能启用时才核实，本蓝图不堆积税率、门槛、接口规则或法律文本。

## 5. Success criteria — 怎样判断做好了

衡量重点是实际完成的工作和减少的人力。以下口径用于建立基线并持续比较；目前不宣称已经测得改善，也不杜撰上线目标值。

| 指标 | 如何判断产品是否改善 |
|---|---|
| 每个客户期间的人工处理时间 | 在业务复杂度和资料完整度相近的前提下，比较人员用于录入、追问、复核及更正的总时间 |
| 自主完成率 | 资料和权限足够的工作中，无额外人工操作即完成完整业务结果的比例；同时展示被排除的等待和失败工作 |
| 必要交互质量 | 区分确实缺资料或缺决定的问题，与重复追问、已有资料仍要求输入、无意义确认；观察回答后能否继续完成 |
| 交付时效 | 从资料齐备到可用账务结果，以及从满足关账前提到完成报告的时间 |
| 正确性与后续更正 | 重复入账、错配、账簿不一致及需返工的比例；用相同业务样本比较，不用生成数量代替质量 |
| 可解释性与恢复 | 能否找到来源和更正链，能否在中断、换人或失去连接后完成原工作且没有重复结果 |
| 事务所采用程度 | 活跃处理的客户数与核心旅程的重复使用情况，结合会计人员对节省时间、可信度和掌控感的反馈 |

一个可交付的核心版本，应让真实事务所在产品内走完「建立事务所 → 建立客户和期初 → 接收资料或指令 → 完成账务 → 处理问题及更正 → 对账和关账 → 取得报告」的完整旅程，无需工程师代写账务。完成条件还包括：直接操作与 Clara 得到相同业务结果；相关明细与总账对齐；问题在各入口一致；重试、中断和取消不制造重复也不丢失已完成结果；权限变化有效；来源可追溯；键盘和窄屏使用完整；不可用或未完成的能力明确呈现。仅有原型、单项测试成功或上线记录，都不能单独证明这条旅程已经可用。
