# Incumbent-SDK gap analysis — can the OpenAI Agents SDK or the Claude Agent SDK fulfill the durable-runtime requirements?

> **Charter:** stress-test the exclusion of the two incumbent-adjacent SDKs from the Clara rebuild runtime decision, with the burden of proof on EXCLUDING them. Requirements R1–R11 from `clara-rebuild/docs/architecture/ARCHITECTURE.md` §4.0a; prior analysis `docs/phase2-research/runtime-recommendation.md` (2026-07-17) taken as the baseline to attack, not repeat.
> **All decisive claims below re-verified against primary sources on 2026-07-17.** Versions confirmed via `npm view` today: `@openai/agents@0.13.4` (published 2026-07-15), `@anthropic-ai/claude-agent-sdk@0.3.212` (registry modified 2026-07-17, license "SEE LICENSE IN README.md" = Anthropic Commercial ToS).
> **Headline:** the exclusion of the OpenAI Agents SDK **stands and is reinforced** by fresh evidence. The exclusion of the Claude Agent SDK **stands on the requirements as written (R7)** — but the prior analysis's R1/R2/R5 scores for it are **outdated**: three shipped features (the `defer` permission decision, the `SessionStore` adapter, first-class OTel full-content export) materially improve its durability/HITL/tracing story, and the honest elimination rationale must be restated. The AI SDK 7 + WDK recommendation survives, with one addition (Temporal `@temporalio/ai-sdk` as a second fallback data point).

## 1. OpenAI Agents SDK JS (`@openai/agents@0.13.4`)

### 1.1 What is native today (verified 2026-07-17)

- **HITL / RunState** (docs, `guides/human-in-the-loop`, fetched today): `result.state.toString()` / `RunState.fromString(agent, serialized)`; "You may store your serialized state in a database, or along with your request"; "The human-in-the-loop flow is designed to be interruptible for longer periods of time without keeping your server running." Sticky `alwaysApprove`/`alwaysReject` decisions "survive toString() / fromString()".
- **The version-skew caveat is still in the docs, verbatim, today:** "If your approval requests take a longer time and you intend to version your agent definitions in a meaningful way or bump your Agents SDK version, we currently recommend for you to implement your own branching logic by installing two versions of the Agents SDK in parallel using package aliases," plus guidance to stamp "your own code a version number… storing it along with the serialized state and guiding the deserialization to the correct version of your code."
- **NEW since the prior analysis's frame — a Sessions feature** (`guides/sessions`, fetched today): built-in `MemorySession` ("intended for local development… reset when your process exits") and `OpenAIConversationsSession` (server-side, OpenAI-hosted); a custom `Session` interface ("back memory with Redis, DynamoDB, SQLite, or another datastore"); Prisma/file example backends in `examples/memory/`. **Persistence is per-turn, after the turn completes**: "After a non-streaming run one call to `session.addItems()` persists both the original user input and the model outputs from the latest turn"; streaming runs append "once the turn completes." HITL "approval checkpoints still round-trip through `RunState`". So sessions solve cross-turn history, **not** mid-run durability.
- **Run controls** (`guides/running-agents`): `errorHandlers` (maxTurns/modelRefusal/invalidFinalOutput), retry from saved RunState after guardrail errors, `AbortSignal` cancellation. Explicitly **not documented**: background execution, durable execution, checkpointing.
- **Model-agnosticism**: the `@openai/agents-extensions/ai-sdk` adapter "is still in beta, so it is worth testing carefully with your chosen provider, especially smaller ones" (fetched today); requires AI SDK provider spec v2/v3; several Responses-API tool flows unsupported through it.
- **Release history May–July 2026** (GitHub releases, fetched today): v0.11.6 (May 29) → v0.13.4 (Jul 15). Content: GPT-5.6 support, realtime changes, guardrail additions, experimental *hosted* multi-agent, and — notably — **v0.13.2 (Jul 10): "Restored run usage when deserializing RunState"** (i.e., a deserialization defect in exactly the layer parked approvals depend on, patched mid-July). **No 1.0, no step engine, no checkpointing, no Temporal integration, no durability features shipped.** Five releases in the first half of July alone — on a 0.x line whose vendor tells you parked state may not survive an upgrade.
- **Temporal rescue lane: Python-only.** Temporal's OpenAI Agents SDK integration went **GA for the Python SDK on 2026-03-23** (temporal.io change-log). Temporal's TypeScript durable-AI integration is `@temporalio/ai-sdk` — it wraps **Vercel's AI SDK**, in public preview; the Temporal TS docs contain **no** openai-agents-js integration (docs.temporal.io/develop/typescript/integrations/ai-sdk, fetched today). The industry's durable lane for this SDK does not exist in our language.

### 1.2 What we would have to build for R1–R3 (the custom kernel, concretely)

RunState materializes only at boundaries *we* orchestrate (interruptions, run end). A crash mid-tool-chain loses everything since the last serialize (R1 fail as shipped). To fix it ourselves:

- **Tables:** `agent_tasks`, `agent_runs`, `run_checkpoints(run_id, seq, serialized_state jsonb, sdk_version, code_version, created_at)`, `agent_interruptions(hook of our own design)`, `tool_call_receipts(tool_call_id, idempotency_key, status)` — plus DB idempotency keys on every audited writer (already planned regardless).
- **Serialization points:** to checkpoint mid-run we must drive the loop turn-by-turn (single-turn runs in a loop, serializing after every model response and tool batch) instead of one `run()` call — re-implementing the runner's loop semantics around the SDK, or accept interruption-only checkpoints and eat the crash window.
- **Replay semantics:** on re-drive, `RunState.fromString(agent, …)` requires compatible agent definitions and a compatible SDK version. We must stamp `sdk_version` + `code_version` into every checkpoint and route deserialization to the matching code — the vendor's own prescription is **parallel SDK installs via package aliases**, forever, for any deploy that lands while an approval is parked. Clara's approvals *routinely* park across deploys.
- **Failure modes an accounting product cannot tolerate:** (a) an un-deserializable parked approval after an upgrade = a consequential posting frozen or silently re-driven from an older checkpoint; (b) re-drive re-poses a tool call the DB already executed — only the DB idempotency key stands between that and a double-post, with no engine-level memoization as the first layer; (c) the July 10 RunState-usage-deserialization patch shows the serialized format is *actively being fixed* — each such fix is a potential poison event for state parked across it.

**Engineering-risk estimate: HIGH.** This is precisely the reverted WP-015 custom kernel rebuilt around a vendor blob we don't control the schema of — strictly worse than WP-015 (which at least owned its own serialization).

### 1.3 The strongest honest case FOR adopting it anyway

The team knows it; SSE is proven in the current build; typed tools and guardrails are mature; the new Sessions feature covers cross-turn history cleanly; and "RunState in Postgres + DB idempotency keys" is real and vendor-blessed for the *pure interruption* case. It could be made survivable by policy: pin the SDK for the life of any parked approval, drain/resolve all approvals before any upgrade, stamp versions into checkpoints, accept the mid-run crash window (minutes of lost work, no correctness loss *if* every writer is idempotent). But that policy inverts the product: Clara's clarify/approval parks are days long and continuous — an upgrade embargo whenever any firm has a pending approval is an embargo always, and the escape hatch is permanent parallel-versioning. And the model-agnostic path (R7) runs through the beta `aisdk` adapter — i.e., adopting the recommended stack's model layer underneath the incumbent's loop anyway, with an extra beta layer in between.

### 1.4 Verdict

**Not reasonably.** R1 requires building the checkpoint kernel ourselves; R2 carries a vendor-documented version-skew hazard on a fast-moving 0.x line (5 releases in July; a RunState deserialization fix among them); R4 is absent (no steps, no memoization, no retries); R7 rides a beta adapter that *is* the competing SDK; the Python-only Temporal lane confirms no bought durable substrate exists for it in TypeScript. **Exclusion upheld, on refreshed primary evidence. Burden of proof met.**

## 2. Claude Agent SDK (`@anthropic-ai/claude-agent-sdk@0.3.212`)

### 2.1 What is native today — three findings that OUTDATE the prior analysis

All fetched 2026-07-17 from code.claude.com/docs (note: docs moved; platform.claude.com 307-redirects there).

**(a) The `defer` permission decision — native, durable, days-later HITL.** The prior analysis scored R2 = 1 with "days-later flow is yours to rebuild." That is no longer accurate. The hooks reference (`/en/hooks`, "Defer a tool call for later") documents, verbatim:

- "`defer` is for integrations that run `claude -p` as a subprocess and read its JSON output, such as an Agent SDK app…" — i.e., exactly the SDK's shape.
- Flow: PreToolUse hook returns `permissionDecision: "defer"` → "The tool doesn't execute. The process exits with `stop_reason: "tool_deferred"` and the pending tool call preserved in the transcript." The result carries `deferred_tool_use` (`id`, `name`, `input`). The caller surfaces the question in its own UI, waits — **at zero compute, the process is gone** — then resumes with `resume: <session-id>`: "The same tool call fires `PreToolUse` again. The hook returns `permissionDecision: "allow"` with the answer in `updatedInput`. The tool executes and Claude continues." **Deterministic: the model does not re-decide; the parked tool call re-runs.**
- "There is no timeout or retry limit. The session remains on disk until you resume it, subject to the `cleanupPeriodDays` retention sweep that deletes session files after 30 days by default." Re-defer loops are allowed.
- The user-input guide states it directly: "If a user might take longer to respond than your process can reasonably stay running, return the `defer` hook decision, which lets the process exit and resume later from the persisted session."
- **The hard limitations, also verbatim:** "`defer` only works when Claude makes a single tool call in the turn. If Claude makes several tool calls at once, `defer` is **ignored with a warning and the tool proceeds through the normal permission flow**." Deferred-tool-unavailable on resume → `stop_reason: "tool_deferred_unavailable"`, `is_error: true`. `updatedInput`/`additionalContext` are ignored with defer. Precedence: deny > defer > ask > allow.
- Related plumbing shipped recently: `canUseTool` gained a `requestId` "for correlating out-of-band permission responses; supports returning null to suppress automatic responses" (changelog 0.3.199).

**(b) `SessionStore` — a shipped persistence adapter interface (the prior "(carried)" claim, now verified precisely).** `/en/agent-sdk/session-storage`: the interface (`append`/`load` + 4 optional methods) is **in the core SDK** with an `InMemorySessionStore`; **S3, Redis, and Postgres adapters exist as reference implementations in `examples/session-stores/` — "not published to npm; copy the `src/` file you need"** — with a conformance suite. So "shipped Postgres SessionStore adapter" from the prior research is half-right: shipped *interface + reference code*, not a supported npm package. Semantics that matter:

- **Dual-write, local-first:** "The store is a mirror, not a replacement. The Claude Code subprocess always writes to local disk first… Local writes remain authoritative."
- **Mirror writes are best-effort:** on failure, ≤3 attempts, then "the error is logged, a `{type:'system', subtype:'mirror_error'}` message is emitted… **the batch is dropped, and the query continues**." Adapters must dedupe by `entry.uuid`. For a 7-year-audit product this means the durable copy of a transcript can silently lose a batch unless we alarm on `mirror_error` and reconcile — the local JSONL on an ephemeral Fly disk is the "authoritative" copy that a redeploy deletes.
- Incompatible with `persistSession: false` and with file checkpointing. Sessions are also cwd-keyed (`~/.claude/projects/<encoded-cwd>/*.jsonl`); resume requires matching cwd or store hydration.
- Unlike the OpenAI SDK, the transcript is written **continuously during the run** (each tool_use/tool_result as it happens), not only at turn end — a genuinely better crash floor. But **mid-run crash resume semantics (a `tool_use` with no `tool_result` in the transcript) are undocumented.**

**(c) First-class OTel export with full-content opt-ins — the prior R5 = 1 ("no first-class trace-export API; build on hooks") is now wrong.** `/en/agent-sdk/observability`: the CLI "has OpenTelemetry instrumentation built in"; exports traces/metrics/log events "to any backend that accepts OTLP, such as Honeycomb, Datadog, Grafana, **Langfuse**, or a self-hosted collector." Traces are **beta** (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`; "Span names and attributes may change between releases"). Content is off by default with explicit opt-ins: `OTEL_LOG_USER_PROMPTS=1`, `OTEL_LOG_TOOL_DETAILS=1`, `OTEL_LOG_TOOL_CONTENT=1` (60 KB truncation), `OTEL_LOG_RAW_API_BODIES` ("`file:<dir>` for untruncated bodies"). W3C `TRACEPARENT` propagation links agent spans into our app's trace; `enduser.id`/`tenant.id` resource attrs give a per-user audit trail. This satisfies the C6 shape (full-content, vendor-flexible, DPA-coverable) with a beta-stability caveat.

**Also confirmed today:** subprocess model ("The Agent SDK spawns and supervises a `claude` CLI subprocess… One agent session maps to one subprocess"); **resources "1 GiB RAM, 5 GiB disk, and 1 CPU per agent is a reasonable starting point"**, "Memory usage grows with session length"; scaling = `agents per host = (host RAM - overhead) / per-session RAM ceiling`, session-pinning via consistent hashing; hybrid pattern (ephemeral containers hydrating from a SessionStore) is a documented first-class deployment shape, Fly Machines named as a provider. Multi-tenant isolation is documented and non-trivial: `settingSources: []`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, per-tenant `CLAUDE_CONFIG_DIR` + `cwd`, per-tenant egress rules. Models: **Claude only** — auth paths are Anthropic API / Bedrock / Vertex / Azure Foundry (all Claude). License: "Use of the Claude Agent SDK is governed by Anthropic's Commercial Terms of Service, including when you use it to power products and services that you make available to your own customers." V2 session API was removed in 0.3.142; structured-output hardening and `claude-fable-5` support landed May–July.

### 2.2 What we would have to build for R1–R3

- **R1:** the transcript is durable, but tasks/runs/interruptions/tool-calls as queryable first-class state are still ours: the same `agent_tasks` / `agent_interruptions` / `wakes_outbox` projection tables as the recommendation, driven off the message stream + `stop_reason` lifecycle. The durability floor is the **best-effort mirror** — we would write our own Postgres `SessionStore` (from reference code we then own), alarm on `mirror_error`, and either accept a dropped-batch window or add a reconciliation sweep comparing local JSONL to the store before container teardown. Mid-run crash semantics need a spike (undocumented).
- **R2:** clarify (AskUserQuestion) and single-call approvals are **native via defer** — genuinely parked at zero compute, resume after days and across deploys, deterministic re-run. The build burden is the constraint: **Clara's tool loop is parallel by design, and defer on a batched turn silently degrades to the normal permission flow ("ignored with a warning")** — the exact convention-not-gate failure class the audit punished (G9). We would have to force single-tool-call turns around every consequential write (prompt-level discipline or serialized tool config) and treat the warning path as a monitored invariant violation; the DB-side authorization law remains the only hard backstop when it degrades.
- **R3:** no step engine, no memoization, no engine retries — a resumed session that *conversationally* re-approaches work relies 100% on DB idempotency keys to avoid double-posting; only the single deferred call itself has deterministic re-run semantics. Version skew across deploys is *less* scary than RunState (a transcript is model-facing message data, and the bundled CLI is pinned to the SDK version) but cross-version resume is not guaranteed anywhere in writing.
- **Risk estimate: MEDIUM** — meaningfully lower than the OpenAI path (the park/resume primitive exists and is deterministic), but the defer batching constraint + best-effort mirror + undocumented crash-resume put unavoidable custom scaffolding and two spike questions in front of R1/R2, and R4 stays entirely on the DB layer.

### 2.3 The strongest honest case FOR adopting it anyway

If the owner relaxes R7, this SDK is now a real contender, stronger than the prior analysis recorded: native skills (the `belcort/` canon's own standard), deepest MCP, subagents, continuous transcript persistence, **defer-parked HITL**, SessionStore multi-host resume, and OTLP full-content tracing to a DPA-coverable vendor. On the model-lock question honestly assessed: if Claude models stay best-in-class, model-lock costs little *day to day* — the real locks are (a) **contractual** (the runtime itself is under Anthropic's Commercial ToS — a pricing, rate-limit, or policy change cannot be routed around by swapping models, because the *harness* is the dependency), and (b) **architectural**: subprocess-per-session at a documented ~1 GiB starting footprint means 20 concurrent firm sessions ≈ 20+ GB fleet RAM with per-session spawn latency (vs one Node process for an in-process loop), plus the multi-tenant isolation checklist (config dirs, auto-memory kill-switch, per-tenant cwd/egress) executed perfectly on every call. And the deepest irony: Clara's tools are all curated DB-function wrappers — the SDK's crown jewels (file tools, bash, sandboxing, CLAUDE.md loading) are dead weight for a DB-tool accounting agent; we would pay the harness tax to use almost none of the harness.

### 2.4 Verdict

**Cannot fulfill the requirements as stated: R7 (model-agnosticism) is a hard, verified fail today** — every documented auth path is a Claude path. With R7 relaxed by the owner, it graduates from "eliminated early" to a genuine head-to-head candidate (corrected rows: R1 ≈ 1.5, R2 ≈ 2⁻ via defer with the single-call constraint, R5 = 2⁻ beta) — but it would still lose the head-to-head on R4 (no step engine — everything rides DB idempotency), the defer silent-degrade hazard on parallel tool calls, best-effort mirroring as the durability floor, subprocess economics, and Commercial-ToS coupling. **Exclusion upheld under the standing brief; the §8 escalation flag ("re-enters if the owner relaxes R7") is now stronger and should be surfaced to the owner honestly rather than leaning on the outdated R2/R5 scores.**

## 3. New contenders / major releases the prior analysis missed (last 2–3 months)

1. **Temporal ⇄ OpenAI Agents SDK (Python) — GA 2026-03-23** (temporal.io change-log). Python-only; irrelevant to our TS runtime, but it is the *only* bought durable substrate for the incumbent, and it doesn't exist in our language — reinforcing §1.4.
2. **Temporal `@temporalio/ai-sdk` (public preview)** — Durable Execution for the **Vercel AI SDK** in TypeScript: "use the AI SDK's API directly in Workflow code while Temporal handles Durable Execution"; model calls and MCP tool calls auto-wrapped as Activities (docs.temporal.io, fetched today). This is a *second* durable substrate under the same recommended model layer — a candidate extra fallback besides LangGraph if the WDK spike fails. Costs vs WDK: requires a Temporal server (self-hosted cluster or Temporal Cloud — new infra, new DPA surface) instead of state-in-our-own-Postgres, and it is itself preview. Worth one line in the Gate-2 packet, not a re-open.
3. **DBOS** (`@dbos-inc` TS library; Go SDK Apr 2026, active 2026 releases) — Postgres-backed durable execution *as a library*, no separate orchestration server: same state-in-our-Postgres shape as WDK, could sit under a plain AI SDK `ToolLoopAgent`. No WorkflowAgent-equivalent AI bridge or `needsApproval` UX layer — more assembly than WDK, less than hand-rolling. Same bucket as Restate/Inngest/Hatchet (all active, none agent-loop-native in the way WDK's `WorkflowAgent` is).
4. **Anthropic Managed Agents** — new hosted REST offering ("Anthropic-hosted event log… long-running and asynchronous sessions"). Non-viable for BELCORT (the data plane and sandbox live on Anthropic infrastructure; model-locked; our agent works against our DB, not a sandbox) but it should be named so the owner knows it was considered.

**Net effect:** every serious TypeScript durable-agent lane that emerged this quarter (Temporal AI-SDK, WDK itself, DBOS-under-AI-SDK) converges on the **Vercel AI SDK as the model layer** — independent corroboration of half the recommendation regardless of which durable substrate wins the spike.

## 4. Does the AI SDK 7 + WDK recommendation survive this stress-test?

**Yes — with corrections.** The decisive rows are unchanged: neither incumbent has a step-checkpointed engine (R4), the OpenAI SDK's R1/R2 story still requires the WP-015-class custom kernel plus a vendor-documented version-skew hazard (re-verified verbatim today, with a fresh RunState-deserialization patch as supporting evidence), and the Claude SDK still hard-fails R7 today. What must change in the packet, for honesty in front of the owner:

1. **Correct the Claude SDK scores** — R2 is no longer "yours to rebuild" (defer is native, deterministic, zero-compute, days-scale) and R5 is no longer "build on hooks" (first-class OTLP with full-content opt-ins, Langfuse named in Anthropic's own docs). The elimination must rest on what is actually true: **R7 hard fail + no idempotency engine + defer's single-tool-call silent degrade + best-effort mirroring + subprocess/ToS economics.**
2. **Keep and strengthen the escalation flag:** if the owner relaxes R7 at Gate 2, the Claude Agent SDK has earned a real head-to-head (it would still lose on R4 and operational shape, on today's evidence — but that is now an argument to make, not assume).
3. **Add Temporal `@temporalio/ai-sdk` (preview) to §8** as a watched alternative durable substrate under the same AI SDK layer, behind LangGraph in the fallback order (new infra + preview status vs post-1.0 + our-own-Postgres).
4. The spike preconditions and the LangGraph fallback are untouched by anything found here.
