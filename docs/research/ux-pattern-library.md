# UX Pattern Library — Reference Study for Clara v2

Wayfinder research ticket [#582](https://github.com/BELCORT-SDN-BHD/clara/issues/582), part of map [#573](https://github.com/BELCORT-SDN-BHD/clara/issues/573).

Method: Mobbin MCP (`search_flows`, `search_screens`), platform `web` throughout except Copilot Money
(`ios`, mobile-first). Every screen listed below was visually inspected (not inferred from metadata).
Task intent used on every call: "Research reference UX patterns for redesigning an AI-native accounting
workspace."

Decided IA (not re-litigated here, see #579/#580): two altitudes (firm workspace / client workspace),
left nav, docked AI chat rail, Linear-style Work list + detail pane with inline thread, LLM-driven
onboarding interview with typed questionnaire cards, per-kind Document schemas, single-flow Close, a
"your reports" Reports page.

---

## Firm home

- **Project grid + usage/alerts cards** — Vercel, dashboard overview ([screen](https://mobbin.com/screens/a8d666ee-3303-4b28-9e1f-06b8dbd63cb6), [screen](https://mobbin.com/screens/5bb75d66-7572-4f2e-a229-ebc54627343b)). Solves: a landing page for an operator who owns *many* child workspaces (Vercel's projects ≈ Clara's clients) — grid of cards with live status glyphs, a compact usage/billing card, and an "Alerts" card that surfaces cross-project anomalies without opening each one. Maps to Clara: firm home = card grid of client workspaces (health glyph = last close status / open exceptions count), a "Needs attention" rail sourced from the Work list, `Card` + `Badge` + a small `Sidebar` account menu. Rejected: a single combined table of all clients' issues (Attio-style list) — firm owners think in terms of *which client*, not a global ticket list, so cards-first beats rows-first here.
- **"For you today" firm-wide to-do rail** — Deel, home ([screen](https://mobbin.com/screens/c12b258a-d50b-4f5e-b6fe-0d1ad050f6b0)). Solves: aggregates cross-entity approvals (expense approvals, data updates, submissions) into one ranked list with inline "Review" buttons, each item routed to its owning object. Maps to Clara: firm home's action rail = a filtered slice of the global Work list (role-floor items awaiting a firm-level human), `Card` rows with a `Button` that deep-links into the Work detail pane rather than a bespoke to-do UI. Rejected: Deel's own per-domain badges (Data updates / Expense approvals / Submissions as separate counters) — Clara already has one unified Work queue per #577 (operator abolished, one inbox), so we don't want parallel counters that fragment it back apart.
- **Docked AI answer over a mostly-empty canvas** — Linear, workspace home ("Ask anything or tell Linear what you need") ([screen](https://mobbin.com/screens/735580ba-5334-4377-8dd8-4338533d99af)). Solves: gives the AI surface top billing on the landing screen without forcing a click to open it. Maps to Clara: firm home keeps the chat rail *docked*, not full-bleed like Linear's — Clara's chat rail is a permanent right-hand column per #579, so firm home renders the card grid at full width with the rail already visible, rather than Linear's centered empty-canvas-plus-input which assumes chat is the primary object.

## Client home (dashboard)

- **Financial-position + ratio dashboard with period compare** — Xero, financial position/business snapshot ([screen](https://mobbin.com/screens/ab410583-e8d2-4e04-af9a-0c6d379d63af)). Solves: three or four stat tiles (cash, DSO, DPO) each with a sparkline trend and an explicit "on [date]" / prior-period delta, plus a compact balance-sheet mini-card. This is the closest reference to "what should a client's home page show." Maps to Clara: client home = a `Card` grid of stat tiles (cash balance, unreconciled count, open Work items, days-to-close) each backed by a real DB-owned aggregation (marked "Not yet specified" in #573 — this pattern assumes those aggregations exist). Rejected: Wave's dashboard-as-report-preview (P&L bar chart + payable/owing table inline on the dashboard, [screen](https://mobbin.com/screens/b0779fe4-db8c-486e-a5d6-bcccf1828216)) — duplicates the Reports page instead of summarizing toward it; Clara's Reports page already owns "your reports," so client home should link out, not re-render.
- **Net-worth line + account list** — Copilot Money, Accounts tab ([screen](https://mobbin.com/screens/30755611-5390-482f-a49b-dfa77e67d8f4)). Solves: one hero number (assets/debt) with a time-range switcher (1W/1M/YTD/3M/1Y) above grouped account cards. Maps to Clara: the cash-position hero chart on client home, using shadcn `Tabs` for the range switcher and a lightweight chart primitive (Recharts, per the dataviz skill) rather than Copilot's native SwiftUI curve. Rejected as a full template: Copilot's category-budget donut ring ([screen](https://mobbin.com/screens/cca95442-6e70-485b-8d1a-2ee035ad7348)) is a consumer budgeting concept with no accounting-firm analogue — accrual-basis accounting has no "budget remaining" ring to show a bookkeeper.
- **Overdue + payable/owing two-column table** — Wave, dashboard ([screen](https://mobbin.com/screens/b0779fe4-db8c-486e-a5d6-bcccf1828216)). Solves: puts "what's overdue right now" directly on the landing page in a compact two-column table (invoices payable to you / bills you owe), each row a link. Maps to Clara: an "Attention" card on client home surfacing top aging items, linking into the Registers → Aging register rather than owning its own table.

## Work list / inbox

- **Grouped, filterable issue list with saved views** — Linear, Active Issues / saved view ([screen](https://mobbin.com/screens/610d34b6-6ad8-45ab-80fb-2107b31ed01e), filter panel [screen](https://mobbin.com/screens/2579f037-4e90-4330-ac35-19323ca9828a), saved view with chip [screen](https://mobbin.com/screens/0f263579-9bcb-4815-991e-ad45b408814d), assigned/created tabs [screen](https://mobbin.com/screens/671d22cf-69d7-4289-886c-f4e2f288f058)). Solves: status-grouped rows (Todo/In Progress/Done), a filter-chip bar above the list, and a right-hand "Add Filter" popover with grouped filter types (Status, Assignee, Agent, Priority, Labels…) including an explicit **Agent** filter row — directly relevant since Clara's Work items are agent-originated. Maps to Clara: this *is* the Work list per #579 — `DataTable`-style grouped rows, `Popover` + `Command` for the filter builder, saved views persisted per user/workspace. Rejected: Attio's spreadsheet-style list (sortable columns, per-column aggregation footer, [screen](https://mobbin.com/screens/b1f51bfb-4b7f-4d77-a7ce-9a1568db223e)) — good for a CRM record list, wrong metaphor for a queue of *actions requiring disposition*; Clara's Work items need one-click status transitions (approve/decline), not spreadsheet sorting as the primary interaction.
- **Detail pane with inline activity thread** — Linear, issue detail with comments ([screen](https://mobbin.com/screens/2e6c00de-40a7-455d-875f-0d8cb27c8270), sub-issues [screen](https://mobbin.com/screens/1ea32209-1221-46de-b4ad-875a8f1b5777)). Solves: single-column detail (title, description, sub-issues) with an **inline** activity+comment feed directly below — no separate "comments" tab — and a slim right-hand properties rail (status, priority, assignee, labels). This is the exact "detail pane with inline thread" spec'd in #579. Maps to Clara: Work item detail pane = description/evidence block, inline agent+human thread underneath (reuses the chat message component), right rail for structured fields (counterparty, amount, GL account, confidence). Rejected: Asana's task detail with a *separate* approve/reject action bar plus a distinct Comments tab at the bottom ([screen](https://mobbin.com/screens/e94342b0-adf8-4b9e-85ce-c01c0909cf9a)) — splits disposition from discussion into two visually distant zones; Clara wants the decision and the reasoning trace in the same scroll.
- **Approval action bar with visible chain** — Airwallex, spend request slide-over ([screen](https://mobbin.com/screens/89c96631-be20-4176-be78-d24175e013ed)); Mercury reimbursement modal ([screen](https://mobbin.com/screens/60364c06-7c88-4ac9-a5e2-cf1041ab4e84)). Solves: Approve/Decline pinned to the panel, with submitted-by/approved-by timestamps stacked above. Maps to Clara: the Work detail pane's disposition controls (approve / post / needs-info) sit fixed at the top of the pane, not buried below a long evidence scroll — evidence is the thing being reviewed, the decision affordance shouldn't require scrolling past it. Rejected: burying approve/reject at the bottom of the page (older QuickBooks-style forms) — costs a scroll on every review, which matters at agentic-work volume.
- **Empty state that explains *why* nothing is showing** — Linear, "No issues matching the filters in the milestone" with an explicit "16 issues hidden by filters — Clear Filters" ([screen](https://mobbin.com/screens/d3ab0127-662f-4764-9c84-511cd7345e27)). Solves: disambiguates "genuinely empty" from "filtered to empty," which matters enormously in a queue UI where a firm owner might panic-think the agent stopped working. Maps to Clara: Work list empty state must always state the hidden-count + one-click clear, never a bare "No items."

## Documents (list + detail + evidence viewer)

- **Split evidence viewer: source doc left, extracted fields right** — Mercury reimbursement ([screen](https://mobbin.com/screens/60364c06-7c88-4ac9-a5e2-cf1041ab4e84)); Melio bill detail ([screen](https://mobbin.com/screens/2f89852c-25d3-4fc0-8f22-fa72d4aaf85e)); Navan expense detail ([screen](https://mobbin.com/screens/386fafb7-196f-43cf-b54a-8fbcaa6ab5b7)); Midday inbox-to-transaction match ([screen](https://mobbin.com/screens/bb6dcd6c-9b61-4382-a0d8-401ce16b6247)). Solves: this is the single most load-bearing pattern for Clara's Documents surface — a zoomable receipt/PDF on the left, a structured field panel on the right (amount, date, category/GL, payment method), with clear provenance of which fields came from OCR vs. human edit. Maps to Clara: Documents detail = `Resizable` two-pane layout, left pane a PDF/image viewer with zoom controls, right pane a per-kind schema form (per #573's "Documents show per-kind schemas" decision) built from shadcn `Form` + `Input`/`Select`. Rejected: QuickBooks' single-column invoice editor with a slide-out "Customisation" toggle panel ([screen](https://mobbin.com/screens/f36c5dd0-5922-4ac7-baf0-31036cef9381)) — that's an *authoring* UI (building an invoice to send), not a *verification* UI (confirming what an agent extracted from an inbound document); the two-pane compare pattern is specific to inbound-evidence review, which is what Clara's Documents surface actually does.
- **Visible extraction-in-progress state** — Acctual, new bill ("Scanning your invoice to auto-fill the details") ([screen](https://mobbin.com/screens/b812e034-b340-4c0d-b7ee-41d556ea1f07)). Solves: makes OCR/LLM extraction latency legible instead of a blank spinner — the form fields are already laid out, with a scanning indicator at the top telling the user what's about to auto-populate. Maps to Clara: when a Document lands and classification/extraction is running (Q-00 lane), the detail pane should render the field skeleton immediately with a "Reading document…" indicator, not a full-pane spinner. Rejected: a modal blocking spinner over the whole viewer — hides the document itself while it's the thing being read, which reads as if the agent is doing something to a document you can no longer see.
- **List with match/reconcile footer** — Midday inbox ([screen](https://mobbin.com/screens/bb6dcd6c-9b61-4382-a0d8-401ce16b6247)). Solves: a document list on the left where each row shows a lightweight status chip ("Pending," "Analyzing…"), and selecting a row opens the receipt with a "Select a transaction" match action pinned at the bottom of the detail pane. Maps to Clara: Documents list rows carry the same status vocabulary as Work items (so a document mid-classification reads consistently with a Work item mid-review) — reuse the `Badge` variants across both surfaces.

## Journals

- No direct Mobbin reference exists for a general-ledger journal-entry list (none of the sampled apps expose double-entry journals as a first-class UI — QuickBooks/Xero hide journals behind "Advanced"). This is a genuine gap: closest transferable patterns are the **grouped, filterable table** from Linear's Work list (status/date grouping, saved filters) and the **dense tabular financial statement** from Fey ([screen](https://mobbin.com/screens/04db1121-595e-4723-90fb-061cc3bd25be), dark financial grid with year columns and inline % deltas) for a debit/credit ledger table treatment. Maps to Clara: Journals = a `DataTable` with debit/credit columns, grouped by date or source document, each row deep-linking to its originating Document/Work item (journal-entry-first per #576 means every line should be traceable back to its evidence). Flag for follow-up: worth a dedicated Mobbin pass once a specific competitor's "General Ledger" or "Journal" screen is identified — QuickBooks Online's Journal report and Xero's "Manual Journals" list would be the next places to look if this surface needs deeper reference; not fetched here to keep this pass within its per-query budget.

## Registers (chart of accounts, fixed assets, recurring adjustments, aging)

- **Chart of accounts — tabbed groups with inline descriptions** — Wave ([screen](https://mobbin.com/screens/0dfbf491-e722-45a5-8697-3f16439931ac)): top-level tabs (Assets/Liabilities/Income/Expenses) each with a count badge, grouped sub-headers ("Operating Expense"), and a plain-language description under every account name. Maps to Clara: register-type tabs at the top of Registers, `Tabs` + count `Badge`, with descriptions surfaced for accounts that need SST/MYR-specific explanation (useful given "SST no input-tax credit" is a domain quirk accountants new to Clara won't intuit). Rejected: Midday's nested tree table with tax-type/tax-rate/report-code columns ([screen](https://mobbin.com/screens/bbd8aade-bb21-4c0e-8eb9-9d50ea45f220)) — more powerful but denser than a Malaysian SME-firm bookkeeper needs day to day; save that density for an "advanced" toggle, not the default view.
- **Chart of accounts — numbered codes + YTD + archive workflow** — Xero ([screen](https://mobbin.com/screens/60eeff3c-49be-4f67-b5e4-ed283613de86)). Solves: account codes as a sortable leading column, YTD balance inline, and accounts are *archived* rather than deleted (preserves referential integrity for posted journals). Maps to Clara: Registers must default to archive-not-delete for any account/register row with existing journal references — a hard constraint worth carrying into the register's row actions.
- **Aging register — two-bucket-table pattern** — Wave, Payable & Owing ([screen](https://mobbin.com/screens/d0e9e8e5-11d0-4054-9b3f-ec2527d34d03)). Solves: side-by-side "Invoices payable to you" / "Bills you owe" tables, each bucketed Coming Due / 1-30 / 31-60 / 61-90 / >90 days overdue. Maps to Clara: Aging register reuses this exact bucket vocabulary (`Table` with a bucket column), since it's already the universal accounting convention — no reason to invent new bucket names.
- **Recurring register — status-segmented list with a monthly trend chart** — Rocket Money, Recurring ([screen](https://mobbin.com/screens/10e4c041-cc08-41c0-a605-4424dc5486b8)): Upcoming/View All/Calendar tabs, an inactive section collapsed below active rows, and a small monthly-breakdown bar chart. Maps to Clara: Recurring adjustments register = active/inactive split with a `Tabs` switcher, each row showing next-run date and last-posted status. Rejected: PayPal's five-way status taxonomy (Active/Near/Outstanding/Suspended/Canceled, [screen](https://mobbin.com/screens/4286fca7-e4b5-43ba-b073-efc9387dc8d8)) — too many states for what should be a simple active/paused/ended lifecycle in an accounting register; over-modeling a merchant-billing concept onto a standing-journal concept.
- **Fixed assets register**: no fixed-asset-specific screen surfaced in this pass (searches returned bank-reconciliation and general-ledger results instead). Treat the chart-of-accounts patterns above as the base, adding a depreciation-schedule column — worth a targeted follow-up query ("fixed asset depreciation schedule table") if this register gets built before a dedicated research pass.

## Bank reconciliation

- **Two-pane match workspace** — Xero, Reconcile ([screen](https://mobbin.com/screens/b433257a-a7a0-4249-a4a5-04e2681d1432), match/select flow [screen](https://mobbin.com/screens/d434009d-5eba-4d42-833b-19e97f3d1fa7), adjustments + must-match validation [screen](https://mobbin.com/screens/722f15b0-bb7c-4bb3-90b8-0cb41e1cab74)). Solves: left column = imported bank statement lines; right column = Match/Create/Transfer/Discuss tabs against Clara-side transactions, with a running "must match money spent" total that turns red until balanced, plus an inline "Adjustments" dropdown (bank fee, minor adjustment) for the residual. This is the canonical bank-rec UX and should be followed closely. Maps to Clara: Bank reconciliation = `Resizable` two columns, right side `Tabs` (Match/Create/Transfer/Discuss — "Discuss" maps neatly onto Clara's inline-thread pattern from Work items, letting a reconciler flag an ambiguous line for agent/human discussion without leaving the screen). Rejected: nothing structurally — Xero's pattern is close to unimprovable for this specific job; the only adaptation is swapping "Discuss" to reuse Clara's existing thread component rather than building a parallel comment system.
- **Per-account reconciliation status roll-up** — Wave, Account reconciliation ([screen](https://mobbin.com/screens/f81b1c92-b818-4553-8e22-e3858f183b21)). Solves: one card per bank account with a "Reconciled Up To [date]" badge and a statement-balance-vs-book-balance diff shown inline before drilling in. Maps to Clara: a reconciliation summary strip above the two-pane workspace, so a reviewer can see all accounts' rec status without opening each one — pairs with the firm-home "client health glyph" pattern above.
- **Bulk categorize/match bank feed** — QuickBooks, Bank transactions ([screen](https://mobbin.com/screens/8fd16d88-dd92-4c23-a3d5-bc5cebd032ca)). Solves: Pending/Posted/Excluded tabs above a table where every row has inline Match/Categorize actions and a bulk-post action bar. Maps to Clara: the *pre*-reconciliation triage step (before a line even reaches the Xero-style match workspace) — useful for the "auto-post when evidence is unique" posture from #577, where most lines shouldn't need a human at all and only the ambiguous remainder should reach the two-pane match UI.

## Close

- No accounting product sampled exposed a dedicated "close checklist" screen through Mobbin search (Xero/QuickBooks/Wave don't surface one; Deel's "For you today" to-do rail is the closest general-purpose analogue, [screen](https://mobbin.com/screens/c12b258a-d50b-4f5e-b6fe-0d1ad050f6b0)). Given #576 already collapsed the six ceremonies into role-floor + automatic receipts, and #573 decided "Close is a single flow," the more relevant reference is **Linear's project pulse / progress pattern** ([screen](https://mobbin.com/screens/e88b6bd7-3d4b-4e1e-8cd7-a9d2a6852795)): a status pill (On track/At risk), a progress bar computed from sub-item completion, and a "post update" action that snapshots the delta since the last update ([screen](https://mobbin.com/screens/64e4516f-bb0f-42b6-9576-6b4f1d7e6f72)). Maps to Clara: Close = one flow with a Linear-pulse-style header (period, status pill, % complete from underlying role-floor items), and a "receipt" concept borrowed directly from the post-update snapshot — closing the period *posts* a receipt the way Linear posts a project update. Rejected: a literal numbered checklist (classic close-management SaaS pattern) — #576 already ruled out ceremony-as-checklist in favor of role floors, so resurrecting a checklist UI here would fight the product decision rather than express it.

## Reports

- **"Your reports" hub with financial-ratio trend cards** — Xero, financial position / snapshot ([screen](https://mobbin.com/screens/ab410583-e8d2-4e04-af9a-0c6d379d63af)). Solves: a period selector at the top (comparison range explicit: "1 Jan 2026 – 25 May 2026" vs. prior year), then a grid of report cards, each a small stat + trend rather than a full table — the drill-in is optional. Maps to Clara: Reports page = a `Card` grid (per #573, "shows your reports," i.e. a curated set the firm actually uses, not every possible statutory report), with a shared date-range control at the top driving every card. Rejected: Wave's dashboard-embedded single P&L bar chart with no card grid ([screen](https://mobbin.com/screens/b0779fe4-db8c-486e-a5d6-bcccf1828216)) — fine for a one-report SMB tool, too thin for a firm managing statutory + management reporting across many clients.
- **Dense tabular statement view (for drill-in)** — Fey ([screen](https://mobbin.com/screens/04db1121-595e-4723-90fb-061cc3bd25be)). Solves: once a report card is opened, a full financial-statement grid with year/quarter columns and per-line % change badges. Maps to Clara: the "open report" detail view, reserved for when a user drills past the card summary — keep this out of the default Reports landing per the card-grid pattern above.
- Management-report template content and statutory wording are explicitly "not yet specified" per #573 (pending owner/lawyer) — this research does not attempt to resolve report *content*, only the page's structural pattern.

## Onboarding — firm signup → OTP → legal → checkout

- **Account creation → OTP with inline error state → success** — Walmart account flow ([flow](https://mobbin.com/flows/0238f81f-a9c3-443c-85ec-615f0fec7056), OTP boxes [screen](https://mobbin.com/screens/1bd82b7f-b11f-499c-a2cf-cf334821e5a6)); Shop signup ([flow](https://mobbin.com/flows/ec2d5551-50bd-45c9-be09-b5a84a3f6605)). Solves: six discrete boxes (`InputOTP`) that auto-advance, a "Didn't receive it? Get another code" link, and a visible red inline error banner ("Please check and re-enter the 6-digit code") rather than a toast, so the error stays anchored to the field. Maps to Clara: firm signup OTP step uses shadcn `InputOTP` with the same auto-advance + persistent-inline-error pattern — critical because a toast that auto-dismisses is easy to miss mid-signup.
- **Account → plan/trial → payment timeline** — Canva onboarding ([flow](https://mobbin.com/flows/68f04fb3-c6d9-4266-80ba-b59d60ac05b7), payment step [screen](https://mobbin.com/screens/8078ab7e-2257-4f24-bcee-54f4102b3773)). Solves: the checkout step pairs a payment-method form with a **vertical timeline** on the right ("Today — free trial starts," "Jul 19 — reminder," "Jul 26 — subscription starts") so the user understands exactly when they'll be charged before they commit. Maps to Clara: the checkout step of firm signup should show the same explicit timeline (signup date → trial end → first invoice date) rather than a bare "Enter payment details" form — reduces surprise-billing support load. Rejected: a plain pricing-table-then-Stripe-checkout with no timeline (the more common SaaS pattern) — Clara's buyer is a Malaysian accounting-firm owner, a persona highly sensitive to exactly when and how much they're charged; the explicit timeline is worth the extra step.
- **Legal/terms as a lightweight inline acknowledgment, not a blocking modal** — Walmart's create-account form embeds the Terms/Privacy links directly under the password field with a single checkbox ([screen](https://mobbin.com/screens/2bd5d87e-9d98-4311-a102-c3c52c6d1991)) rather than a separate full-screen "Accept Terms" step. Maps to Clara: fold the legal/DPA acknowledgment into the same screen as company details, as a checkbox + inline links, instead of a dedicated "Legal" screen in the wizard — one fewer step in a flow that already has signup → OTP → checkout. Note: actual Terms/DPA legal text is out of scope per #573 ("Terms / DPA lawyer draft is the owner's task"); this only concerns placement, not wording.

## Onboarding — client onboarding interview (LLM-driven, typed questionnaire)

- **One question per screen, numbered progress, list-tap options** — OKX identity/KYC flow ([flow](https://mobbin.com/flows/33e69f00-5625-4bc2-8e50-374ce7c7ee5e)): a dot-stepper at the top ("● ● ● ● ○ ○"), one question per screen ("What is your source of wealth?"), full-width tappable option rows (not radio buttons), and a persistent Back link. Maps to Clara: this is the closest real-world analogue to #580's "typed questionnaire parts that write canonical facts" — each questionnaire part = one screen, `Progress` stepper at top, options rendered as full-width selectable `Card` rows (bigger tap targets read as more considered for a professional/compliance context than tiny radios). Rejected: Laravel Cloud's tighter "Question 1 of 3" survey with classic radio-button rows ([flow](https://mobbin.com/flows/50d44602-9183-47a6-8e5f-91782acd2840)) — functionally fine but reads as a marketing-attribution survey, not a compliance interview; OKX's heavier list-row treatment better signals "this answer matters and gets recorded," which is the correct tone for TIN/entity-type/SST questions feeding canonical facts.
- **LLM chat as the onboarding surface itself, with a persistent context sidebar** — Base44, first-run chat ([screen](https://mobbin.com/screens/2bc7b827-089b-4245-aea7-bca28d079e44)): the whole onboarding *is* a chat with the agent introducing itself and explaining what it needs, left rail shows Chat/Brain/Tasks/Files as the eventual destinations. Maps to Clara: for the parts of the interview that are genuinely open-ended (vs. typed questionnaire cards), the LLM-driven conversation can run in the same chat-rail component used everywhere else in the product — reinforcing that the onboarding *is* the same agent the firm will use afterward, not a disposable wizard. Rejected: a fully chat-only onboarding with no typed cards at all — #580 explicitly wants typed questionnaire parts that write canonical facts (TIN, entity type, SST, payer id, framework), and free-text chat alone is a poor source for fields that must validate against a schema; the typed-card + chat hybrid (cards for schema-bound facts, chat for everything else) is the right split.

## Workspace settings / members

- **Settings as a left-nav category list, not tabs** — Linear workspace settings ([flow](https://mobbin.com/flows/820abf56-0781-456e-b6ed-98609be8edc9), General [screen](https://mobbin.com/screens/7370d11e-e3fc-4638-b9b0-ad512c27824d), Labels [screen](https://mobbin.com/screens/011f7932-2bfb-451f-8385-70a287f6378a)); v0 preferences ([screen](https://mobbin.com/screens/6b62ae24-d11e-4869-aa17-e6a27a1d310b)). Solves: a persistent left `Sidebar` (Workspace: General/Security/Members/Labels/Plans/Billing…, then My Account: Profile/Notifications/API) rather than horizontal tabs, so deep settings trees stay navigable without nesting tabs-within-tabs. Maps to Clara: workspace settings uses the same left-nav shell as the rest of the app (nested under a "Settings" root), consistent with Clara's overall left-nav IA decision from #579 rather than introducing a second navigation paradigm just for settings.
- **Members table with role dropdown + inline description** — Obvious ([screen](https://mobbin.com/screens/7e43776a-22eb-433a-b8a8-66c09235280a)): role `Select` shows a description subtext per option (Guest — "can only access projects they're invited to"; Admin — "can manage members, invites, and workspace settings"). Maps to Clara: the role picker in Members must show these inline descriptions — critical given Clara has a firm/client altitude split plus role floors (#577), where "what can this role actually do" is not self-evident from a bare label like most tools assume.
- **Invite-with-pending-state table** — Linear Members ([screen](https://mobbin.com/screens/37054da5-16ca-474e-88a7-7d49e339d1bc) area) showing Admin (Invited) rows distinct from active members; Copilot client-portal Team page pairs this with a "Client Access" feature-gate banner and a success toast ([screen](https://mobbin.com/screens/6cd14492-9ff4-4564-80ee-d848043aba7b)). Maps to Clara: Members table needs a clear Invited/Active `Badge` distinction and — notably — Copilot's "Client Access" banner is a near-exact analogue for Clara's firm/client altitude permission (an accounting-portal product literally shipping "which client(s) can this staff member see" as a settings concept). Worth revisiting this specific screen when designing the firm→client access-grant UI.

## Chat rail

- **Docked rail with reasoning disclosure and cited sources** — Customer.io agent panel ([screen](https://mobbin.com/screens/fafcbfb9-fa85-4b4d-b17f-54df962305b5)). Solves: a collapsible "Thought for 26 seconds" line above the answer (click to expand the reasoning trace), inline numbered references that open a popover with source links, and action chips (Fix liquid syntax / Add preview text / Optimize images) offered contextually below the answer. Maps to Clara: the chat rail's message component needs (a) a collapsed-by-default reasoning/thinking disclosure, (b) inline citations that pop over to the source Document/Journal/Work item rather than navigating away, and (c) contextual action chips the agent can offer (e.g., "Post this entry," "Flag for review") as first-class chat UI, not just prose. Rejected: HoneyBook's AI panel, which renders as a semi-transparent overlay *floating above* the dashboard content ([screen](https://mobbin.com/screens/fa243020-70b3-41a7-94c1-50e5d51c7355)) — Clara's rail is decided as **docked** (#579), i.e. it reflows the layout rather than overlapping it; an overlay panel would contradict that decision and cause it to obscure the evidence the user is discussing.
- **Right-side positioning as a user preference, not fixed** — v0 Preferences ("Chat Position: Right") ([screen](https://mobbin.com/screens/6b62ae24-d11e-4869-aa17-e6a27a1d310b)). Solves: lets the user flip which side the assistant docks on. Maps to Clara: low-priority nicety — worth a settings toggle once the rail ships, not a v1 requirement.
- **Custom instructions as a persistent per-user field** — v0 Preferences, "Custom Instructions" textarea feeding the LLM ([screen](https://mobbin.com/screens/6b62ae24-d11e-4869-aa17-e6a27a1d310b)). Maps to Clara: a per-firm or per-user "house style" instruction field (e.g., default rounding, preferred memo phrasing) that the ClaraAgent reads on every turn — cheap to add, high leverage for firms with standardized conventions.

## Command palette

- **Cmd+K surfacing structural navigation, not just search** — Linear's "More" menu / command surface exposes Drafts, Initiatives, Members, Customers, Teams, Customize sidebar ([screen](https://mobbin.com/screens/37054da5-16ca-474e-88a7-7d49e339d1bc)). Solves: the palette isn't only fuzzy-search-for-an-issue, it's also a fast path to structural areas a user might not have in their permanent left nav. Maps to Clara: command palette (shadcn `Command`) should index both *objects* (documents, journals, clients) and *destinations* (Registers, Close, Reports, Settings), with recent/frequent items ranked first — consistent with Linear's pattern of using the palette as a navigation accelerant, not solely an entity search box.
- No dedicated "empty/first-open palette" screen was captured separately — the general recommendation is to seed it with recent Work items and recently opened clients on first open (nothing typed yet), mirroring how Vercel's project switcher pre-populates a "Find Project" list before any input ([screen](https://mobbin.com/screens/63496168-dbae-470d-9039-6883d8d1e479)).

## Empty / loading / error states

- **Layout-matching skeletons, including the detail pane** — Frame ([screen](https://mobbin.com/screens/482086dd-4487-417a-b11b-fcbb798e87e4)): gray bars in the exact shape of the eventual content, including a skeleton for the right-hand detail rail, not just the main list. Maps to Clara: every list+detail surface (Work list, Documents, Registers) needs a `Skeleton` state that mirrors the two-pane shape, so the detail pane doesn't "pop in" empty after the list resolves.
- **Empty state that explains and offers the escape hatch** — Linear's filtered-empty pattern (see Work list section above, [screen](https://mobbin.com/screens/d3ab0127-662f-4764-9c84-511cd7345e27)) and Pinterest's "nothing yet" state that pairs a friendly headline with a concrete next action ("Respond to comments, track reactions…") rather than a bare icon ([screen](https://mobbin.com/screens/888b9337-770c-4dd2-ba86-799683069a4b)). Maps to Clara: every empty state names *why* it's empty (no data yet vs. filtered to zero vs. genuinely nothing to review) and gives one primary action — never a bare "No results" with no path forward.
- **Inline, field-anchored error, not a toast** — Walmart OTP error ([screen](https://mobbin.com/screens/1bd82b7f-b11f-499c-a2cf-cf334821e5a6)) — see Onboarding section. Maps to Clara: validation errors on structured forms (questionnaire cards, Document field edits, journal entry forms) render inline next to the field, reserving toast/`Sonner` for transient, non-blocking confirmations (e.g., "Posted," "Reconciled") per the ask-sonner skill's guidance on toast scope.

## Recommended composite (≤30 lines)

**Shell.** Left `Sidebar` (fixed width, collapsible) carries the two-altitude switcher (firm/client) at
the top, then destination nav (Home, Work, Documents, Journals, Registers, Bank, Close, Reports,
Settings). Main content area is `Resizable` two-pane wherever a list+detail relationship exists (Work,
Documents, client record). A docked chat rail (Customer.io-style: collapsible reasoning, inline
citations, action chips) sits right of the main content as a third, always-present column — never an
overlay. Command palette (`Cmd+K`) indexes objects and destinations together, seeded with
recents-on-open.

**Work list ↔ detail interaction.** Left column: Linear-style grouped, filterable table (`DataTable` +
`Popover`/`Command` filter builder, saved views), with a status vocabulary shared across Work,
Documents, and Bank triage rows. Selecting a row opens the right-hand detail pane *in place* (no route
change feel): disposition controls (approve/post/needs-info) pinned at the top, structured fields in a
slim right-hand rail, and an inline activity+comment thread below the description — agent reasoning and
human replies interleaved in one scroll, matching the "detail pane with inline thread" decision in #579.
Bulk triage (bank-feed style) happens *before* items reach this pane; only ambiguous items need a human
here, consistent with #577's event-driven autonomy posture. Evidence-bearing items (Documents, Bank
matches) reuse the same pane shape but replace the properties rail with a two-pane
document-viewer-plus-extracted-fields (Mercury/Melio pattern) instead of a single-column body.

## Anti-patterns seen (avoid)

- **Overlay AI panels that cover content** (HoneyBook) — contradicts Clara's docked-rail decision; an
  overlay obscures the evidence being discussed.
- **Checklist-as-close** (generic close-management SaaS convention) — #576 already collapsed ceremonies
  into role floors; a literal checklist UI would silently reintroduce ceremony.
- **Disposition controls buried below a long scroll** (older invoice/expense forms) — costs a scroll on
  every review at agentic-work volume; approve/reject must be reachable without scrolling past evidence.
- **Bare "No results" empty states** — never disambiguates filtered-to-zero from genuinely-empty; both
  Linear and Pinterest solve this and should be the baseline everywhere in Clara.
- **Toast-only validation errors on structured forms** — auto-dismissing toasts are easy to miss
  mid-entry; keep validation inline and field-anchored (reserve toasts for confirmations).
- **Role labels with no inline description** — most tools ship bare role names; given Clara's
  firm/client altitude split, every role picker needs the one-line "what this role can do" subtext
  (Obvious pattern).
- **Over-modeling consumer-finance concepts onto accounting concepts** — e.g., Copilot Money's
  budget-remaining donut ring has no accrual-accounting analogue; don't import consumer fintech visuals
  where the underlying concept doesn't map.
