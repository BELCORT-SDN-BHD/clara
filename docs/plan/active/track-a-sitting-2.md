## TA-P6 · 两人墙在代理时代量谁

**RULED 2026-08-22: A。** 代理身份永不占据墙的任一端；墙重新瞄准 `on_behalf_of` 里那个**指挥的人**
（→ `requested_by`）；无指挥人时签发 fail-closed 成一个没参与准备的人的动作；收据新增
`agent_prepared`。独资走既有 CLR05 自签臂，签发墙**增加一条独资臂**，第二个人一进来自动升级。
详见 `docs/adr/0074-the-track-a-sitting.md` TA-P6。

**阻塞** · 5 个成员 · 解锁 F-A4 · F-A5 · F-A7

帐上有几道「两个人」的墙：签发一份报表包的人不能是要这份包的人、也不能是封存它的人；
定案关帐时收据要写这一年是「两人复核」还是「独资自签」；开户提交的人不能是任何一个答过
题的人。这些墙量的都是**人的身份**。现在 Clara 会站到其中一端——她会是那个「要这份包
的人」、那个「做了一整年帐的人」。**最危险的失效是无声的**：如果代理身份占了墙的一端，
墙不会报错，它会**自动失效**——那个真正指挥这件事的人，悄悄地重新获得了批准自己请求的
资格，而墙上一个字都没有被改过。

- **A ★ 代理身份永不占据墙的任一端；墙改量「指挥的那个人」。** (1) 凡两人墙比对的身份，
  代理身份既不满足它、也不解除它——墙要**重新瞄准 `on_behalf_of` 里那个指挥的人**
  （法 69 的形状）；(2) **没有指挥的人时**（自跑），墙不是消失，而是把那一步 fail-closed
  成一个人的动作（签发仍要人来，且不得由任何参与准备的人签）；(3) 收据要**如实**：
  Clara 编制的年度不得标成 `two_person`，新增一种 `agent_prepared`，写明「本年度由
  Clara 编制，唯一人类签字人是 X」。 ← **裁定**
- **B 接受失效并记录在案。** 明文承认：Clara 一进来，报表签发的两人墙就失效了；收据继续
  写 `two_person`。
- **C 把墙实质加回来。** Clara 编制的年度必须由两名人类分别复核并签字；自跑的报表包一律
  要第二个人。

**★ 推荐 A 的诚实代价**

1. 要动 `finalize_close` 这个活体和收据表的 CHECK 取值域，而 Track B 的 task #17 Fix A
   要改的是**同一个函数体** → 两条线必须合并成一次迁移或严格排序，并占一次 D1 停写窗口。
2. 报表签发那一支要**重新武装**（把指挥的人写进 `requested_by`，或把 segregation 分支改
   瞄 `on_behalf_of`）——这是判断逻辑，要走完整的独立复核（复核法 1）。
3. **自跑的包会在签发这一步停下来等人**：「端到端」到签发前一步为止（见 TA-P14 的
   pre-sign 一题）。
4. 换来的是一份不会误导审计的收据，和一道**继续咬人**的墙。

**触及的法/裁定**：法 4（maker/checker，人手半边不变；ADR-0072③）· 法 68（ARM-0）·
法 69（领养语义 / 墙量指挥的人）· 法 22（诚实标签）· 法 25 / E-R11 · E-R14（签发是专业
人员的动作）· ADR-0071 G2（钥匙②③）· CLR05 · B3 职责分离 · 复核法 1。

## TA-P7 · 归属墙：非人类的判断可不可以满足不变量 (a)

**RULED 2026-08-22: C（owner 亲裁）——归属是代理的判断；不确定时她跟用户澄清。**
owner 原话：「只要 agentic LLM 能读到对的 DB / context，那就够了。」**这是一次修宪**（PRD §6.2(a) LAW ·
ARCHITECTURE §0.1 · 摘要法 2），三处条文的拟稿在 ADR-0074，**待 owner 下次签摘要才生效**。
四条 walls-validate riders 与 orchestrator 的 A（DB 判定硬号码佐证）异议，见 ADR-0074 TA-P7。

**阻塞** · 4 个成员 · 解锁 F-A7 · F-A3

「一份单据属于哪个客户」这道墙（不变量 (a)，≥0.95）今天在数据库里只认两种答案：**人点
的**，或**死板号码比中的**（TIN / SSM / 银行户口完全相同）。AI 自己的判断在任何信心值下
都被**结构性排除**。F-A7a 要让 AI 自己归户，就必须为她开一格——这会是**第一次由非人类
的方式满足一条基石不变量**。

- **A ★ 墙开一格，佐证由数据库判。** 新增一种「AI 已佐证」的归户方式，成立条件是：两路
  独立读法（OCR 文字路 + 原图路）读到**同一个硬号码**、该号码锚定到版面上的具体区域、
  且这个号码在本所唯一指向一个客户；**是否算数由数据库的确定性谓词判定，不是模型自己
  打分**（与您在 G1.1 给金额定的规矩同形）。**名字永远不足以单独授权归户**——名字只能
  用来排候选：BELCORT 自己就有 ROME PROPERTIES、ROME SECRETARY，重置后 ROME PUBLIC
  ADVISORY 还会以真实供应商身份回到帐里，「ROME」这个名字家族在您自己的帐上就是一个碰撞
  源。同一条规矩往下推：F-A7b 从证书上抄下来的**号码**（TIN/SSM/SST/EPF/银行户口）也是
  「模型产生的识别码」，而 PRD 不变量 2(b) 明写「永不发明识别码」——所以它们要么走同形的
  双路佐证，要么就只能是**建议**，由人回显确认后才落库。 *(→ 落为 orchestrator 的异议)*
- **B 墙不动。** AI 只提候选并说明理由，最终归户仍要人点头或死板号码比中；F-A7a 退化成
  「AI 提名 + 人一键确认」。
- **C 墙全开。** 模型说 0.97 就 0.97，信心值由模型自报。 ← **裁定取 C 的「判断可满足不变量 (a)」
  这一半；其「信心值由模型自报」的形式在议程阶段已被排除，裁的是「判断 + 结构性墙 + 不确定就问」。**

**★ 推荐 A 的诚实代价**

1. 这是**第一次由非人类的方式满足一条基石不变量**：要落 ADR、要重新签摘要、要改三处法条
   文本（PRD §6.2(a)、ARCHITECTURE §0、AGENTS 硬约束），评审走完整梯子——不便宜。
2. **只覆盖「单据上有硬号码」的那一半。** 马来西亚小供应商开的帐单绝大多数只写客户名字，
   不写 TIN 也不写 SSM——这一大类单据**长期停在人工归户队列**里，「单据丢进来就自己进
   帐」在这一类上不成立。换来的是：一次错归的后果不是一条错分录，而是**两个客户的帐同时
   错**，而且若已过帐，撤销要先冲销。
3. 因为 A 与 B 都必然留下「判不出来」的残量，**必须有一个 firm-scoped 的待答问题载体**
   ——今天没有：`wake_open_question` 结构上要求一个已归户的客户，一份还没归户的单据**按
   构造够不到这条兜底**。这是一块新的授权范围（新 scope、新 RLS 形状），要在 F-A7a 一起
   做，否则「挂人工」这句承诺是空话。
4. 选项 **C 建议直接排除并记为「提过、拒了」**——它与法 72「模型永远不给自己的一致性打
   分」同构，也与 PRD §6.1 的数字墙精神冲突。*（**裁定说明**：owner 采的是 C 的判断权，
   不是 C 的自报分数形式；「模型永不给自己打分」原样成立，见 ADR-0074 TA-P7 末段。）*

**触及的法/裁定**：PRD §6 不变量 2(a)（≥0.95 客户归属，LAW）· 不变量 3（零不可归属分
录；<0.95 先问）· 不变量 2(b)（溯源绑定；永不发明识别码）· PRD §6.1 · PRD §4.4（unassigned
lane）· 法 71 / 72 · ADR-015（GRANT 分道）· 硬约束 13 · ADR-0072⑤。

| 成员 | 选 A ★ | 选 B | 选 C ← **裁定** |
|---|---|---|---|
| **OQ-A7-2** 墙开不开一格 | 开一格「AI 已佐证」，谓词在 DB、不是模型自评 | 不开，退化成「提名 + 人一键确认」 | 全开，信心值由模型自报 *(裁定形式：判断 + 结构性墙 + 不确定就问)* |
| **OQ-A7-3** 只凭名字够不够 | 永远不够，名字只能排候选 | 不适用（人点头本来就看名字） | 本所内唯一命中即可归户 *(rider：名字家族碰撞 >1 候选必须澄清)* |
| **F-A7-M3** F-A7b 抽出来的号码受不受不变量 2(b) 管（*遗漏候选*） | 受管：要么同形双路佐证，要么只能是建议 + 人回显确认才落库（`client_identifiers` 永久 append-only，写错只能作废不能删） | 只管会计金额；参考号码不受管，人的回显确认即算数 | 不受管 *(TA-P8 另裁：学来的号码只进知识层，晋升为 key 要人一键确认)* |
| **F-A7-M4** 「判不出来」的待答问题住在哪（*遗漏候选*） | 必须新建一个 **firm-scoped** 的未归户工作队列 | 同样需要，而且 B 的残量更大 | 残量最小，但仍需要一个兜底 *(rider 4：随 F-A7a 一起出货)* |

**若您不作声**（fail-closed 默认，*历史 —— 本题已裁*）：按 **B**——墙不动，AI 只提名，人一键确认；F-A7a 缩成
一条提名 lane，人工归户队列长期存在。

## TA-P8 · 身份资料与学习回路：她学到的可不可以变成明天的权威

**RULED 2026-08-22: B（通用形式），RS 专属扩张 DROPPED，另**授予一道晋升门**。**
她凭判断学到的识别资料只进知识层当**下一次判断的上下文**，永不写成死板比对的 key；key 只有两个来源
（人确认 · 两路见证读到同一个印出来的号码）。Clara 可以**提议**「晋升为硬事实」，人一键确认后
经 `0063` 形状的审计门落库。硬约束 12 仍钉在 RS，不扩张。详见 ADR-0074 TA-P8。

**阻塞** · 3 个成员 · 解锁 F-A3 · F-A7 · F-A8

硬约束 12 说 ROME SECRETARY 的客户永远**只留名字**，不可以补上注册号或税号；0062 那堵
数据库墙也只挡那三个栏位、只挡「被标记客户的**顾客**」——供应商侧、未标记客户、以及
知识库都在射程之外。可是 Wave F 会从三个新方向带回识别资料：银行配对带出付款人的银行
户口号码与银行印出来的名字；归户判断学到「这个 SSM 号是 BEE 的」；上网查证查到某个往来
单位的注册号。**她自己学到的这些东西，可不可以变成明天自动比对的权威？**

- **A ★ 学来的身份资料永不自动固化。** (1) 硬约束 12 的射程**扩大到所有外部识别资料**
  （含银行户口号码），数据库墙一并扩，知识库同禁；(2) **她自己判定的归户不沉淀**成客户
  档案里的号码——只有**人确认过的那一次**归户才允许沉淀，切断「她今天的猜测变成明天的
  确定性权威」这条回路；(3) 上网得来的第三方识别资料**不准写进知识库**，知识库只放规则/
  法规内容，识别事实只能走审计过的往来户门（0063 的形状）。
- **B 只挡固化，不挡记录。** 知识库可以记（含 RS 客户的银行户口、网上查到的注册号），但
  永不写进 `client_identifiers`、永不喂死板比对器。 ← **裁定（+ 晋升门）**
- **C 全开。** 学到什么记什么，并让它成为下次的自动依据。

**★ 推荐 A 的诚实代价**

1. **RS 的银行配对会失去最有力的一条线索**（付款人户口），只能靠金额加日期；同额分不清
   的情况会更常见、更常要人回答问题——RS 这个客户的自动化程度会明显低于其他客户。这是
   刻意付的：硬约束 12 存在的理由本来就是「一旦补料，`_resolve_counterparty` 之后会在每
   一张发票上无声地拒绝」（法 59 记着这笔学费）。
2. **学习变慢**：每个客户、每个号码，第一份单据仍要人确认一次，之后才自动。
3. **要扩一堵已上线的墙**（0062）——它今天是 uuid 钉死、事实驱动、apply 时行为自证的；
   扩它要按同样的规格重做，而且解除仍然只有 OWNER 能做、必须走 0063 的审计门。
   *（**裁定说明**：不扩。硬约束 12 维持 RS-pinned，随 Wave-G 重置一起走。）*
4. **知识库那一侧要加一道识别码写入过滤器**，是新工程。

**触及的法/裁定**：硬约束 12 · ADR-0062 / ADR-0063（解除是 OWNER-only 的审计门）·
法 59（RS 补料陷阱）· 法 73（知识层是学习回路）· ADR-064 反循环（对规则机器已 moot，
形状在此复现）· PRD §6.8（没有删除动词）· PRD 不变量 2(a) · 法 75。

| 成员 | 选 A ★ | 选 B ← **裁定** | 选 C |
|---|---|---|---|
| **A3-OQ-8** 硬约束 12 管不管银行识别资料 | 扩大到所有外部识别资料，DB 墙一并扩、知识库同禁 | 数据库栏位维持现状，但知识库不准记 RS 客户的银行识别资料 | 只管注册号/税号，银行识别资料照记 |
| OQ-A7-6 她学到的号码能不能沉淀 | 只有**人确认过**的那次归户才沉淀成客户档案号码 | 同 A（B 更松，但仍不写 `client_identifiers`） | AI 自判的归户也沉淀，从此自动——一次读错的号码会被永久固化成「死板比对」的一条真理 |
| **F-A8-M4** 网上查到的身份事实能不能进知识库（*遗漏候选*） | 不能：知识库只放规则/法规内容，识别事实走审计过的往来户门 | 可进知识库，但不得进 `client_identifiers`、不得喂死板比对器 | 可进，且可成为下次的依据——一条绕到墙**背后**的补料路径 |

写、不记、不沉淀；RS 的银行配对只用金额 + 日期。

## TA-P9 · 自由读的读取边界

**RULED 2026-08-22: A。** 读面是「决定出来的」，不加签字门：绑客户的会话服务器端强制编译范围；
跨客户读是**具名 + 留收据**的动作（回答，不是拒绝）；HOME 聊天按设计是全所（永不跨所）；
表清单逐条列举并印成审计行（关掉稽核 GAP5-5）；先只开 `interactive`；不按发问人分级、不设逐所签字门。
详见 ADR-0074 TA-P9。

**阻塞** · 4 个成员 · 解锁 F-A6 · F-A5

F-A6 是「随便问 Clara 关于这套帐的任何问题」这句承诺底下的机制：一支跑在结构性只读角色
上的参数化查询工具。问题是——这个只读角色**今天能看到什么，是七十几个 migration 一路
累积出来的结果，从来没有人当成一个决定来审过**：它对几乎整套帐目表都有 SELECT，而且
**隔离只做到「同一个事务所」这一层**，事务所内部哪个客户的帐都能被同一条自由 SQL 读到
（这正是最早那份稽核报告点名的 GAP5-5 高危缺口，至今无人认领）。另外，wake kind 的允许
清单**结构上管不到一条裸 SELECT**（它只能挂在函数名上），现有那道后备墙在这里够不着。

- **A ★ 读面是「决定出来的」，但不加签字门。** (1) 由绑定了客户的会话触发的自由读，
  服务器端**强制把范围编译到那个客户**；跨客户读是一个**单独具名、单独审计**的动作，
  不是默认能力（稽核报告自己开的药方）；(2) 表清单**逐条列举**并作为一条审计行印出来
  （法 34 的家规），而不是继承一份历史累积的授权；(3) 先只开 `interactive`（有人在场）
  这一种唤醒，要伸到无人值守的唤醒另立一次具名裁定；(4) **不按发问人的权限分级**（那是
  凭空发明的新产品能力，现有六个固定读工具都没有），也**不设逐所签字门**（见 TA-P1）。 ← **裁定**
- **B 继承。** 就用现有只读角色的累积授权、全所范围、不限唤醒种类——ARCHITECTURE 字面
  就是这么写的（「跑在只读角色上」），成本为零。
- **C 最大化收紧。** 在 A 之上再加：按发问人的 RBAC 分级收窄 + 逐所签授权。

**★ 推荐 A 的诚实代价**

1. 要在这条读路径上新增一层**客户边界校验**，不能是裸 SQL 直通——多一次迁移/谓词设计、
   多一轮评审，建造成本从「中低」变成「中」。
2. 「表清单逐条列举」意味着以后每加一张表都要改代码并重跑那次对抗审查——这是它的用意，
   但它会让「随便问」在遇到新表时短暂地答不出来。
3. 只开 `interactive` 意味着**无人值守的 lane 暂时用不上自由读**（F-A2 的过帐判断、F-A5
   的自跑报表要靠类型化读），这会在设计里逼出一批新的类型化读动词。
4. 不做的代价：这次「注入面」审查只堵住了「读到不该读的**数据类型**」，却放过了稽核报告
   早就写明的「读到不该读的**客户**」——而且是在明知道缺口存在的情况下放过。

**触及的法/裁定**：PRD 不变量 2(a)/(c)/(d) · ARCHITECTURE §3.2（参数化 + 记帐）·
ARCHITECTURE §3.3（角色楼层今天只管写、不管读）· 法 3（授权按 GRANT 分道）· 法 34
（豁免名单逐条可见）· 法 28（注入面要跨模型对抗审查）· 稽核 GAP5-5（HIGH，无人认领）·
复核法 2（普查只扩不弱）· 硬约束 2（结构性拥有边界）。

| 成员 | 选 A ★ ← **裁定** | 选 B | 选 C |
|---|---|---|---|
| **F-A6-OQ-1** 客户边界 | 会话绑客户时强制把 `client_id` 编译进查询范围；跨客户读另立具名动作 | 只按事务所隔离，靠聊天上下文/提示词自觉 | 同 A |
| **F-A6-OQ-2** 要不要按发问人的权限收窄 | 不收窄（与现有六个固定读工具一致）；要做就单独立项、单独 review | 不收窄 | 收窄到发问人自己的等级——要新建一套「按人分级的读」机制，今天任何读工具都没有 |

## TA-P10 · 非权威层（沙盒）的射程

**RULED 2026-08-22: C′（owner 偏向 C，对齐后的形式）。** 沙盒产物可自由导出、**水印烧进字节** + 导出留痕；
**跨客户导出在「收件人涵盖档案里每一个 `client_id`」的机械校验通过时允许**（不是一刀切禁止）；水印文字
走 owner 一次签的三语 claim-policy 行，缺行拒绝渲染；自由查询的合计数是**叙述性**的——可说、可画、可导出、
可作为推理依据进收据（连查询原文），但**永不**成为持久产物里的权威数字。详见 ADR-0074 TA-P10。

**阻塞** · 5 个成员 · 解锁 F-A5 · F-A6

G4 给了 Clara 一个「分析沙盒」：她可以对帐本自由计算、画图，产物打上「非权威」水印，
结构上永远碰不到封存链。但**「非权威」到底能走多远**没有定：这张图能不能存成文件、能不
能发给客户？能不能把这家客户跟您另外两家比？水印那句话谁来写？还有一个更隐蔽的问题：
一条自由 SQL 算出来的合计数——**输入**是数据库的，**聚合方式**却是模型现写的、没有版本
——它算不算「数据库拥有的数字」？能不能被引用进一份过帐理由、一条知识库条目、一个待答
问题里？

- **A ★ 非权威的东西可以离开屏幕，但要带着自己的标签，并且不准渗回权威侧。** (1) 沙盒
  产物可导出，但**水印烧进字节**（不是 UI 上一层 CSS），并记录谁在什么时候导出了什么；
  (2) 绑定到一个以上 `client_id` 的产物**结构性禁止外发**（导出路径上一道客户基数墙，要
  能在两个方向上被证明）；(3) 水印文字走**版本化的 claim-policy 行**、owner 签一次三语
  （en/ms/zh），代码里没有默认串、缺行就拒绝渲染；(4) 一条自由 SQL 的合计数是**叙述用**
  的：可以出现在答话与沙盒图上，可以作为**推理依据被引用**（连查询原文一起进收据，法 75
  的引用形状），但**永远不得**成为持久产物里的权威数字——过帐理由里的金额、知识库里的
  事实、报表包里的格子，都只能来自 TA-P2 的三个出身。
- **B 只在屏幕上。** 沙盒不生成任何文件、不导出；自由 SQL 的数字只在当前答话里活着，不落
  任何持久文字。
- **C 自由。** 可导出、可跨客户、水印由建方写死一句默认串、SQL 合计数视同普通数据库读。

**C′ 是裁定的形状**：A 的 (1)(3)(4) 原样成立；A 的 (2) 被 **C′ 改成「收件人涵盖校验」**——跨客户导出
不再一律禁止，而是在机械校验通过时允许（集团老板可以看多公司对比）。C 的第四项（把自由 SQL 合计数
视同普通 DB 读）会修 PRD §6.1，**未取**。

**★ 推荐 A 的诚实代价**

1. **会多出第二条渲染路径**（沙盒渲染 ≠ 封存渲染），两条会漂移——尤其 N3 新增的三种图表
   要在两边各实现一次。缓解是共用同一份几何库，但「共用库、两个入口」本身要写进设计并在
   评审里盯住，否则就是 F-A10 最讨厌的那种「两套架构」的小型翻版（判准见 TA-P11）。
2. **沙盒要能出图，得先请您坐一次把三句水印话定下来**（可以和已经挂着的 ms/zh
   claim-policy 文案合并成一次会）；在那之前沙盒只能在屏幕上看。
3. **跨客户的分析只能内部看**：想给客户看就得手工重做成单客户口径。*（C′ 改为：机械校验
   通过即可外发。）*
4. **第 (4) 条会让 Clara 经常说「这个数我只能给你看，不能写进去」**——体验上别扭，但它是
   「数据库拥有每个权威数字」这条硬约束在分析层的必然结果。

**触及的法/裁定**：法 74（沙盒 watermarked non-authoritative，结构上碰不到封存链）·
法 2 / PRD §6.1（含「reporting/export/analysis boundary」那一句）· PRD §8 排除表·
E-R8 floor 2 · E-R14（claim wording 走版本化行）· 法 22 / ADR-048（合成与非权威必须自己
说清楚）· 法 36（fail-closed-on-unknown）· PRD 不变量 2(a) · 法 57/58/59 · 法 75 · F-A10。

| 成员 | 选 A ★ | 选 B | 选 C ← **裁定（C′）** |

| F5-OQ-7 沙盒产物能走多远 | 可导出，水印烧进字节 + 导出留痕 | 只在屏幕/聊天里看——会计要把图放进给客户的月报，只能截屏 | 自由导出，不额外设限 *(C′：可导出 + 水印烧进字节 + 留痕)* |

## TA-P11 · 退休的射程：什么算「第二套架构」

**RULED 2026-08-22: A —— 一条判准 + 三个具体答案。** 判准：**共用同一个确定性核心、每个界面只有一个
入口 = 一套架构；对同一个事实有两条互不知道的计算、或两条互不知道的授权路径 = 两套。**
(1) 银行规则机器**全部退休**（supersede WCC-R5 的银行臂）；(2) **7A-R3 与 E-R13 正式记录为已随规则机器
消灭**（是记录，不是沉默）；(3) SST-02 自己一套表单产出器、共用底下的求值器，写进 F-A10 收口口径。
**在 PR-1 合并之前裁定，如议程所请。F-A10 可以关门。** 详见 ADR-0074 TA-P11。

**阻塞** · 3 个成员 · 解锁 F-A3 · F-A5 · F-A10

F-A10 是 Wave F 唯一一条**高于项目清单**的完成条件：Wave F 关门时只能存在**一套**架构。
ADR-0071/G1.4 点名退休的是「发票编码那一套规则机器」；可是银行那边**另有一套**人手签名
的规则机器（提议/签署/退役银行规则、要 ≥3 次目击才繁殖的目击表、还有一张建议卡），从头
到尾没有被点名，F-A2 更明文把它排除在自己的范围之外。同样悬着的还有两件：撑着「无税
发票永不无人值守过帐」（7A-R3）的那九个控制随规则 lane 一起退休了，这条法要怎么正式收；
以及 SST-02 申报表另做一条产出路径，算不算「第二套架构」。

- **A ★ 一条判准 + 三个具体答案。** 判准：**共用同一个确定性核心、每个界面只有一个入口
  = 一套架构；对同一个事实有两条互不知道的计算、或两条互不知道的授权路径 = 两套。**
  由此：(1) 银行规则机器**全部退休**——停止写入、历史行保留做知识燃料、前端四个面一并
  下架（与 D35/D36 同一个处理法）；(2) 7A-R3 与 E-R13 的登记式解除**正式记录为「已随规则
  机器一起消灭」**——「无税」不再是一道额外门槛，这是**记录**，不是沉默；(3) SST-02
  **自己一套表单产出器**、不进封存/claim 那套机器，但**共用下面的确定性求值器与 bigint
  分**——按判准这不是第二套架构，要在 F-A10 的收口口径里写明。 ← **裁定**
- **B 只退点名的。** 银行规则机器保留为纯人手工具（Clara 不读不写）；7A-R3 原样保留；
  SST-02 硬塞进封存/claim 链。
- **C 押后。** 银行那一半留到 Wave G 再处理，其余不裁。

1. **退休面变宽，而且宽在已上线的共用授权体上**：`accept_bank_rule_suggestion` 要

   作无税」——那是税务申报层的问题，但它会安静地过帐进去。**这一题最好在 F-A2 PR-1 合并
