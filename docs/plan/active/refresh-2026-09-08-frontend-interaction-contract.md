# Clara frontend interaction contract

Date: 2026-09-08. Target behaviour for the accepted refresh, not a claim that these routes or controls are implemented.

This document turns the [34-journey coverage inventory](refresh-2026-09-08-frontend-flow-coverage.md) into concrete interaction requirements. It supplements [product spec §6](refresh-2026-09-08-product-spec.md#6-页面职责与组件提案); accounting authority, Work lifecycle and Knowledge policy remain owned by that spec and the [PRD](../../PRD.md). The [64-component disposition](refresh-2026-09-08-component-contract-research.md) remains the catalog assessment. A Home/Work sample does not establish acceptance for the other journeys.

## 1. One workspace, durable objects and contextual conversation

The selected A shell and client Home pair with B's list/detail Work. Firm and client identity stay visible at every width. Sidebar items navigate real destinations; a page title identifies the current destination. Breadcrumbs identify ancestry without a second copy of the same large heading. The client selector carries the client identity, while the period selector carries its own explicit date scope.

Work is the durable record of an execution. A document is evidence, an accounting object is the business result, a journal entry is the general-ledger effect, a report is an output, and a chat is a conversation. Each can link to the others without taking over their lifecycle. Uploading through Documents and attaching in chat converge after source custody. A user can begin an instruction without an attachment where the operation permits it.

Desktop has one navigation region, one primary content region and one optional Clara region. The sidebar can collapse; the content must remain usable with the rail open. On narrower layouts, list-to-detail navigation uses the full primary region and a Back control restores the list selection and position. A brief contextual form can use a Sheet; a long Work, document or accounting detail has its own address. The narrow Clara Sheet is optional and closing it does not cancel an accepted operation.

The existing client remount/epoch boundary must survive the shell replacement. A result arriving for the previous client cannot render under the new client's heading or submit through the new scope. A firm request can produce several client Work items, but each question, result and financial amount carries its own client.

## 2. Page recipes for every journey

The identifiers below match the coverage inventory. These are the target steps and layout; current capability and source-reference grades remain in the inventory. Unsupported actions stay explicitly unavailable until the relevant backend slice exists. A historical route may redirect to the matching destination, never silently to unrelated Home.

| Journey | Target steps and primary surface | Detail and recovery requirements |
|---|---|---|
| A1 Account / firm admission | Account details → verification → applicable legal/admission steps → checkout status → claimed firm. One focused stage per page with Field and Card. | Persist accepted stages; reload checks the actual claim/payment state before offering resubmit. Late payment confirmation has a waiting explanation and recovery link. Do not infer paid/claimed from a browser redirect. Only supported legal and billing controls appear. |
| A2 Sign-in / recovery | Login or recovery request → sent-link/code state → confirm/reset → intended authorised destination. | Distinguish sent, expired, used, refused and rate-limited. Preserve the email and a safe return destination. Input OTP only when the actual code shape fits; support pasting. Field error and form-level Alert are distinct. |
| A3 Invitation | Open invite → identify intended account/firm/role → authenticate if necessary → accepted membership → workspace. | Token expiry, wrong email, revocation and already accepted each have their own explanation and next action. A valid accepted invite need not run through new-firm signup. |
| A4 Members / access | Settings/Members list → invite or member action → focused form → authoritative roster state. | Invite shows delivery/pending state separately from membership. Role/scope change and removal identify the affected member and firm. Last-owner/current-permission refusals stay inline. A removed live session loses access immediately on the next authoritative response. |
| A5 Firm setup | Resume setup → answer only missing firm facts → saved progress → usable firm Home. | Related facts can be a Questionnaire; optional education can be skipped. Confirmed facts go to the same canonical settings/Knowledge record. Setup progress uses an actual checklist, not an arbitrary percentage. |
| A6 Client / accounting opening | Create or select client → required identity/accounting facts → source/opening intake where applicable → tie-out Work → client Home. | Separate no opening needed from missing imported balances. GL, AR/AP and assets show their own completeness and discrepancies. Sufficient independent bookkeeping can proceed where existing opening/period rules permit; do not add a blanket onboarding approval ritual. |
| A7 Scope switch | Client selector/Command or firm breadcrumb → authorised destination loading → new scoped data. | Preserve the prior Work's true owner. Clear sensitive stale data on permission loss. Preserve an unsent draft only under its original scope; never move it to another client implicitly. |
| B1 Firm Home | Portfolio and Work attention → client/Work drilldown → return to preserved portfolio view. | Work counts and client status disclose coverage and freshness. No cross-client money total masquerading as consolidation. Zero clients offers client creation to an authorised member. |
| B2 Client Home | Needs you / active / recent → relevant Work; financial summary → corresponding books/report; readiness → Close Work. | Four metrics and three charts use the agreed dashboard pack, periods and definitions. Work attention is not hidden by the displayed financial month. Unknown, stale and zero remain visibly distinct. |
| B3 Work list/detail | Filterable list → stable Work detail → current question or result → linked input/object/history. | List filters are visible and clearable; empty list differs from no filter matches. Detail retains current question above Results/Sources/Activity Tabs. Batch child counts are explicit; independent children can finish while others wait. |
| B4 Shared clarification | Open the same question from any surface → read what is missing and why → answer with field/choice/text/file → server acceptance → resumed Work. | A single fact uses Field; a related set can use Questionnaire. Do not force a guessed option: allow correction, supporting material or leaving it pending. Stale/answered-elsewhere/current-permission responses converge without losing a still-useful draft. |
| B5 Activity | Attributable event feed → event detail → Work/object/source. | Activity reports observable events, not internal task names or private model reasoning. Corrections link to both the original outcome and its replacement. Pending questions remain owned by Work. |
| B6 Start Clara | Visible firm/client context → composer and attachments → accepted message → streamed explanation and/or accepted Work card. | File upload and message send have separate states. Sending twice after a lost acknowledgment must not create duplicate Work. An accepted background Work card remains useful after the response stream ends. |
| B7 Continue / stop / cancel | Inspect current Work in the rail → answer or issue a scoped instruction → current result. | Stop reply stops the response stream. Cancel Work is a separately named action; admitted operations may be settling, shown as 正在停止. Completed effects remain linked. No text animation is evidence of execution. |
| B8 Conversation history | New / choose history / archive / restore / delete ordinary conversation text. | New conversation starts empty without erasing Work or confirmed Knowledge; an unsent draft stays with its original conversation. Delete names the conversation and its unsent draft, clears any associated recovery copy, and explains the minimum retained Work basis. Deleted text/drafts cannot reappear after reload or archive restoration. Deletion failure is visible; archive is not presented as deletion. An already accepted Work continues unless explicitly cancelled. |
| C1 Source intake | Upload or attach → per-file receipt → client/type/extraction state → typed detail and linked accounting Work. | Batch rows report individual failure and progress. An unassigned source stays in firm intake until attribution. Extraction success, facts success and accounting success are separate; unsupported kinds are explicit. No Request autodraft prerequisite. |
| C2 Source correction | Document detail → field/source location or management menu → correction and impact → accepted revision / resulting Work. | Original remains readable. Posted effects require the correction chain, not an in-place rewrite. A stale revision keeps the attempted correction visible for comparison. A server-accepted correction followed by lost response is resolved by receipt/read, not a second operation. |
| C3 Journal / JV / manual operation | Accounting/Journals or typed object action → concise expert input or Clara instruction → validation → operation receipt → object and JE detail. | Manual and agent paths expose the same complete accounting result. An optional attachment is truly optional. Balanced cents, source and period failures identify the relevant field or constraint. “View journal” is an inspect action, not the completion of every domain operation. |
| C4 Bank line / match | Statement or account list → line detail → evidence and candidate/book result beside one another → match/create/allocate outcome. | Auto-resolve only with sufficient current basis. Show the arithmetic and residual for partial/multiple candidates; retain ambiguous/unidentified movements as pending. Matching an already booked movement does not create a second cash effect. |
| C5 Reconciliation | Choose statement/account period → current book/statement bridge → resolve linked gaps → completion receipt. | Show beginning/ending values, applicable movements, difference and coverage. Zero difference alone does not prove readiness. Preserve exclusions with the required attributed decision. Readiness/authority governs automatic completion, not a default extra human signoff. |
| C6 Receivables / payables | Open-item list → signed item, due date, identity and source → allocation / settlement history → linked operation. | Keep debtor/creditor roles and credit balances meaningful. Partial, unapplied, undated, reversal and non-bank settlement have explicit states. Unsupported credit-note producers cannot be disguised as working buttons. |
| C7 Fixed assets | Asset list → acquisition/source/value → depreciation policy and schedule → runs/corrections/disposal history. | Acquisition can be complete while policy setup waits. Missing useful life or start date highlights only the dependent setup. A supported disposal shows its asset and GL consequences. Do not silently authorise a future plan from repeated past behaviour. |
| C8 Prepayment / amortisation / accrual | Supported typed action or Clara instruction → source/basis and dates → schedule preview → accepted plan / current run. | Schedule inputs show effect and effective date; prior runs remain immutable. Distinguish supported execution from read-only foundations. Corrections, skipped periods and locked-period handling link to Work. |
| C9 Recurring plans | Plans list → purpose/basis/authority/schedule → next occurrence preview → run history and revise/pause/cancel. | Creating a future plan requires an accepted explicit instruction or an existing explicit authorisation rule whose scope covers that plan; a Knowledge preference or calculation policy alone does not supply authority. No global “enable agentic” switch. A future schedule does not authorise historical catch-up. Duplicate wakes converge on the same run. |
| C10 Accounts / control relationships | Search/filter account list → account detail → supported edit/remap → affected-book check and receipt. | Historical/inactive accounts with balances stay inspectable. Explain protected-code/control-account refusals and remap effects. A configuration change with no financial effect must not fabricate a JE. |
| C11 Close / reopen / late evidence | Period overview → readiness and preparation Work → required decisions → close result; late source → impact and period-treatment decision. | Bank settlement precedes the writer freeze. Separate missing evidence, hard failures and user-permitted scoped evidence exceptions. Schedule time starts preparation; it does not imply readiness. Late input never silently reopens a locked period. |
| C12 Reports | Report list → supported report type, period and basis parameters → generation Work → report viewer → export / trace to books. | Plain TB/GL views and formal outputs label their status correctly. A report type is a selectable output, not another Close workflow. Keep parameters, as-of state and superseded status with the artifact. Current book-snapshot reporting does not imply a selectable cash-basis calculation; such a choice needs a supported deterministic schema/evaluator. Failed or incomplete generation is not a downloadable completed report. |
| C13 Knowledge / identity | Search or category list → fact/identity/policy/experience detail → source/history/conflict → correction or withdrawal. | Show current scope, source, status and applicability. Explicit information saves to canonical records; inference stays unverified. Identity aliases are maintained automatically when supported; no pre-binding ceremony. Corrections show affected work and stale projections. |
| D1 Personal preferences | Settings/Account or Preferences → grouped fields → save state. | Expose only persisted, supported preferences with clear user/firm scope. Preserve dirty fields on failure; saving must not clear unrelated settings. Respect the OS reduced-motion preference. |
| D2 Firm / billing settings | Settings destination → firm/member/commercial responsibility → current authorised state and supported actions. | Accounting policy links to Knowledge and schedules link to Plans. Payment/usage absence has an explanation, not synthetic live controls. Legal acceptance remains versioned and attributable. |
| D3 Operator / administration | Explicit authorised admin destination → queue and detail → permitted support action → receipt. | Operator support access does not expose another firm's accounting. Retain affected entity, current state and refusal/retry context. Do not merge operator controls into normal client navigation. |
| D4 Tax / beta capability | Discoverable Accounting destination → supported read/watch state and explicit capability boundary. | An inactive feature explains what can currently be read. No fake Prepare/File buttons. Existing read-only data remains reachable where authorised. |
| D5 Moved links | Old route/bookmark → corresponding new object or saved view with validated scope. | Preserve back navigation and target identity. Missing or unavailable object has a useful Empty/Alert state. A removed destination explains its replacement rather than changing meaning silently. |
| D6 Retired workflows | Old autodraft, vendor-binding or runtime-only entry → supported Work/Knowledge/history destination. | Retain historical receipts and in-flight legacy visibility. Internal queues and wiki compilation are not normal accounting destinations. A historical action's removal does not erase its results. |

## 3. Shared control and state contract

These rules apply to every recipe, including controls inside chat cards. A component's presence is not acceptance of its behaviour.

| Situation | UI contract | State owner / verification |
|---|---|---|
| Initial read | Skeleton fits expected content; show no placeholder amount as zero. A meaningful error replaces loading. | Authorised read result; loading ends on success, failure or permission loss. |
| Refresh with known data | Retain labelled prior data only while still authorised. Distinguish refreshing and delayed/partial state. | Version/freshness contract; immediately clear data that is no longer permitted. |
| Empty | Empty states distinguish first use, filtered no-results, valid no-data, unavailable capability and missing object. Offer the applicable action. | Actual read outcome, not caught error mapped to an empty array. |
| Short mutation | The initiating Button shows a Spinner and pending label; prevent duplicate local submits without freezing unrelated work. | Server idempotency remains required; a disabled button alone is not protection. |
| Accepted long operation | Show a persistent Work link and observed state. The user may navigate away. | Accepted request/Work receipt, never the lifetime of the original HTTP request. |
| Lost response | Show checking/reconnecting and read the current receipt/state before allowing a distinct resubmit. | Same operation identity for retries; new intent gets a new identity. |
| Field validation | Field error sits by its control; required labels, formats and units are explicit. Focus the first invalid field or a linked error summary. | Preserve user input. Do not change amount/date semantics to make validation pass. |
| Business refusal | Inline Alert describes the concrete constraint, current state and available next action. | No generic red toast for locked period, stale revision, ambiguous identity or missing source. |
| Answer accepted elsewhere | Replace the stale pending action with current accepted answer/time/basis; offer a supported correction route. | Same Work/question/version read. Do not emit another execution for a stale card. |
| Partial batch | Show actual child counts and individual outcomes; let independent children continue. | Parent summary derives from children and distinguishes complete from merely no longer running. |
| Cancellation settling | Show stopping and explain that already admitted operations are finishing; reveal completed receipts. | No new operations admitted after cancellation; do not show terminal cancellation early. |
| Permission change | Read-only where allowed; remove protected data/actions where required and explain the resulting access state. | Recheck the server, including after role/client changes and on resumption. |
| Success feedback | Update the persistent object/Work state first. Base Toast may acknowledge a short action without being the only receipt. | Do not offer Undo for an immutable posting when the actual operation is a separate reversal. |
| Draft across local view changes | Preserve unsent input under the same user/firm/client/object/question version. Tabs and an explanatory Popover do not submit or discard it. | Do not promise reload recovery from memory-only state. Scope change never transfers a draft into a different client. Warn before a navigation that will truly discard input. |
| Context/menu actions | A visible Dropdown Menu provides secondary actions; a Context Menu can duplicate them. Menubar only if a sustained command set justifies it. | Important pending questions and primary next actions stay outside overflow menus. |
| Destructive action | Name the target and effect; use a focused Alert Dialog when confirmation is appropriate, such as actual conversation deletion. | A normal bookkeeping instruction does not gain a second confirmation merely because Alert Dialog exists. |
| Dates and money | Label posting/as-of/due dates distinctly. Allow precise typing alongside Calendar/Date Picker. Reuse the checked money input and minor-unit boundary. | No floating-point amount coercion, locale guessing, timezone date shifts or animated intermediate ledger values. |

## 4. Tabs, overlays, focus and motion

Tabs divide adjacent views of one object: Work results/sources/activity, asset details/schedule/history, or related views within a settings destination. They do not replace client or object route links. The focused tab follows the native keyboard pattern; automatic activation is appropriate only when the panel is ready without noticeable delay. Tab switching never invokes a write. Source: [WAI Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).

Dialog is a focused decision or edit. Sheet is a contextual side task. A narrow Drawer can present a short choice when its height, keyboard and dismissal fit; a long source comparison or multi-section accounting form uses a full detail destination. Do not open an uncontrolled stack of navigation Sheet, chat Sheet and edit Dialog. A menu may close into a labelled dialog with deliberate focus transfer. Native title, initial focus, modal focus containment, Escape, visible close and return focus must be verified; if the trigger disappears, move focus to the next logical element. Sources: [WAI Dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [shadcn Drawer](https://ui.shadcn.com/docs/components/base/drawer).

The main destination has a page heading. Work detail focuses its heading when reached by navigation; merely opening a background update does not steal focus. Answer submission leaves the accepted result reachable, and a list row disappearing after resolution does not dump focus onto the document body. At narrow widths and 200% zoom, the amount, identity, status and primary action remain visible without page-wide horizontal scrolling; a genuinely two-dimensional ledger table may have its own labelled horizontal viewport and a useful row detail.

Retain existing Source Sans/Source Serif bridges, semantic colour roles, density, radius and motion tokens. Glass is limited to surfaces where composited text, focus and controls remain readable. A table or evidence pane needs stable solid readability. Motion communicates panel entry, selection, state transition or chart comparison; do not stagger routine rows or animate money through false intermediate balances. Respect reduced motion for shimmer, chart entry and overlays, and show equivalent static state. The exact timing comes from the current tokens, not a copied reference product's raw values.

## 5. Native agent interaction and announcement boundary

The composer, Message/Bubble, Attachment and Message Scroller display the conversation. A typed Work card displays an accepted request or result, and a typed question displays the currently applicable question. Free text, source upload and structured answers use the same domain admission path. Questionnaire owns local fields and progression; it cannot decide authority, persist its own competing question, or restart accounting from a stale tool part.

Use short observable progress such as “Reading 3 files” with actual counts. Shimmer is a transient presentation of an active response, not a long-running Work status. Describe executed tools and outcomes without exposing private model reasoning. Avoid fabricated steps, elapsed-time percentages or a generic “thinking” state that hides a question waiting for the user.

Message Scroller must keep a user reading earlier content in place while new content arrives and offer a labelled jump-to-latest control. At the latest message, follow new content without scrolling the primary workspace. Reopening a closed rail rereads current Work and conversation state. Stop reply, new chat, archive and delete conversation are distinct from Cancel Work.

Keep one transcript announcement boundary separate from independently announced errors/status/cards; do not nest live logs or make every streaming delta an interruptive alert. Each transition has one announcement owner so a card update and transcript insertion do not announce the same result twice. The current production thread deliberately separates these regions, so a native component migration must preserve the behaviour with assistive-technology checks. The local native-chat prototype is proof of a synthetic stream/answer interaction, not of this full announcement contract or backend recovery.

## 6. Verification and implementation handoff

Each vertical slice must name a journey identifier above and provide one complete user-triggered outcome with its source/authority/accounting state, UI and recovery. Reuse existing operation, scope and receipt tests where they cover the behaviour; do not create a separate mock engine to satisfy UI assertions. A screenshot is visual evidence only.

The minimum review packet for a slice is:

1. A normal journey at desktop and narrow width, including its final persistent result.
2. The concrete missing-information/conflict/refusal path applicable to that action.
3. Duplicate submission or lost-response retry, and the same authoritative result from another entry point.
4. Refresh/resumption and live access change without scope leakage or duplicate effect.
5. Keyboard/focus, 200% zoom, reduced motion and announcement checks relevant to the controls used.
6. Relevant arithmetic/source ties for financial output, and correction/partial/cancellation consequences where applicable.

The backend runtime decision still owns authority-through-commit, version cutover and durable recovery proof. The audit/slicing ticket owns stale-finding disposition and concrete implementation tickets. Research can finish when its choices, evidence and remaining implementation obligations are explicit; it does not need to falsely claim that production acceptance has already passed. Any unresolved product or architectural choice remains a real decision ticket rather than a checkbox disguised as research completion.
