# Dashboard data evidence and metric contract basis

**Reviewed:** 2026-09-08
**Status:** evidence underpinning the owner-selected A+B homepage contract for [确定首页财务指标、聚合口径与数据新鲜度](https://github.com/BELCORT-SDN-BHD/clara/issues/608). This note proves source seams and arithmetic, not implemented dashboard reads.

## Contract boundary

The accepted product contract makes the client home work-first and adds compact financial context; the firm home is an authorised portfolio/workload view, never a combined client ledger ([PRD](../../PRD.md), [product spec §6](refresh-2026-09-08-product-spec.md#L252)). Accounting Work is the durable job/outcome identity, Needs you is its attention view, and Activity is history ([glossary](../../../CONTEXT.md#L15)). Charts remain optional and require a readable value/table fallback plus source, period, currency, and freshness ([component research](refresh-2026-09-08-component-contract-research.md#L50)).

The selected client-home scope keeps Work attention across all accounting periods for the current client. Money defaults to the current calendar month-to-date using Clara's `Asia/Kuala_Lumpur` business date and exact `as_of`; choosing a completed historical month uses that whole calendar month. The money selector never changes the Work population.

Current source inspection found no durable Accounting Work table/read or `/work` route. Runtime `agent_tasks`, Needs-you queue rows, and activity receipts have different identities and meanings, so none can truthfully supply Work counts. The current client home exposes Needs-you domain counts, document queues, latest statement dates, a fiscal-year close card, and recent agent receipts; it exposes none of the proposed cash, AR/AP, or P&L values. The firm home exposes review/runtime/activity/client-status summaries and no monetary aggregation.

## Read-model and response seams

1. Build Work cards from one canonical Work read model. Needs-you, active, and recent are facets over the same `work_id`; pagination rows and overlapping queue populations are not totals.
2. Build a client-scoped financial pack without widening access through an aggregate endpoint. Current bank/aging reads require bookkeeper+; the PRD's Viewer responsibility includes reading authorised information. Align those underlying read permissions deliberately in the implementation slice instead of treating the current stricter gate as a new product role decision. Until aligned, restricted source values stay unavailable to that caller. Compute each internally consistent metric set in one SQL statement/transaction. Keep firm totals to workload counts; never sum client money across the firm.
3. Return metric-specific `status`, value, unit/currency, exact `as_of` or period dates, `computed_at`, definition/query version, source watermark, and coverage. A successful complete read may say zero. Missing period/account classification/due dates, permission denial, or read failure must remain unknown/partial rather than render as zero.
4. `pg_current_snapshot()` can identify the visibility boundary of a read, but it is not a replayable historical dataset. Exact later reproduction needs persisted inputs or a dataset hash. Existing period snapshots contain completed-month trial balance and AR/AP aging, not Work or bank; their stale/current state cannot label unrelated live metrics. The generic metric-input snapshot currently includes approved journal contributions but does not expose a safe closing-transfer exclusion for this home P&L contract.

## Verified implementation seams and limits

- The chart is client-scoped rather than fiscal-year-scoped ([0003](../../../packages/db/migrations/0003_books_core.sql#L43)); `trial_balance_as_of` cumulatively sums approved entries through its date ([0017](../../../packages/db/migrations/0017_wave_b.sql#L3572)). The opening registry permits one non-cancelled semantic seed per client ([0017](../../../packages/db/migrations/0017_wave_b.sql#L1075)); opening entries and their correction mirrors post at that seed's `as_of` ([0017](../../../packages/db/migrations/0017_wave_b.sql#L3376)). They are already part of cumulative TB and must not be added again as an annual base.
- Fiscal years are a separate contiguous period spine ([0056](../../../packages/db/migrations/0056_wave_e_close_model.sql#L232)). Final close computes all income/expense movement, posts only those P&L accounts against retained earnings, and pins balance-sheet positions ([0128](../../../packages/db/migrations/0128_f_a4_pr_1b2_a4_truth.sql#L299)). That is why book cash crosses FY boundaries without a reset, while interval P&L must exclude closing-transfer lines.
- Needs-you counts and their firm/client event-sequence watermark come from the latest `list_review_queue` body, including the later coding-lane exclusion ([0016](../../../packages/db/migrations/0016_a21_compliance_watch.sql#L4558), [0168](../../../packages/db/migrations/0168_coding_lane_kind_exclusion.sql)). The watermark is a mutation position, not a wall-clock freshness promise.
- Bank registration and statement reads are in [0038](../../../packages/db/migrations/0038_wave_c_b_bank.sql#L241). `is_bank_account` remains set after remapping/deactivation; [0121](../../../packages/db/migrations/0121_f_a3_pr1b_agent_limb.sql#L4721) also documents the zero-registry/unmapped detection limit.
- Aging rests on signed items and allocations in `_subledger_outstanding_asof`; the latest `_aging_core` preserves those totals while canonicalising counterparties ([0040](../../../packages/db/migrations/0040_wave_c_c_tieout.sql#L3932), [0149](../../../packages/db/migrations/0149_counterparty_merge_pr_1.sql#L539)). Legacy/no-terms items can have no due date.
- Reporting periods and immutable completed-period snapshots are defined in [0057](../../../packages/db/migrations/0057_wave_e_registry_snapshots.sql#L279). Metric input snapshots are in [0058](../../../packages/db/migrations/0058_wave_e_delta_metrics.sql#L383). Close lifecycle code marks closing transfers and copies that marker to reopen mirrors ([0120](../../../packages/db/migrations/0120_f_a4_pr_1b_close_lifecycle.sql#L515)). The web's business-date authority is MYT ([business-date.ts](../../../apps/web/lib/business-date.ts#L14)).
- The current schema and bank ingestion path are MYR-only; clients have no reporting-currency field. Any explicit non-MYR or mixed-currency input is unsupported/unknown until foreign-currency policy exists, with no implicit FX conversion.

The repository graph was used for discovery and coverage, then every cited SQL/TS seam was read directly because the working tree is metadata-changed and large SQL migrations are only partially indexed. Negative findings are bounded to exhaustive current-tree search, not a deployed-database catalog inspection. No database was queried, so live row completeness, granted roles in a deployed environment, and actual metric values remain unverified.
