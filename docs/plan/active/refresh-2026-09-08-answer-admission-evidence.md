# Current Clara answer-admission evidence

Date: 2026-09-08  
Repository baseline: `68ab432308e1bfe87871565c207f8f4ac1e89101`  
Scope: current clarify answer/cancel admission and delivery only; read-only source investigation

## Decision

The raw Workflow SDK observation that two concurrent `resumeHook` calls can both return 200 is **not a demonstrated Clara answer-admission defect**. Clara's browser does not call `resumeHook`. It submits an interruption id, answer, and operation key to `clara.answer_interruption`; PostgreSQL serializes competing answers on the interruption row and permits only `pending -> answered`. The runtime later leases the single persisted terminal row and calls `resumeHook`.

Preserve and reuse the existing database gate, control-listener delivery path, and frozen workflow registry. Do not add a second first-answer gate around the SDK call. The material follow-up is narrower: prove the real Postgres World behavior both after a crash between resume and `delivered_at` and when a slow/batched resume outlives its lease, then design and verify the write-admission ordering required by accepted owner ruling Q8.

## Duplicate and conflict outcomes

- Same `op_key` and same interruption/answer: the stored receipt is replayed.
- Same `op_key` with a different interruption or answer: CLR10, `op_key reused with different args`.
- Different `op_key` racing the same pending interruption: the first transaction changes the locked row to `answered`; the loser reads the now non-pending row and receives CLR13.
- Cancel wins the interruption row first: answer receives CLR13 because status is `cancelled`.
- Answer wins first, then cancel: both admissions can succeed on their respective state transitions; runtime delivery/abort ordering applies. Current source does not yet prove the accepted Q8 boundary below.

## Accepted cancellation semantics to implement and verify

Owner ruling Q8 already sets the product contract. A cancellation stops admission of new business operations. The UI reports **正在停止** while an atomic operation admitted before cancellation finishes settling. Any completed receipt remains part of the audit trail; undoing its business effect requires the domain's separate reversal path. The task reaches terminal `cancelled` only after settlement is complete.

This is proposed implementation acceptance for Q8, not a claim that the current answer/resume/cancel ordering already satisfies it. The implementation still needs a defined ordering point shared by cancellation observation and business-operation admission, plus tests for the race. The design must bound observation latency and prevent any operation from being admitted after that cancellation ordering point; it cannot promise instant rollback or preemption of an operation admitted earlier.
