## Proposed component contract

Selection rule: use a primitive where its built-in interaction, semantics, or state model removes custom behavior; keep existing routed navigation and domain-specific typed cards; add components by task rather than importing the catalog wholesale.

Disposition vocabulary: **use** means the component has a concrete accepted Clara trigger; **conditional** means add it only when the named trigger is implemented; **no current need** rejects present adoption rather than rejecting the component forever. **Production** means one of the 15 checked-in `apps/web/components/ui` files. **Visual only** means one of the six extra untracked files in the isolated prototype worktree. Every one of the official catalog's 64 entries appears exactly once below.

For the deterministic human-input prototype, the exact state chain is: local transport streams assistant text and an unresolved `askQuestions` tool part → the part ends in `input-available` → native Questionnaire renders the versioned question UI → ordinary answers call `addToolOutput({ tool, toolCallId, output })` → `sendAutomaticallyWhen(lastAssistantMessageIsCompleteWithToolCalls)` requests the scripted continuation → the continuation merges as a new step of that assistant message and renders the accepted-answer/continued state. Ordinary clarification is **not** `needsApproval`; reserve `needsApproval` + `addToolApprovalResponse` for a real approval-gated action. Production must replace the local transport boundary with a Work-aware adapter that validates current request/version and permission, persists the idempotent answer, returns accepted/stale/already-applied/error explicitly, and resumes the owning Work. The isolated native-chat prototype is currently in flux and has not been accepted as tested production behavior.

## Cross-component interaction decisions

**Overlay hierarchy:** durable Work detail, history, requested input and shareable outcomes use a routed Work URL. A **Sheet** adds supporting navigation, filters, or context beside the current route. A **Drawer** is limited to a short touch-first picker/peek on a narrow viewport when swipe interaction is itself useful. A **Dialog** contains one focused bounded form or decision. An **Alert Dialog** is the final interruption for a consequential destructive action. Responsive code may pair Dialog on desktop with Drawer on mobile only when both preserve the same short task, title, draft, validation, submit identity, focus return and dismissal rules; mounting both variants at once is invalid.

**Command visibility:** the primary action is a visible Button or route link. Dropdown Menu holds secondary object actions and keeps items in labelled groups. Context Menu cannot be the exclusive path to any command and has no current Clara trigger. Menubar is reserved for a persistent desktop command suite, which the accepted shell does not have. Command supports search/switching; it does not become an unlabelled action drawer.

**Empty, loading and durable state:**

- First use explains what will appear and offers the first permitted action. No results preserves the user's query/filter and offers Clear filters. A valid no-data result names its period/scope. No permission names the restriction without a fake create/retry action. A read error uses Alert plus retry/support detail; it is not Empty. Render `0` only after a successful complete read.
- Skeleton stands in for a known layout during initial loading. Spinner marks a local indeterminate operation, normally inside a disabled initiating control. Progress requires a measured numerator/denominator. Once Clara accepts background Work, replace activity animation with the durable Work identity, named state and link; do not leave a perpetual Spinner.
- Base Toast is brief confirmation after an action is durably recorded. Persistent result/history remains in Work or Activity, and actionable failure stays inline. Requested input and approvals stay in the owning form/Work view; Toast must never offer blanket approval or become the only accessible notification.

**Forms, dates and chat:** new forms use FieldGroup + Field; related Checkbox/Radio controls use FieldSet + legend; option semantics choose Radio Group, Checkbox, Switch, Select/Combobox, or Toggle Group rather than visual preference. Posting and plan dates are plain calendar dates: Calendar/Date Picker must retain the exact ISO value, allow keyboard/typed precision, state range limits, and avoid timezone shifting. Questionnaire submission carries question/request version and idempotency key; a stale answer must be rejected inline without discarding the draft. Message Scroller owns transcript scrolling; Message/Bubble cover prose, Attachment covers files, Marker covers system/citation boundaries, and typed Work/question/result cards remain explicit siblings. Streaming status is announced once through the existing log contract, without nested live regions.

## Implementation verification still required

Before any add, run `pnpm dlx shadcn@latest add <component> --dry-run`, then `--view` or `--diff` one component at a time. Review every overwrite, normalize generated utility imports to `@/lib/utils`, and preserve `globals.css`, font, semantic color, density and motion tokens. Validate the exact Base API from app-aware generated code rather than copying Radix, old Vaul, or MCP-listed Sonner examples. Do not bulk-install the catalog or copy the visual worktree's files into production as a set. Resolve the empty-registry CLI search discrepancy before relying on search output; MCP inventory is discovery evidence, not the app installation contract.

For each adopted composition, acceptance requires:

- full keyboard operation in logical order, visible focus, accessible name/description, and no keyboard-only or pointer-only command;
- overlay initial focus, focus trap where modal, Escape/cancel behavior, and focus restoration to the invoker after close or route change;
- explicit unsaved-input policy for Escape, outside press, swipe and mobile back; dismissal cannot silently discard a draft or double-submit it;
- one coherent overlay stack with the active layer interactive and closed/transitioned layers unable to intercept pointer or focus; no separately mounted desktop and mobile modal copies;
- usable 320px/narrow layouts and 200% zoom without clipped actions, hidden table meaning, horizontal page traps, or unreachable close controls;
- `prefers-reduced-motion` behavior using Clara's motion tokens, with state meaning retained when translation/scale/stagger is removed;
- distinct loading, successful empty, no-result, no-permission, stale/partial, and error states, each with the currently permitted action only;
- read-only and current-permission behavior proved from the real caller policy; hiding a control does not substitute for write authorization;
- Questionnaire and other durable answers proved against current request version plus idempotency, including stale-answer rejection, retry, reconnect, and duplicate-submit handling;
- Message Scroller anchoring/jump-to-latest, reconnect, attachment failure, one transcript log, and typed-card semantics preserved;
- Toast completion also visible in durable Work/Activity or the changed surface, while field/read errors remain inline and announced accessibly;
- Chart source, exact period, currency/unit, freshness and a readable values/table fallback verified before accepting the dependency or visual treatment.
