## Closure decisions and remaining implementation discovery

1. **Direct debit semantics are resolved.** The owner [confirmed the scope][D611]: observed-debit bookkeeping/settlement and explicitly authorised recurring accounting plans are included; actual payment initiation and mandate management remain future scope. Chat, bank/files and Accounting share the same operation and Work result. This closes the last product choice found by the coverage pass; remaining Partial rows describe implementation discovery or unfinished delivery, not pending owner choices.
2. **Copilot motion now has bounded first-party evidence.** The [motion and chart study](refresh-2026-09-08-copilot-motion-research.md) separates observed public-site row transitions, official recorded-demo states, vendor documentation and inference. It closes the wholly-unobserved gap while leaving exact timing/easing and authenticated-app behavior unclaimed. Clara must still verify its own chart, focus, reduced-motion and refresh behavior.
3. **Accrual/prepayment/amortisation capability needs source inventory before controls.** The product semantics are settled, but the flow audit does not establish which executors/adapters are callable. This is bounded implementation discovery, not a fresh product interview. A missing required executor becomes explicit backend implementation work; absence in the legacy code does not remove an accepted operation from the refresh.
4. **Claim-form execution needs a real capability/schema cut.** Its accounting consequence is settled; extractor/typed fields/business tool support are not proven for every claim kind. The formal spec must name the required kinds, fields and complete-operation acceptance, then build missing support rather than presenting an enabled control without an executor.
5. **The runtime route is resolved.** [The decision][D607] selects the first successor and explicitly hands real-Clara integration, partial-stream recovery, delivery and cutover to implementation. Native-v1 compatibility and its finer replay advantage were tested fairly; its exact dependency costs are recorded.

## Settled direction that should move to implementation acceptance

- All 34 frontend journeys have concrete entry, state, backend ownership, layout/component and failure/recovery requirements. Their remaining work belongs in implementation tickets and acceptance, with source tracing first where an executor is uncertain.
- Work/question identity, chat reset/delete/cancel boundaries, default autonomous execution, close/readiness, JE-versus-business-object boundaries, non-bank allocations, control-account consequences and Client KB scope/authority are product decisions. Do not ask the owner to choose them again.
- The A Home + B Work visual direction, native shell/chat component roles, semantic tokens and Clara-specific restrained motion are selected. The isolated prototype is evidence, not production code.
- Claude research, Karpathy/OKF analysis and bounded vendor/UI research were incorporated with explicit corrections and limits. More screenshots are not a substitute for the production acceptance scenarios already documented.
- The audit/backlog register should classify historical findings and evidence levels, then `/to-spec` reconciles seams and `/to-tickets` creates the concrete implementation graph. [重判旧 audit 与 backlog，切出可验证实现切片][D605] can remain open across those phases.
