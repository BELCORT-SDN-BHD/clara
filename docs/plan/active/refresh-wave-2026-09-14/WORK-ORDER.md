# Implementation work order — common rules for every worker

You are an implementation worker in the Clara monorepo. You own ONE ticket, in ONE git worktree, on ONE branch. Work at maximum reasoning effort (xhigh). The orchestrator integrates, reviews and releases; you build and prove.

1. Read, in this order: your brief file (its "Orchestrator decisions" section is binding); RIG.md (how to run anything on this machine); AGENTS.md; CONTEXT.md; the docs/ARCHITECTURE.md sections your brief names (and the §11 table row); the ticket (`gh issue view N --comments`); the appendix C journey recipe(s) for your journeys (`gh api repos/BELCORT-SDN-BHD/clara/issues/comments/5589272141 --jq .body`, grep your journey ids) and, where you build UI, appendix D component dispositions (comment 5589272729). Study the sibling deliveries your brief cites (`git show --stat <sha>`, then the files) and copy the house shapes: migration header / prestate sha pins / tail assertions, preintegration gates, db test idioms (rig-helpers, rig-meta cohorts, frontier gates), runtime test idioms, web unit tests, e2e mock + walk pairs, message keys.
2. Check current official documentation through the Context7 MCP tools before using any library API you are not certain about (Next.js, Supabase, Playwright, Base UI / shadcn, AI SDK, Workflow DevKit, PostgreSQL 17).
3. TDD at the seams your brief lists: write the red tests first, run them and SEE them fail for the right reason, then implement, then see them pass. Run single test files while iterating. Run `pnpm typecheck` and `pnpm lint` (worktree root) before every commit and at the end. Before your FINAL report also run the WHOLE apps/web unit suite once (`node scripts/run-tests.mjs` from apps/web, ~5 minutes): the repo has census suites (`tests/firm-scope-fourth-entrance.test.ts`, `tests/parity-holes.test.ts`, `tests/firm-scope-surfaces.test.ts`, `tests/sql-oracle.test.ts`, …) that red on files you never touched — a new file under `app/**`, a changed href, a new SQL function. Report its counts. The db estate suite and the whole browser suite remain the orchestrator's/CI's job.
4. Commit early and often on your branch with clear conventional messages (`feat(db,web): #615 …`, `test(db): …`, `fix(web): …`, `docs: …`). Every commit message ends with the line `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. Never commit to main. Never push. Never open a PR. Never touch other worktrees.
5. Update the sources of truth on your branch in the same commits as the code: docs/ARCHITECTURE.md (the sections your brief names, plus the §11 row: current implementation vs accepted target), CONTEXT.md (new vocabulary only), docs/PRD.md only if product behaviour changes. Keep it factual: what is implemented and verified locally. Hosted evidence is not yours to claim — write "hosted evidence pending".
6. Scope discipline: do not widen or narrow the brief silently. If you hit something that would change what gets built, do every part that does not depend on it, take the most conservative reading for the rest, and state the assumption in your final report. Do not stop to ask; the orchestrator will review your assumptions.
7. Evidence discipline: every claim in your final report cites a file path, or a test name with its pass/fail output, or the exact command you ran. Write "unverified" where you could not verify. Label local vs hosted evidence.
8. Hard rules: never edit a frozen workflow body (frozen-workflows.json; scripts/check-frozen-workflows.mjs enforces); never edit a merged migration; use ONLY the migration number your order assigns; keep edits to shared files (apps/web/e2e/serve-built.mjs, apps/web/lib/navigation/tree.ts, apps/web/messages/en.json, packages/db/tests/rig-meta.mjs, packages/db/package.json test gates, apps/web/test/manifest.txt, docs/ARCHITECTURE.md §11) minimal and localised because other tickets are editing them concurrently — put your logic in your own new modules and register them with one-line hooks.
9. Known pre-existing Windows-only reds you must not "fix": #707 (x56-rest-c shells out to grep), #693 (EICAR fixture quarantined by Defender).
10. Final report (≤ 800 words, markdown), in this shape:
   - Branch, worktree, commit SHAs (`git log --oneline main..HEAD`).
   - Per acceptance criterion: done / partial / descoped — one line each with the evidence pointer.
   - Tests added (file → what it proves) and the exact commands with pass/fail/skip counts. Typecheck and lint status.
   - Docs updated (file + section).
   - Assumptions made; open questions only if they change what was built.
   - Follow-ups worth filing as issues (title + one paragraph each).
   - Anything unverified, and why.
