## 1 · Scope, and how Q9's "T1 · T2 · T3" reads

Q9 phases P4 as: *"**P4** firm tiers (T1 invite/RBAC · T2 operator-approved creation ·
T3 screens flag-hidden; admin/metering; pricing SHAPE only)"*.

**T1/T2/T3 are BUILD TRANCHES, not product tier names.** "T2 operator-approved creation" and
"T1 invite/RBAC" are not names a customer-facing tier could carry, and "T3 screens
flag-hidden" only parses as *the tier screens ship hidden behind a flag* — exactly what
"pricing SHAPE only" plus the fenced pricing sitting requires. Recorded as OWNER QUESTION 1
for a one-line confirmation; nothing downstream changes if the answer is a re-labelling. So
the **build order is T1 → T2 → T3**, while the **user journey** runs signup → approval → firm
exists → invites/RBAC. Those are different axes, not a conflict.

**In scope.** The self-serve signup door and its screens · the operator approval queue and
console · the no-firm holding state (§3) · in-firm invite issue/accept/revoke · the member
roster and role management · the tier-selection surface and metering rollup, both
flag-hidden · the R2 cream-ground entry surfaces and the R3 focus unification · the gate and
battery extensions covering all of it. Out of scope: §9.

## 3 · The structural finding: the identity gap

**This is the finding that reshapes P4, and it is not what the backend-gap ledger
expected.** The handoff records the P2 invite door as built. It is built — on the Supabase
Auth side only. On the Clara side it does nothing, and the two sides are joined by a
convention with no mechanism behind it.

`clara.users.id` is documented at `packages/db/migrations/0002_foundation.sql:187` as equal
to `auth.users.id`, deliberately **without a cross-schema foreign key** ("portability"). No
trigger, no function and no door ever writes that row for a real person. Every
`insert into clara.users` in the tree is either the structural agent-identity seed, a
migration probe that rolls back, or a raw INSERT in `packages/db/seeds/0002_core_seed.sql`
running as the deploy role.

The consequence, traced end to end through `apps/web/components/invite-accept-form.tsx`:
a person accepts an invite, sets a password, gets a valid Supabase session, and lands on `/`
with **no `clara.users` row and no membership**. `clara.jwt_firm()` returns NULL, so every
RLS-scoped read returns zero rows and every governed write raises `CLR04 'actor has no
active membership'` at `clara._human_ctx`. The shell renders, and nothing in it works. The
estate has never hit this because the seed pre-creates `clara.users` rows whose uuids must
happen to match the Supabase auth uuids — a coupling that is invisible, unenforced, and will
not survive a real signup.

**Three things follow, and they set P4's shape:**

- **The identity door (ask 1) is upstream of everything else in P4.** Signup, invite-accept
  and `add_member` all dead-end without it. It is the first thing built, not the last.
- **`add_member(p_user uuid, …)` is effectively uncallable from the UI for a new person** —
  not because of its floor, but because nothing can discover the uuid. `clara.users`'
  policy exposes self plus *active* firm-mates, and a not-yet-member is neither. This is why
  P4's invite is **email-keyed** (ask 3) and resolves to a uuid only at accept time, from
  `jwt_sub()`. `add_member` is kept unchanged for the already-provisioned case.
- **P4 must design the no-firm state explicitly**, because it is now a reachable, legitimate
  state rather than an accident. That is §4 E.

## 4 · The five journeys

### A · Self-serve signup — the principal registers a firm

Screens: a public `/signup` (firm name · principal name · email · password), then the
holding state (E).

Two DB facts constrain the chain hard: the applicant has no `clara.users` row (§3), and
`create_firm` refuses any actor who **already holds an active membership anywhere in the
estate**, because `uq_membership_active_user` is global. So "I am already staff elsewhere and
want to start my own firm" must be refused at REQUEST time with a legible message, not
discovered at approval time.

1. `supabase.auth.signUp` creates the `auth.users` row. Email confirmation is **required** —
   PRD §8's interim guardrail names email-verify as half of fail-closed admission, and it is
   the only thing standing between the queue and a bot.
2. On first authenticated load the client calls the identity door (ask 1) to mint the
   `clara.users` row. The display name comes from the form; **the email comes from the JWT
   claim, never client input** — otherwise a caller could claim another person's address.
3. The client calls the registration-request door (ask 2), which refuses fail-closed when the
   actor already has an active membership or an open request.
4. The applicant lands in the holding state (E) until an operator rules.

### B · Operator approval — BELCORT rules on the queue

Screens: /admin/registrations inside the firm shell, visible **only** to a member of the
firm carrying `is_operator`.

Authority: the queue verbs copy `set_wake_source_enabled`'s predicate exactly —
`_human_ctx(role_rank('admin'))` **and** `exists(select 1 from clara.firms where id = c.firm
and is_operator)`. That is the estate's one proven operator gate; P4 invents no second shape.

**Approval creates the firm directly — the admission token never reaches the applicant.**
This is the design's one non-obvious call. The alternative (approval mints a
`firm_admissions` token, the applicant then calls `create_firm` with it) would put a bearer
credential through the browser and add a round trip that can strand a firm half-created.
Instead `create_firm`'s core is **extracted** into a shared internal
`_create_firm_core(p_actor, p_name)` with two entrances: `create_firm` keeps its signature
and behaviour unchanged, still token-gated, still the ops escape hatch; and
`approve_firm_registration(request, op_key)` is operator-gated and passes the *applicant* as
the actor rather than the caller. That is law 81's "one deterministic core with one entrance
per surface", the same extraction PR-1c used for `_depreciation_run_due_core`.
`firm_admissions` is left byte-untouched — zero grants, zero policy, as today.

The core must preserve everything the LIVE 0017 body does, including opening the
`onboarding_plans` firm-scope plan and revision 1 and returning `plan_id` alongside
`firm_id`. A screen written against 0004's or 0005's return shape would silently drop it —
the superseded-body class; the annex pins the byte evidence. Rejection is a first-class verb
carrying a reason, never a silent deletion.

### C · In-firm invite — staff join an existing firm

Screens: an invite dialog on /admin/members; the existing public /invite/[token] accept
page, extended.

Issue (admin+): `invite_member(email, role, op_key)` (ask 3) writes a `clara.firm_invites`
row and returns the invite id. It does **not** create a user and does not send email.

Sending email needs the Supabase service-role key, which the browser must never hold, so the
mail step lives in a server-only Route Handler that (1) verifies the caller's session,
(2) calls `invite_member` **as the caller** so the DB performs the authority check, and
(3) only on a successful return uses the service key to send the Supabase invite. The UI is
never the wall; the handler is a courier, not a guard. This is judgement logic and takes the
independent review pass under review law 1.

Accept: `accept_invite(token, display_name, op_key)` (ask 4) is one transaction that
provisions the `clara.users` row from `jwt_sub()`, inserts the membership at the invite's
role, and consumes the invite. **The wall is that the JWT's verified email must equal the
invite's email** — without it, anyone holding the token binds it to their own account. That
is a second, independent wall on top of Supabase's `verifyOtp` binding, which the P2 surface
already performs and which stays exactly as built. The existing accept page keeps its
click-gate, hard-coded `type: "invite"`, subject-binding check and `router.replace("/")`;
P4 adds one step after the password is set — the `accept_invite` call, whose refusal renders
verbatim like any other.

### D · Members and roles — the RBAC surface

Screens: /admin/members — the roster, the pending-invite list, role change, remove.

Reads ride one new consolidated view (ask 5), because today name, email and status live on
three surfaces with three different visibility rules — `users_visible` (names, any status),
`clara.users` (email, active only, no rank floor), `firm_memberships` (role and status).
Consolidating them is also the natural place to put a rank floor on email, the standing
Track-A debt row. Writes are the three existing doors unchanged — `add_member`,
`set_member_role`, `remove_member`; P4 adds only `revoke_invite` (ask 6).

**The last-owner wall is not pre-empted in the UI.** `_tf_guard_last_owner` refuses `CLR09`
when the last non-agent active owner would be demoted or removed. The UI lets the click
happen and renders the refusal verbatim; pre-disabling would be the UI guessing the DB's
answer, and the house law is that a `DoorRefusal` renders verbatim and no control invents a
wall. Every act re-reads the roster afterwards — no optimistic update.

**Affordance shaping, as a rule:** whole surfaces below the caller's rank are **hidden** from
nav; in-context verbs above it are **shown disabled with the required rank named**. Hiding
avoids a dead end; disabling teaches the ladder. Neither is a security boundary —
`_human_ctx` is. There is no re-activation verb and P4 does not ask for one: re-inviting a
removed person creates a fresh membership row, which the partial unique index permits.

### E · The holding state — an authenticated session with no firm

A new route renders honestly for a session with no active membership: registration pending,
registration rejected with its reason, or invite-expected. It is the one screen that must
work with `jwt_firm()` NULL.

**Where the check lives.** Not in `apps/web/proxy.ts` — the JWT carries no firm claim (`jwt_firm()`
is a DB lookup), so the proxy would need a data round trip and it is deliberately the auth
gate only. Instead the firm shell's layout, already a Server Component that explicitly
declines to re-check auth, gains a **scope** check: read the caller's context once (ask 7),
redirect to the holding route when there is no membership. The fail-closed direction holds —
a failed read and an empty result both route to the holding state, which grants nothing.

`apps/web/proxy.ts` changes by exactly one line: `/signup` joins `PUBLIC_PATH_PREFIXES`. The holding
route is **not** public — it requires a session, it just does not require a firm.

## 6 · R2 and R3 — execution, and two collisions to surface

### R2 — the cream ground on entry surfaces

**Mechanism.** The four entry surfaces (login, signup, invite-accept, holding) move into one
route group whose layout owns the cream ground. Route groups add no URL segment, so every
existing URL is unchanged, and R2 becomes **structural** — a page is on cream because of
where it lives, not because someone remembered a class.

`--identity-canvas` is defined at `apps/web/app/globals.css:166` and deliberately **not**
bridged into `@theme inline`, above a comment naming that bridge a "founder-approval item
under §3.3 and §9". **R2 is that approval.** The execution replaces that comment with R2's
grant recorded verbatim — the citation stays, its conclusion inverts — and adds the
`--color-identity-canvas` bridge. The comment is not deleted: it records why the question
was open.

**Collision to surface — R2 is, against today's tokens, visually a no-op.** The entry pages
render on `--shell` today. Measured with the gate's own functions:

| | ratio | RGB delta | verdict |
|---|---|---|---|
| identity-canvas vs **shell** (today's entry ground) | **1.0082** | (0, −1, −3) | imperceptible |
| identity-canvas vs background (white) | 1.0814 | (−8, −9, −13) | perceptible |

The founder note was granted for a change that, executed literally, no one can see — the
pages it applies to are already on a near-identical ground, and cream only reads against
**white**. Owner question 2 puts the choice plainly: accept R2 as a provenance change (the
entry pages now cite the identity token, which matters when that token later diverges from
`--shell`), or give them the composition the ruling was reaching for — a white card floating
on cream. The second is what makes the brand's front door read as one, and it needs a token
decision, because a white card on cream is **1.081** and `--border` on cream **1.195**: the
card would have almost no edge. Text on cream needs no decision — all ten semantic pairs
pass 4.5:1, tightest `muted-foreground` at **4.636**, worth pinning so it cannot drift.

### R3 — unify on the shadcn ring

**The collision is real, and it is NOT the cream-specific one R3 anticipated.** R3 asks the
gate to re-derive the ring composited "including on the R2 cream ground" and to surface an
R2×R3 collision if it fails there. Measured, the translucent ring fails **on every ground in
the app, white included** — cream is incidental.

| effective indicator | on cream | on shell | on white | on surface-subtle | bar |
|---|---|---|---|---|---|
| the ring halo at 50% alpha, composited | **2.317** | **2.310** | **2.363** | **2.313** | 3:1 — FAILS all |
| the solid `--focus` outline (contract §9, today's base rule) | 6.197 | 6.248 | 6.702 | 6.182 | PASSES all |

So this is an **R3 × WCAG 2.1 AA (SC 1.4.11) collision, ground-independent** — and Q7 ruled
AA as the formal bar. Two things sharpen it:

- On bordered primitives (Button, Input, Textarea, Select, Badge) the idiom also swaps a
  **solid** `focus-visible:border-ring` edge, so a solid carrier exists there — but its
  outward neighbour is the halo, not the ground: **2.674–2.837**, still under 3:1. On any
  focusable element with no border slot (a plain link, a list row) the halo is the *only*
  carrier, at 2.31.
- **The contrast gate has never measured this idiom at all.** Both existing focus pairs use
  `fg: (h) => h("focus")` — the solid token — and their `source` strings cite only the base
  `:focus-visible` outline rule. Nine components render the other idiom and no pair sees it:
  a pre-existing gate blind spot, independent of P4, found by this pass.

**Recommendation (owner question 3): raise the ring's alpha rather than abandon R3's shape.**
The halo alone clears 3:1 at ≥64% on cream, shell and surface-subtle, and ≥62% on white, so
moving the ring to 65% alpha passes everywhere with margin while keeping the translucent
character R3 chose. It is the smallest change that makes R3 lawful — and it is an amendment
to a founder amendment, so it is the owner's, not this lane's.

### The gate work, concretely

`PAIR_SPECS` in `apps/web/scripts/check-token-contrast.mjs` is a closed-world array and
already supports composited colours — `destructive-on-destructive-10` uses the
`composite(token, alpha, overHex)` helper the spec signature passes in. So no schema change
is needed; the additions are rows. **The gate has no `--strict` flag** — one existed and was
retired at the P3 finale; `main()` now fails on any failing pair unconditionally. Any
instruction to "flip it to `--strict`" is stale.

Rows to add: six composited focus-ring pairs (cream, shell, white, surface-subtle, secondary,
accent) at threshold 3 · ten cream-ground text pairs at 4.5 · the input-boundary pairs below.

**A third finding, pre-existing and worth its own decision (owner question 4).** No pair
measures a form field's boundary. `--input` (#c7c5bd) against every ground it is drawn on:

| on white | on shell | on cream | on surface-subtle |
|---|---|---|---|
| **1.728** | **1.611** | **1.598** | **1.594** |

SC 1.4.11 wants 3:1 for the visual information needed to identify a component, and
`apps/web/components/ui/input.tsx` ships `bg-transparent` — the field has no fill distinguishing it
from the page, so the border is the *only* identifier and the 3:1 applies squarely. This is a
live AA failure on today's login and invite pages and on every P3 form, not something P4
introduces; P4 merely makes it much more visible by adding four form-heavy screens. The fix
is a token change (darken `--input`), which is a clarabook-frontend contract recut, so it is
surfaced rather than taken.

## 8 · Battery plan

The gates are the hand-written rule engine and the token script, not axe-core (the P3 finale
recorded a confirmed axe false positive). A surface is registered into a scan by having its
own test file mount it with fixture props and assert zero violations — there is **no
known-violation pinning mechanism**, so a real violation is a component fix, never a pinned
exception.

- **a11y scans** — one file per new surface: signup, holding, members roster, invite dialog,
  registrations console, tier panel. Plus the two P2 surfaces that were **never registered in
  either scan** and are in P4's blast radius: the login form and the invite-accept form.
- **Keyboard walks** — the invite dialog and the role-change control are the two that matter
  (a dialog that traps focus, a menu that must be operable without a pointer); plus login,
  signup and accept as form walks.
- **Contrast** — the rows in §6. The cream `muted-foreground` row at 4.636 and the composited
  ring rows are the ones that will catch drift.
- **Auth-boundary tests** — extend the existing suite: `/signup` is public and every other new
  route is not · the no-firm redirect fires on empty AND on failed reads (both directions
  asserted, not just the happy one) · accept refuses a JWT-email/invite-email mismatch · the
  Route Handler refuses an unauthenticated or cross-origin caller and never sends mail when
  the door refused.
- **Enumeration** — every new test file goes explicitly into `apps/web/package.json`'s `test`
  script. Node 20 does not directory-scan for `.test.ts`; an unenumerated file silently never
  runs. Add a count control so a dropped entry is loud.
- **DB-side** — each ask's train carries rig tests for its floor, refusal codes and receipt,
  including a negative test per floor and, for ask 8, a positive control that a non-operator
  admin is refused.

## 9 · NON-GOALS

- **Pricing amounts.** Fenced — the owner's sitting. Every price renders through one named
  placeholder component stating the amount is pending; never a number, and never `RM0` or an
  em-dash, both of which read as "free".
- **Payment wiring.** Stripe is the named provider (Q-B) and the checkout shell stays
  provider-agnostic, but no wiring lands here — it rides the sitting plus tier-3's own gate.
- **Capability gating by tier.** Owner question 6; laws 76/78/81 forbid it and this design
  does not assume it.
- **Client-level permissions.** Roles are firm-wide; per-client access is not in the schema.
- **Multi-firm membership.** The global unique index makes one active membership per person
  an estate-wide invariant; P4 designs within it (owner question 7).
- **The mobile corridor.** Q6 scope — the entry surfaces are single-column and will behave,
  but no corridor work is claimed.
- **New `parts[]` wire types.** P4's surfaces are pages and forms, not chat parts; the
  catalog and its tsc guard are untouched. The four-part bump stays P6.
- **Narrowing the 0002 email grant.** Ask 5 creates the floored surface that makes it
  possible later; the base-table revoke needs its own consumer census (Track-A row).
- **Re-activation of a removed membership.** Re-invite instead.

## 10 · OWNER QUESTIONS

Each carries this lane's recommendation. None is resolved here.

1. **Do Q9's T1/T2/T3 read as build tranches** (invite/RBAC → operator-approved creation →
   flag-hidden tier screens) rather than product tier names? *Recommend: yes — the design is
   written to it; a re-label changes no work.*
2. **R2 is visually a no-op against today's tokens** (cream vs the entry pages' current shell
   ground is a 3/255 max-channel delta). Accept it as a provenance-only change, or pair the
   cream ground with a white card so the front door actually reads as one? *Recommend: the
   white card — but it needs a card-edge token decision, because the card is 1.081 and its
   border 1.195 against cream.*
3. **R3 fails SC 1.4.11 on every ground, not just cream** — the composited ring halo at 50%
   alpha measures 2.31–2.36 against a 3:1 bar, white included. *Recommend: move the ring to
   65% alpha (clears everywhere with margin, keeps R3's translucent shape). This amends a
   founder amendment, so it is yours; keeping both idioms is what R3 just ended.*
4. **Form-field boundaries fail SC 1.4.11 today**, 1.728 on white, and no gate row sees it.
   The fix is darkening `--input`, a token-contract recut. *Recommend: take it, in the same
   §9 recut PR R3 already owes clarabook-frontend, and add the gate rows here.*
5. **Who may change a firm's tier?** *Recommend: the operator only, for beta. A self-serve
   upgrade button with no payment wired would be a fake control, which the house law forbids.*
6. **Confirm tiers are a BILLING concept only** — price and included allowance — and never a
   capability gate or a usage brake. Laws 76 ("meter, never cap"), 78 ("capabilities
   default-on, no per-firm dial") and 81 ("every usage gate that pauses automation is
   REMOVED"; migration 0105 exists to delete one) all forbid the gating reading, and the ruled
   PRD §8 shape — base monthly tier plus metered overage — is compatible with them.
   *Recommend: confirm billing-only, so no lane later builds a T1 feature wall.*
7. **One active membership per person, estate-wide** is a hard DB invariant. It means a
   principal who is currently staff at another firm cannot register their own without being
   removed there first, and a BELCORT operator cannot hold a client-firm membership.
   *Recommend: keep it and refuse early with a legible message at request time. Changing it
   is a schema change with wide RLS blast radius.*
8. **Signup posture and the deploy obligation.** `apps/web/README.md` currently instructs that
   Supabase "Allow new users to sign up" be **off**, calling invite-only "a product invariant,
   not a UI choice". P4 inverts that. *Recommend: the flag flips in the same PR that ships the
   approval gate, never before — the standing law is that a security mechanism is not weakened
   ahead of its replacement — and the README wording is re-worded in that PR to "self-serve
   signup is open; admission is fail-closed behind the operator approval queue".*
9. **The `is_operator` ceremony.** Zero firms carry the flag and marking BELCORT is a raw
   audited ops act. *Recommend: schedule it with the ask-8 train; the operator console cannot
   be smoke-tested before it runs.*
10. **Metering has no rank floor** — `get_llm_usage_summary` lets a viewer read the firm's
    monthly spend, while `audit_log` and agent receipts both floor at bookkeeper+.
    *Recommend: add an admin floor in the DB (ask 11); a UI-only fix would not be a wall.*

## 11 · Mobbin grounding — UNMET, and why

The handoff's rule is that every NEW product flow is grounded in a Mobbin reference, and the
task named the MCP as available in-session. **It is not authenticated** — the authenticate
call returns an OAuth URL needing a browser round trip this lane cannot complete
autonomously.

No Mobbin references are cited here, because citing references this lane did not consult
would be exactly the fabrication the repo's evidence laws exist to prevent. The obligation is
recorded as open, not quietly dropped. Four flows need grounding before build, conventional
enough that one authenticated sitting closes all four: multi-tenant **signup with an approval
hold**, an **operator approval queue**, a **members + roles table with an invite dialog**,
and a **tier selection panel**. R5 already approved adding the server to `.mcp.json`; doing
that in the same sitting makes this reproducible for every later lane.
