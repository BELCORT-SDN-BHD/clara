## 大白话

这张票的场景很具体。客户「隆兴贸易」6 月 10 日银行进账 RM550.00。会计师上个月已经按发票记了一笔
「Dr 银行 550 / Cr 销售收入 550」，这笔分录已经过账（approved）。现在月结单来了，那一行必须**挂到
这笔已有分录上**，而不是再记一笔现金——否则这个月的账面现金会多出 550 块，而且是凭空多的。

**今天已经很扎实的部分**：数据库里这条路是**完整的、活的**。`clara.match_bank_line`（0038:3817）
先锁住那笔分录、再锁客户、最后锁银行行，重读月结单还是不是「在世」的，重算这笔分录在银行科目上**还
剩多少额度**，拒绝已被别人匹配的行、拒绝被冲销的分录、拒绝超额；**只写一条匹配关系和一张收据，一笔
新分录都不生**（只有会计师自己填了「差额调整」才会生一笔，那是另一回事）。并发两个人抢同一行，第二
个人会被按名字拒绝（0038:4042-4051）。Clara 这边也有：`wake_match_bank_line`（0121:6031）带一套
八项「横杆」自检（有没有开着的例外、金额对不对、是不是有第二笔一模一样的候选、额度够不够……），任何
一项不过就**只留收据、不动账**。

**真正缺的是四件事，全在「人看得见的那一半」**：

1. **候选面上看不到该看的东西。** 数据库那条候选读只吐 entry_id / 日期 / memo / coding_kind /
   counterparty **id** / 剩余额度——**没有对手方名字**（web 的类型里写了 `counterparty_name`，
   DB 从来不吐，所以这一栏永远是「—」，`match-types.ts:49` vs `0038:8021`），**没有匹配历史**，
   **没有可信度/依据**（那条 `list_bank_line_suggestions` 已经在 0129:395 被整条退役），
   `high_stakes` 是写死的 `false`（`0038:8025`）。界面本身是一串复选框，不是表。
2. **「重试只产生一张收据」今天做不到。** 数据库的幂等是真的（`_reserve_op`，0004:46），但网页端
   每点一次就现场 `crypto.randomUUID()` 生一把新钥匙（`match-doors.ts:26`）——响应丢了再点一次，
   拿到的是「这行已被匹配」的拒绝，不是原来那张收据。房子里已经有正确写法（`useDecisionKey`，
   `work-cancel-dialog.tsx:95`），银行这条车道没用。
3. **「有开着的例外时，这一行要留着待办、并给一条明确的恢复路径」——数据已经算好了，没人显示。**
   `_wdb_line_booking_block`（0044:2459）会吐出 `exception_booking_outstanding` + 每一笔
   `caused_by` + `remedy_calls` + `remedy`；全仓 grep，web 和 runtime **零个消费者**。而且带开例外
   的行会直接从「未匹配清单」里消失（0040:4117-4123），会计师在 Matching 页看不到它。
4. **「模糊的候选留一个问题」今天没有对象承载。** 银行车道拒绝时写的是 `bank_agent_receipts` 一行
   （agent）或一条内联拒绝（人），**没有任何 Work / 问题对象**。这条和 #947（工资）/ #949（租金）撞
   在同一个形状上，谁先落地谁定形——必须先裁定，否则会造出第二套。

**这一轮新查到的一件事，值得单独说**：票面写的第二条路径（B3「Work 列表 / 详情」）要长的那个页面，
**房子里已经建好了**——Work 详情页把「当前这个问题」放在 Results / Sources / Activity 三个页签**上面**
（`work-detail.tsx:567-647`），代码注释里还把验收那句话原文抄了一遍（`:545`）。真正卡住的不是页面，是
**开问题的那道门**：`open_work_question` 只发给 Clara 的运行时（`0180:686`），而且必须挂在一个**正在跑
的**会计 Work 上，没有就按名字拒绝（`0180:607-615`，不在 `running` 是 `:641-642`）。会计师在银行页面点一下产生的歧义，身上没有那个
「正在跑的 Work」——所以这条路今天对人是断的。要么让 Clara 从对话里开这个问题（那就是发新正文），要么
承认这一票不建这条路。这是 **Q6**。

**最硬的一个判断**：这张票**不需要动冻结的工作流正文**。聊天里的 `match_bank_line` 工具走的是
DB 的 `wake_*` 门，返回值原样透传（`chatTurn.v14.bank.ts:77`）；候选包也是 DB 自己拼的
（`0121:5735`）。**只要把新字段加在数据库那一侧，冻结的 chatTurn 正文一个字都不用改**——这是本票
最省的一条路，也是它和 #649 那种必须发新正文的票最大的不同。

## Frozen-body verdict

**No frozen successor is needed — and that is a measurement, not a preference.**

Neither `chatTurn_v21` nor `claraWork_v5` nor `bankAgent_v2` is required for this slice, because every
enrichment this ticket needs lands **below** the frozen boundary:

1. **The candidate/line data**: `list_bank_match_candidates` and `list_unmatched_lines` are DB functions,
   and the chat lane does not read them through TypeScript — it reads
   `_agent_get_bank_pack_core`'s jsonb (`0121:5685`), which **inlines their bodies** (`:5714-5771`).
   Enriching the read enriches the pack, and the pack rides through the frozen chat body untouched:
   `BankPackPart.pack` is `Record<string, unknown>` (`chatTurn.v14.bank.ts:79`).
2. **The act result**: `runMatchBankLine` (`chatTurn.v14.bankActs.ts:59-72`) posts the DB's jsonb into
   `BankActPart.result` verbatim (`chatTurn.v14.bank.ts:77`, `:82-95`). A richer `_finish_op` payload
   (linked JE ids, the no-new-cash statement, the residual arithmetic) reaches chat with **zero** runtime edits.
3. **The refusal**: `classifyBankResult` already recognises `{status:'refused', rung_vector}` and
   `{status:'refused', reason}` (`chatTurn.v14.bank.ts:82-95`); a new `rung_vector` key or a new Tier-C
   reason is data, not a contract change.

**What WOULD force a cut, and must therefore stay out of the slice:** a new chat *tool* (a new zod input,
a new `execute`, a new roster entry — all literal in `chatTurn.v14.tools.ts:108-166` and
`chatTurn.v20.tools.ts`), or a new typed part kind. So: **if AC9's "one Work question" is to be opened
BY CLARA FROM CHAT, that is a `chatTurn_v21`.** If it is opened by the database as a side effect of the
refusal, or by the human web, it is not. That is Q1.

> **One alternative worth naming and rejecting.** The enrichment could be computed in a new non-frozen
> runtime lib and merged into the pack in TypeScript. Reject it: the estate's own precedent is that any
> module a frozen workflow imports is **frozen by closure** — `packages/runtime/lib/periodic-adjustment-basis.ts`
> is in `frozen-workflows.json` with that note, and `check-frozen-workflows.mjs` hashes the transitive
> relative-import closure. A lib the chat bank acts import freezes on import. The DB is the recuttable
> placement here, and it is also the only placement both lanes (human RPC and wake) already share.

**Also true and worth stating positively:** `wake_match_bank_line`'s signature does not change, so the
`wake_fn_allowlist` roster, `assert_wake_allowed` and the `clara_wake_interactive` grant (`0130:89`) are
