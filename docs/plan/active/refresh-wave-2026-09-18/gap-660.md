## 大白话

这张票要做的是：会计师打开「Sinar Maju Sdn Bhd」这个客户的首页，**一眼看到两个数和两条趋势**——
账面现金 RM 182,340.55（截至今天 2026-09-18），本月（9/1–9/18）利润 RM 23,110.40；
现金那条是六个时点（4月底、5月底、6月底、7月底、8月底、加上今天），收入费用那条是六个自然月
（4月到9月，9月标明「到 9/18 为止，未满月」）。点任何一个数，都能追到组成它的那些分录。

**今天有什么**：客户首页已经是一块真正的「情况板」（`client-workspace-overview.tsx:115-203`），
有身份带、需要你、在跑的 Work、文件积压、银行、关账、最近活动七块。#650 刚交付的
`clara.get_client_work_pack`（`0214:234`）是这一波所有「带时间戳、带覆盖、30 秒补读、60 秒说延迟」
读法的样板，网页那半（`use-client-work-pack.ts:63-200`）可以几乎照抄。

**今天缺什么——四件事，一件比一件硬**：

1. **客户首页上今天一分钱都没有。** 银行那块只显示「每个账户最新一张月结单的日期」，
   它自己的头注写明「never coverage」（`client-bank-summary.tsx:1-18`）。整个首页 grep
   `cents`/`MYR` 零命中。所以这不是「改一个数」，是从零加一条钱的读法。
2. **「哪些科目算现金」这件事，数据库今天答不出来。** 会计科目表上没有「现金类」这一列
   （`0003:47-57`：只有 asset/liability/equity/income/expense 五类和一个 payable/receivable 的
   `account_class`）。唯一结构化的现金标记是 `is_bank_account`，而它**只由「登记一个银行账户」
   这个动作盖上**（`0121:4721-4722`）——**零用现金、手存现金永远盖不到**。而且这个估算有一条
   明写的家法：「**永远不准用科目名字或编号去猜**」（`0121:4749`）。所以「有余额的停用账户 + 零用现金」
   这个集合，今天**没有任何合法途径推导出来**，必须有人把它定下来。
3. **「排掉年结结转」这件事，反而已经有现成的正确标记，而且有一个坑。**
   `journal_entries.closing_transfer`（`0016:51`）就是为这件事造的，SST 那个评估器用的判据
   （`0016:602`）和这张票要的一字不差；关账分录和重开镜像今天都会被正确盖章
   （`0120:514-516`、`0120:797-814`）。**坑是**：0120 之前关的年度，那面旗是 false
   （0120:518-521 自己写明「born false forever」），0016:217 当时还种了一条
   `closing_transfer_review` 待办给已有客户。所以老年度的利润数**今天算出来是错的**，
   这必须如实标成「覆盖不全」，不能假装算得准。
4. **图表这个零件还没装。** `apps/web/components/ui/` 里没有 `chart.tsx`，
   `apps/web/package.json` 里没有 Recharts——装它等于给这个部署到 Cloudflare Workers 的前端
   加一个新的运行时依赖。颜色变量倒是早就备好了（`globals.css:109-113`、`:350-354`）。
   另外「期间选择器」全仓库不存在，「追到账簿」的落点也不存在：`/journals` 只按客户过滤，
   没有按科目、按日期的过滤（`lib/journals/api.ts:81`），试算表/总账页面整个网页端没有。

**最硬的那个判断**：第 2 条。数据库里其实**已经有**一套「受治理、带版本、带生效区间、
成员被 sha256 冻住、同一时刻只有一个 published 版本」的科目集合模型
（`clara.account_sets` / `account_set_versions` / `account_set_version_members`，`0058:104-121`），
写它的门 `create_account_set_v1`（`0058:363`）也已经授权给了 `clara_authenticated`。
**但它解析成员时写死了 `is_active`**（`0058:344` 的 `_metric_selector_account_ids`），
点名一个停用科目会被明确拒绝——**正好是这张票必须包含的那一类**。
而且这扇门在 2026-08-28 的普查里被记成「**退役候选**、产品史上零调用者」
（`apps/web/lib/reports/types.ts:216-224`）。所以「直接骑现成的」走不通，
要么另开一扇门写进同一批表，要么重切一条属于报表 delta 车道、被 0113 用 sha 钉过的函数。

### Q1 — 「哪些科目算现金」由谁来定？

**大白话.** 要显示「账面现金 RM 182,340.55」，先得回答「哪几个科目加起来才是现金」。
**今天**：会计科目表上没有「现金类」这一列；唯一的结构化标记 `is_bank_account` 只在「登记银行账户」时
盖上，零用现金永远盖不到；而家法明写「永远不准用科目名字或编号去猜」。数据库里确实有一套现成的
「受治理、带版本」的科目集合（0058），但它的解析器写死了「只收在用科目」，而这张票**必须**包含
停用但还有余额的账户——正好被它拒掉；而且那扇门在产品史上零调用，被记成退役候选。
**我的建议**：新建一张属于这张票的「现金科目集合」表和一扇 admin 才能用的发布门，形状照抄 0058
（版本、生效区间、成员 sha256 冻结、同一时刻只有一个 published），但成员**不筛 is_active**，
并且每个成员要写明「为什么算现金」（银行登记 / 人工声明为现金 / 人工声明为零用现金）。
同时给一个只读的「候选建议」：把所有 `is_bank_account=true` 的科目（含停用、含有余额的）列出来，
让人确认；零用现金**必须由人加**，因为系统没有任何合法依据去猜它。
在有人发布之前，首页的现金格显示「现金科目集合尚未确认」并给一个入口——**不显示 0**。
**另一条路的代价**：重切 `_metric_selector_account_ids` 去放开 `is_active`，会改变全估算里**每一个**
科目集合的成员语义，而 0058 的冻结校验只对着存好的 sha 重算、不重跑解析器，所以这种漂移**静默不报**；
同时 `create_account_set_v1` 被 0113 用函数体 sha 钉过并派生出 agent 孪生体，重切它等于连带重派生。
**代码名**: `clara.cash_account_set_versions` / `cash_account_set_members` /
`publish_client_cash_account_set` / `propose_client_cash_accounts` vs
`clara._metric_selector_account_ids(0058:344)` + `clara.create_account_set_v1(0058:363, pinned 0113:46)`.
