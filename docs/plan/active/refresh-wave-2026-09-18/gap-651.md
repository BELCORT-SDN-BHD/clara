## 大白话

这张票的一句话是：**「按已经签好的折旧政策，把每一期折旧跑出来，而且以后改估计不许回头改已经提过的账。」**

举个具体例子。Nasi Lemak Sdn Bhd 2024 年 3 月买了一台咖啡机，成本 RM 12,000，直线法、5 年、残值 RM 0。
今天这套东西**已经能跑**，而且跑得相当扎实：

- 有「折旧授权」这个东西：bookkeeper 提议、**admin 亲自签**、admin 才能撤（`0041:3277/3316/3361`）。签的人是谁，
  后面每一笔机器过的折旧分录都记在他名下。
- 有一条每天跑的皮带（`reconciler-fa.mjs`），它**自己不算日期**，只问数据库「这个客户最早哪一期还没提」，
  然后叫 `run_depreciation_period` 跑那一期。
- 一期折旧 = 一张日记账 + 每台资产一行不可改的折旧明细 + 一张运行回执，**同一笔事务里一起落地**（`0041:2318-2330`）。
- 重复触发（皮带跑、人手跑、断线重跑）都收敛成同一笔（op key + 两个唯一索引）。
- 改估计（比如年限从 5 年改成 7 年）是**往后生效**：旧那一行封存，新开一行接着提，已经提过的**结构上就改不了**
  ——想把生效日期设在已提期间之内，数据库直接按名拒绝（`0041:3164-3172`，CLR37 `fa_revise_effective_conflict`）。

**那还差什么？差五件事，每件都很具体：**

1. **「这次改动算哪一种」没人记。** 会计上改年限（估计变更）、改会计政策、和「上次算错了要更正」是**三件不同的事**，
   处理方式也不同。今天数据库里一个字段都没有（219 个迁移全文搜过，零命中），所有改动一律当「估计变更」处理，
   而「算错了要更正」这条路**根本没有门**——门会直接拒绝你。
2. **关了账的期间，折旧会先起草、再在批准那一刻撞墙。** 而且更糟：那张死掉的草稿会**卡住这个客户之后所有期间的折旧**
   （`0041:1921` 一看到有未结草稿就答「不到期」），要人手工去撤掉。没有任何一个测试跑过这条路。
3. **资产详情页的「历史」页签，看不到折旧历史。** 数据库的读门 `get_fixed_asset` **已经把每一笔折旧明细返回了**
   （`0041:4175`），前端从头到尾没读过这个字段（全仓搜索只搜到类型定义）。页签里现在放的是「前身/后继/同单据同批」
   这类资产血缘，不是「这台咖啡机哪个月提了多少」。
4. **跑折旧之前看不到预览。** 今天那个对话框就是两个日期框加一个按钮（`fa-depreciation-runs-panel.tsx:99-119`），
   按下去才知道会提多少、哪几台被跳过。票里明写要 preview 和 exact JE/asset effects。
5. **Clara 这一侧没有入口。** 有意思的是——**门其实早就造好了**：`wake_run_depreciation_catchup`
   （`0138:2413`）带理由、带模型、带回执、带「没有在世授权就拒绝」的挡板，还接进了关账对话车道（`0159:333`）。
   但它的 wake source `close_prep` **是登记了但关着的**（`0133:915-917`，`0223:247` 上个月还再确认了一次），
   而且账本里有一条明确裁定：**要开它，属于 `closePrep_v2` 的事，要自己走一次评审**。

**最大的一个岔路口**：票里有半句话是「把折旧的到期适配器注册到共享调度器」。但 `CONTEXT.md` 第 37 行白纸黑字写着
**「折旧和关账排程不是计划种类，按名拒绝」**，数据库也确实按名拒绝（`0223:590-594`）。也就是说，这半句话和
仓库现在的词汇表**是冲突的**。我的建议是**不要搬**（理由和代价见 Q1）——折旧已经有自己的授权和自己的调度器，
缺的不是「搬家」，是把授权补齐成计划那套法律真正要求的样子：**指向哪一条指令**，和**从哪个月开始往后跑**。

  the cadence's). `through` bounds a catch-up and defaults to the current book day.

  — `(p_client, p_through, p_op_key, p_obo)`, the `complete_fixed_asset_particulars_for` OBO shape

  **A NEW verb name is mandatory, not stylistic:** `rig-meta.mjs:691-693` is an executable census that fails the
  moment `run_depreciation_manual` reaches a machine role.

  one before Clara can run depreciation." · `period_draft_outstanding` → "A depreciation draft is already waiting for
  approval; approve or withdraw it first." · `period_earlier_unmet` → name both dates · `period_request_invalid`
  (`not_ended`) → "That period has not ended yet." · CLR19 `write_into_closed_period` → name the fiscal year and the
  reopen path · CLR04 `obo_not_active` / `insufficient_role` → "You no longer hold the authority to run this."

**Q2 — 签了授权，要不要自动把过去补提出来？** *(changes what is built)*
**今天**：`_fa_oldest_unmet_period`（`0041:1904-1960`）返回**最早**一个未提月份，没有任何下限；
`reconciler-fa.mjs:111` 每个客户每轮最多连跑 24 期。也就是说，给一个有两年资产的客户第一次签授权，
人批准掉第一张草稿之后，后面 23 个月会**自动过账**。而计划车道的法律正好相反
（ARCHITECTURE §5D：「错过的期间一律走显式补提，扫描从不回填」），C9 的配方也写着
"A future schedule does not authorise historical catch-up"。

**另一条路的代价**：什么都不改，第一次签名就静默补提两年折旧，而这正是 C9 明确禁止的行为。

**Q3 — 「改折旧」分几种，这一波做几种？** *(changes what is built)*
