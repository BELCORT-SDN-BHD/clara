## 大白话

这张票的场景是这样的：事务所接手一家已经在做账的公司——比如「新亚五金」——上一手会计交来一张
2025-12-31 的试算表，四十二行，借方合计 RM 1,284,530.00，贷方一模一样。我们要把这张纸变成账本的起点：
每一行对到我们的科目、总数一分不差、人看过点头、一次过账，之后所有数字都从这里算起。读不懂的行不能偷偷丢掉，
要留在那里等人处理；中途断了能接着做；做错了能更正，但更正要留痕，不能把原来的数字抹掉重写。

**今天已经有的，比想象中多。** 数据库那一整套是完整的：期初登记簿（一个客户同时只能有一份）、目标行、
明细分录、批准门（要求 serializable、要求另一个人复核、要求整份对得平、要求期初权益科目净额为零）、
差异表、还有一条巡检会在事后发现「对不平了」并推到「需要你」。网页上 `Registers → 期初` 这一页也真的做完了：
建立、取消、重开、下明细、改错、批准、四道闸门逐条显示过没过——142 个界面文案键。

**缺的是「有来源」这三个字。** 三根线各断在一个地方，而且都能指到具体一行：

1. **读试算表的程序写好了，没有任何生产代码调用它。** `packages/runtime/lib/opening-tb-cells.mjs`
   把 OCR 出来的表格单元格读成数据库能直接吃下的证据行，纪律严到「整张对不平就整张拒绝」「印的总数和我们
   加出来的不一样就整张拒绝」；三套测试全绿。但全仓库只有测试文件 import 它。
2. **浏览器里根本建不出「带文件」的期初。** 「新建期初」对话框把「凭哪份文件」写死成
   `tieDocumentId: null`（`apps/web/components/registers/opening-seed-lifecycle.tsx:62`）。
3. **就算建出来了，带文件的期初只有一条路能录入数据，而网页里没人走。** 那条路是 runtime 的
   `POST /api/opening/parse-targets`（`packages/runtime/src/openingRoutes.ts:32`，已经挂在服务上），
   网页全仓库没有一处调用它。而人手录入的那扇门在遇到带文件的期初时会**直接拒绝**
   （`0017_wave_b.sql:3013-3016`，理由 `parsed_target_writer_required`）。

**所以今天真实能做的只有一件事：人把四十二行一行一行敲进去。** 票面写的「有来源的期初总账」，在浏览器里
从头到尾走不通。这不是「差点交互」，是三根线都没接。

**还有一句话说错了，要改。** 能力目录（迁移 0191）对「前期总账」这一格写着「这份文件只是存着，Clara
推导不出任何东西来驱动业务」。但 `POST /api/seeding/prepare` 今天就能从一本前期总账里读出对方、科目和
日期，开出一批建议给人过目（`packages/runtime/lib/seeding-parse.mjs:377-378`）。这格今天是错的，
AC1 要改的就是它。

**最硬的一问：读试算表的程序接在哪。** 接在 OCR 那一步最便宜——不用迁移、不用切冻结正文，改一个非冻结文件
就行；代价是那一刻还不知道这份 PDF 是不是试算表，所以它会对每一份扫描件都跑一遍（程序本身足够保守，
认不出来就返回 null）。接在「分类之后」最干净——只有被标成期初/管理账的文件才读；代价是要加一条新的处理车道、
两个 CHECK 加值、一条迁移。我的建议在 Q1。
