## 大白话

这张票要做的是：**一张销售发票、一张供应商账单，不管是上传的、在对话里说的、还是会计师自己在
Accounting 里点出来的，都要一次性变成四样东西——一个说得清「这是发票还是账单」的业务对象、一张分毫不差
的平衡分录、一条带到期日和正负号的应收/应付未结项、一张回执——而且要互相链得上，重复提交只算一次。**

举个具体的例子。客户「Rome Properties」收到供应商 Alpha Supplies 的账单 RM 1,060.00（货款 1,000，
SST 60），账单日 2026-09-10，账期 30 天，到期 2026-10-10。今天这条路**走不通**，分三层：

1. **会计师在网页上根本没有「记一张账单」的入口。** `/clients/…/accounting` 上唯一的主按钮是「记一笔
   日记账」（`accounting-hub.tsx:48-58`），那条路走的是 Work 车道。而 Work 车道的过账核心**明文拒绝**
   任何碰到应收/应付控制科目的分录——`0204:550-570` 那一段叫 `generic_control_leg`，理由写得很清楚：
   「一笔泛用日记账不得携带控制科目分录」。所以 Dr 费用 / Cr 应付 这张最普通的账单，在 Clara 今天的主
   车道上是**明确被拒绝的**，不是忘了做。
2. **应收应付未结项今天只有一条产线，而 Work 车道不在上面。** 生未结项的那个钩子
   `_subledger_on_approve`（`0037:1050`）只有六个调用者（`0216:939-945` 重新钉过），Work 车道的过账
   核心**不在其中**——这件事 #639 已经量过并写在 `0216:30-38`。而且未结项是「发票还是账单」这个 kind
   完全取决于分录上的 `coding_kind` 字段（`0037:994-1006`），Work 车道从来不写这个字段。
3. **到期日今天不是从账单上读来的。** 唯一的到期日产线是 `0040:6008-6024` 那段拼接：
   `过账日 + 交易对方的默认账期天数`。Alpha Supplies 如果没在 `counterparties.payment_terms_days` 上
   填过 30，这张账单的到期日就是**空的**；就算填了 30，Clara 读到的「账单上印的 2026-10-10」也进不了
   库。这正好是验收里「preserve … due-date basis」那一句今天不成立的地方。

**今天已经有的、不用重做的**：上传发票 → Azure 抽事实 → autodraft 车道自动过账 + 生未结项 + 带到期日
这一整条**是通的**（`intake-lanes.mjs` → `invoiceFacts_v1` → `autodraft.mjs:40-46` → `autoDraft_v10`
→ `_agent_post_entry_core`（`0106:866`）→ `_approve_entry_core` → `_subledger_on_approve`），
`x37.c2` 这条测试就在证明「账期 30 天 → 到期日精确到日」。应收应付的**读**面也齐了：账龄分桶、交易对方
对账单、抵消/反抵消弹窗都在 `/registers` 的 aging 页（`aging-register.tsx`、`aging.ts`）。
未结项的正负号法律（发票为正、账单为正、贷项为负、结算为负）已经写死在表的 CHECK 里
（`0037:764-771`）——第 11 条验收要的「极性」有一半是现成的。

**最硬的一道选择题**：要让 Work 车道能记发票，那条 `generic_control_leg` 的墙必须动，而它在
`clara._record_journal_entry_core` 里——那是一个被钉过五次、约 610 行的核心函数
（`0204:152-761`），上一波明令禁止重切。**没有别的办法绕过去**：#638 员工报销之所以不用切核心，
正是因为它刻意走「非控制科目」的其他应付款（`CONTEXT.md:443`），而发票/账单按定义必须打在控制科目上。
所以这张票要么切第六次核心，要么另起一个平行过账门（等于把重放、取消、外发、回执四套保证复制一遍）。
我建议**切核心，但只开一条极窄的口子**：仅当这个 Work 在新的发票关系表里有一行时才放行，其余一切照旧。

## Proposed slice

### Migration — ONE new additive file (**number assigned by SYNTHESIS**; frontier at base is 0224)

**§A · The typed business object.** `clara.trade_invoices` — the `clara.staff_expense_claims`
(0221) and `clara.periodic_adjustments` (0194) shape:
- `id uuid pk`, `firm_id`, `client_id`, `work_id uuid NOT NULL UNIQUE`, `logical_op_id text`,
  `kind text not null check (kind in ('sales_invoice','supplier_bill'))`,
  `counterparty_id uuid` (nullable at admission only while a party question is open — see Q2's
  recommendation, under which it is NOT NULL),
  `document_date date not null`, `due_date date`,
  `due_date_source text not null check (due_date_source in ('stated','counterparty_terms','absent'))`,
  `reference text`, `currency text not null check (currency = 'MYR')` (PRD:127 — multi-currency is a
  stated boundary), `total_cents bigint not null check (total_cents > 0)`,
  `tax_facts jsonb` (opaque, echoed, validated against nothing — the #638 rule),
  `source_document_id uuid`, `recorded_by uuid not null`, `on_behalf_of uuid`, `created_at`.
- **No `entry_id` and no `receipt_id` column** (corrected in reconciliation). `0221:350-355` states
  the rule and its reason verbatim: the entry and the receipt are DERIVABLE BY JOIN and are never
  stored on the typed relation, because storing them needs an UPDATE of an append-only row at
  posting time — exactly the shape the table refuses. Both directions are already indexed:
  `ix_operation_receipts_work` (`0178:451`) and `ix_operation_receipts_entry` on
  `(effects->>'entry_id')` (`0178:454`), which is compared as TEXT and never as a uuid cast of the
  jsonb expression (`0181:317`, `0183:690`, `0184:2085`).
- Tenant-carrying composite FKs throughout (`(work_id, firm_id, client_id)`,
  `(counterparty_id, firm_id, client_id)`); `source_document_id` NULLABLE and MATCH SIMPLE so a
  documentless, chat-stated bill skips the check entirely (`0221:344-349`).
- `check (due_date is null or due_date >= document_date)`;
  `check ((due_date is null) = (due_date_source = 'absent'))`.
- Append-only belt + FORCE RLS + zero DML grants. The belt admits **zero** updates to the invoice
  row — there is no back-stamp to admit — written column by column in the `0221:476-500` idiom so a
  later writer cannot quietly widen it by adding a `SET`, and refusing DELETE and TRUNCATE by name.
- A child append-only status ledger (`admitted` / `posted` / `refused`) which **carries the
  `entry_id` and the `receipt_id` on its `posted` row**, appended by an AFTER INSERT trigger on
  `clara.operation_receipts` where `outcome='committed'` and a trade-invoice row names that
  `work_id` — the #638 shape, including its stated reason that the ledger "is where the posting
  moment is recorded, and it carries both ids so §E's trigger and the reads have one indexed handle"
  (`0221:353-355`; DECISIONS 2026-09-15 §2 #638).

p_particulars jsonb, p_basis jsonb, p_basis_origin text, p_source_refs jsonb, p_model text)
returns jsonb`. **The body order is #638's, step for step** — `0221:1207-1220` narrates each step
and why it sits where it sits, and the draft's "write the row, then call the core" is corrected
here, because the core mints the `work_id` itself (`0194:1231`) and no caller can hold one before
it returns:

1. **The intent key, first.** Blank or whitespace ⇒ `invalid_intent_key` before anything durable
   (`0221:1232-1236`, the core's own C82.1 rule at `0194:1074-1077`).
2. **The payload half.** `clara._assert_trade_invoice_basis(p_client, p_particulars, p_basis,
   false)` — `kind` one of the two admitted values, with a credit-note-shaped payload refused as a
   typed CLR10 `credit_shape_not_admitted` **before** the bare column CHECK could fire (the core's
   own stated rule for exactly this, `0194:1078-1081`: "a 23514 out of the INSERT carries no typed
   reason and the runtime could not classify it"); exactly one control leg of the right domain; the
   control leg's signed amount equal to `total_cents` with the right sign; balanced; exact cents;
   `due_date >= document_date` (`invalid_due_date`). (`0221:1238-1240`.)
3. **The authority preamble** — firm, membership, active member, `bookkeeper` floor, active client;
   the core's own arms, order and tokens (`0194:1089-1116`) restated here because step 6 writes
   durably and must never run for a caller the core would refuse (`0221:1242-1269`), including the
   no-existence-oracle rule: an unknown firm and a non-member both answer `client_not_found`.
4. **THE REPLAY PROBE, before any write.** One read of `clara.accounting_work` on
   (firm, client, intent_key) — the unique that makes it safe is `uq_accounting_work_intent`
   (`0178:336`). A Work already under this key resolves to the `trade_invoices` row it carries and

## Questions

### Q1 — 上传的发票，这一波要不要也变成一件 Work？

**大白话.** 今天你上传一张供应商账单，Clara 会自动读、自动记账、自动生成应付未结项——这条路是通的。但它
**不产生一件「工作」**：Work 列表里看不到它，Needs you 里看不到它，也没有 `accounting_work` 行可以链接。
这张票的第 5 条验收要求「Documents、Work、Journals、AR/AP 四者互相链得上」。
**今天**：上传走 autodraft 老车道（`autodraft.mjs` → `autoDraft_v10` → `_agent_post_entry_core`），
十三道准入检查是真实的独立保证，不是冗余的模型复审——规格书自己这么写的（`612-body.md:145`）。
**我建议**：这一波**不动上传车道**。#655 只做 Work 车道的发票/账单操作（对话 + 网页 + 引用文件），
并交付一条「等价性证明」测试：老车道和新车道对同一笔经济事实产生相同的控制科目变动、相同的未结项种类、
相同的正负号和到期日。上传车道改挂到 Work 车道，连同十三道 gate 的退役，归 **#665**（它本来就被这张票
挡着，票名就是「冗余 gate 退役」）。第 3 条验收因此记 `partial`，第 5 条验收的上传那一半记为**具名残留**。
**另一选项的代价**：这一波就把上传改挂过来，等于同时（a）退役或绕过十三道 gate 而没有回归样本，
（b）在同一波里改动两条已部署冻结工作流的触达面，（c）把 #665 的全部范围吞进来。这张票已经是 XL 了。
**Code names**: `autodraft.mjs:38-46`, `autoDraft.v10.ts:144-175`, `0106:866` rungs B1–B15,
`entry_post_receipts` vs `operation_receipts`, `0197`'s two-lane serialization.

### Q2 — 交易对方认不准的时候，是「当场拒绝并给候选」还是「先建一件 Work 再停下来问」？

**大白话.** 验收第 4 条说「对方不明确时，停在同一件 Work 上，通过共享问题继续」。
**今天**：`claraWork_v4` 的工具清单里**有** `ask_question`，可以带选项停下来问（`claraWork.v4.tools.ts:344`），
所以「停下来问」不需要新切工作流版本——这点和直觉相反，是这一轮量出来的。但 v4 **没有**一个通用的
「把答案写回类型化表」的步骤：它只有一个写死给固定资产用的 `applyParticularsStepV4`
（`claraWork.v4.impl.ts:742-765`）。而且 `answer_work_question` 明确拒绝改动已准入 basis 的回答
（ARCHITECTURE §5 记载的 `basis_change_not_allowed`）。
**我建议**：**在准入那一刻定对方**。门在建 Work 之前就把候选算出来，认不准就用 `party_ambiguous` 拒绝并
把候选名单原样带出来，人在表单里或对话里挑一个再提交。运行中停下来问的 `ask_question`，保留给真正
「跑起来才发现」的事（比如客户科目表里缺一个科目）——那种答案不需要写回任何表，下一段重读科目表就行。
**另一选项的代价**：让对方成为「运行中发现的事实」，就必须切 `claraWork_v5`：新 bundle 摘要、新 registry
pin、新 prompt 段落、一个新的 `applyTradeInvoicePartyStepV5`，外加把 v4 全套测试对 v5 重跑一遍。
那是这一波唯一一次 claraWork 切版的预算，而 #933 已经在排队要它。
**Code names**: `ASK_QUESTION_TOOL`, `0180:578` `open_work_question(p_task, p_hook_token, …)`,
`0200:406` `answer_work_question`, `0216 complete_fixed_asset_particulars_for`, 开放票 #933。

### Q3 — 贷项（credit note）算不算这张票？

**大白话.** 数据库里 `credit_note` 的正负号法律已经写死了（应收方向、负数，`0037:766`），
`coding_kind` 也有 `sales_credit_note`。看起来「顺手做掉」很划算。
**今天**：老车道能记销售贷项；Work 车道两种都不能。验收第 11 条明说「现金采购／供应商贷项是**另一张票
自己的语义**，不许当成一张负数的账单」。#666 就是那张票（票名直译：按正确业务含义记录现金采购与供应商贷项），
#662 管未结项列表里的贷项与抵消。
**我建议**：**不做**。#655 只做销售发票和供应商账单两种，并且对贷项形状的载荷**按名字拒绝**
（`credit_shape_not_admitted`），refusal 文案直接指向那条正确的路。这样第 11 条验收是靠「拒绝」成立的，
不是靠沉默。
**另一选项的代价**：加贷项就要同时处理「贷项冲抵哪一张发票」——那是 #662 的抵消语义，两张票会在
`open_item_allocations` 上撞车。
**Code names**: `ck_open_items_kind_matrix` (`0037:764-771`), `_subledger_classify_entry` (`0037:1001`),
#666, #662。

### Q4 — 「到期日」这一格，谁说了算？

**大白话.** 今天到期日只有一条产线：**过账日 + 交易对方档案里的默认账期天数**（`0040:6008-6024`）。
账单上印着「Due 10 Oct」也进不了库；对方档案没填账期，到期日就是空的。
**今天**：`counterparties.payment_terms_days` 由 `set_counterparty_terms` 人工维护，1–365
（`0040:754-760`）；`open_items` 是只追加表，所以到期日是**出生事实**，事后补不了。
**我建议**：**单据上说的优先，对方账期兜底，两者都没有就诚实记「无到期日」**，并把这个来源
（`stated` / `counterparty_terms` / `absent`）作为一格durable 字段存下来——因为「这个日期是谁说的」
本身就是会计师要判断的事实。同时**不改** `_subledger_on_approve` 的兜底逻辑，老车道原样保留。
**另一选项的代价**：继续只用对方账期，等于把一条印在单据上的事实丢掉，第 1 和第 6 条验收的
「due-date basis」就只能记 `descoped`；而反过来只信单据、不要兜底，会让所有没印到期日的账单一律无到期日，
账龄逾期结构比今天更差。
**Code names**: `0040:6008-6024`, `counterparties.payment_terms_days`, `open_items.due_date`,
`SetCounterpartyTermsDialog.tsx`, `aging.ts:33-34`。

### Q5 — 这一波到底切不切那个过账核心？

**大白话.** 上一波（2026-09-15）的规矩第 3 条明令：谁都不许重切 `_record_journal_entry_core`。
这张票**绕不过去**——发票按定义要打在应收/应付控制科目上，而那个核心在 `0204:550-570` 明文拒绝控制科目。
#638 的员工报销之所以不用切，是因为它刻意走了非控制科目的「其他应付款」（`CONTEXT.md:443`），
这条路发票走不了。
**我建议**：**切，但只开一条窄口子**——仅当这件 Work 在新的 `clara.trade_invoices` 表里有一行时才放行控制
科目，其余一切逐字保留，尾部把十七个 refusal token 重新点名断言一遍。并且请 orchestrator **明确排期**：
如果 #656（期初总账）也要切同一个函数体，两张票必须串行，不能并行。
**另一选项的代价**：另起一个平行过账门（不走 `_record_journal_entry_core`），等于把重放、取消、外发授权、
回执、证据链五套保证各复制一遍到第二个约 600 行的函数里——两份实现迟早会漂移，而它们守的是同一条
「一笔经济事实只能落一次」的底线。这比一次受控重切危险得多。
**Code names**: DECISIONS 2026-09-15 §1.3, `0204:152-761`, `0204:776-782` 的 token 名单,
`0216` 的先例（它明确选择了「不切核心，改用车道无关触发器」，但那是因为固定资产的墙在**触发器**里，
