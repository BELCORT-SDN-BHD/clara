## 大白话

这张票要做的是：**Clara 在动手做账之前，先按「哪个客户、哪个期间、要干什么」去把相关的记录和原始依据
读出来，并且把「我读到的是第几版」记下来；读不到的时候要说出来，不能装作这个客户什么都没有。**

举个具体的：`Kedai Runcit Aman Sdn Bhd`（阿曼杂货）上个月有一张 RM 4,820.00 的维修费账单要入账。
事务所在 `/settings/knowledge` 定了一条全所默认「报告口径 = MPERS」，但阿曼这家客户有一条自己的例外
「MFRS」。Clara 接这笔活的时候，应该先读到「这家客户按 MFRS」，记下「我读的是知识版本 41」，
然后再入账。如果中途有人把那条例外撤回了，这笔活在人回答问题、或者在提交之前，应该看到「你当时依据的那条
记录变了」——而不是照着旧的口径把 4,820 块记进去。

**今天到哪一步了：**

1. **读是读了，但一次把整箱都搬过来。** Work 车道确实在每次开跑前读一次知识（`claraWork_v4`），
   而且「读不到」和「没有记录」已经分得很清楚（`knowledge-conflicts.mjs:100-141`）。但那扇门
   `clara.get_knowledge_pack` 是**把这个客户所有在世记录一次全给**——没有期间过滤，也没有上限；门自己在
   注释里写了「`p_purpose` 只记录、不过滤」（`0192:1452-1454`）。唯一的上限是在 JS 那侧硬切 40 条
   （`knowledge-conflicts.mjs:44`），切掉的那部分只留一句「还有 N 条没显示」。
2. **另一条「固定优先级 + 最近」的预载还活着。** 对话车道读的是另一扇门 `clara.get_context_pack`：
   最近 50 笔分录、最近 25 条审批、按次数排前 200 条编码习惯、wiki 页按「页型优先级 + 更新时间」排名再按
   字节数截断（`0209:139`、`:283-326`）。这正是验收词里说的「要换掉的固定优先级／最近预载」。
3. **对话车道读失败会被吞掉。** `catch { contextPack = null }`（`chatTurn.v10.impl.ts:125-138`），
   而这个 step 是冻结的、从 v10 一直 import 到 v20。所以「读失败」和「这个客户没上下文」在对话里今天仍然
   是同一个值——#603 早就判过这是不行的，知识包那一半修好了，上下文包这一半没有。
4. **版本只记了一个数，而且只有机器看得到。** 每次跑都会把 `knowledge_version` 写进执行轨迹
   （`claraWork.v4.impl.ts:593`），但 (a) 只记了**版本号**，没记**读了哪些 key**，所以「变的那条跟这笔活
   有没有关系」今天算不出来；(b) 网页端把这个字段定义了却从来没渲染过
   （`apps/web/lib/work/diagnostics.ts:54`，全仓再无第二处）。人看不到自己是按哪一版在回答。
5. **「相关的变了就重新规划」今天没有任何机制。** `replans` 这个预算只在模型写错参数时才会加
   （`claraWork.v1.tools.ts:399-413`），跟知识版本无关。回答问题的门只比对 `question_version`，
   完全不看知识版本（`0200:406-470`）——这正是 #885 那张票。
6. **要读的东西读不到，今天只有「科目表」那一条会拦。** `list_accounts` 失败会终止且不入账
   （`claraWork.v1.tools.ts:295-320`）；知识读失败**故意**不拦（`knowledge-conflicts.mjs:93-98`），
   理由是「Work 的权威是人给的依据」。这条要不要改，是本票最硬的一个产品裁定。

**三件最硬的事（复核之后改过的）：**

- **冻结面比看上去大。** `lib/knowledge.mjs`、`lib/knowledge-conflicts.mjs`、`lib/work-trace.mjs`、
  `lib/capability-registry.mjs` **四个都已经冻结且 `deployed:true`**（orchestrator 的 note 说
  `knowledge-conflicts.mjs` 是非冻结的——**这条已被推翻**，见 `frozen-workflows.json` 里它自己的条目）。
  所以 B3 那一半必须发 `claraWork_v5`。
- **新的那扇「装配好的读」不给人开门。** 草稿本来打算把它同时开给人和机器，理由是「这样登记簿和知识包
  就是同一个答案」。**这条被推翻了**：老板 2026-09-15 已经裁过一模一样的事（#783），而且裁的理由正好就是
  反对这个理由——`.out-of-scope/human-read-of-knowledge-pack.md` 写着「人读原始登记簿，知识包是给模型的」。
  所以新门只给 runtime；人这边要的「哪一版、在不在期间内」，用登记簿**今天已经返回的字段**就能显示
  （`0192:1013-1036` 里本来就带 `effective_from`/`effective_to`/`knowledge_version`），一扇门都不用新开。
- **新表不许挂那根外键。** 草稿想让新的「这笔活读了什么」表指向 `accounting_work`。0195 已经**量过**：
  那根外键会拿 `FOR KEY SHARE`，跟入账时的 `FOR UPDATE` 打架，测出来一条轨迹插入被堵了 4001 毫秒然后被
  静悄悄地取消（`0195:254-268`）。照 0195 的做法：写入的门自己用 task→work 的正向 join 去认人，不挂外键。

顺带一提：蓝图里两条写明「binding on `claraWork_v4`」的义务（`ARCHITECTURE:373-386` 的写入侧边界、
`:435-445` 的清单摘要要覆盖每个工具 schema）**在 v4 落地时都没做**，现在压在 v5 头上。
