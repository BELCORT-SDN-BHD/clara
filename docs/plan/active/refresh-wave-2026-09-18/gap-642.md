## 大白话

这张票管的是「跟 Clara 说话这件事本身」：在哪家所、哪个客户底下说；能不能一边说一边附文件；
说出去的那句话有没有真的被受理；她回答的时候你能不能看懂她在干什么；断线之后回来，东西还在不在。

举个具体的：会计师在「南方五金 Sdn Bhd」的工作台打开右边的 Clara 栏，附上一张 RM 4,280.00 的
维修发票，写「这张记到维修费」，按送出。今天会发生什么：

- **附件那一半已经做得很扎实**：每个文件自己有「排队 / 上传中 / 校验中 / 归档中 / 就绪 / 失败」六七种状态，
  失败的那一个不会把整个输入框锁死（`ComposerAttachmentControl.tsx:64`、`useUploadQueue.ts:55`），
  没有附件也能直接说一句话就发（`ClaraThreadView.tsx:254`）。这条 AC 基本是**验证**，不是重建。
- **但屏幕上没有一个地方写着"南方五金"**。右边那一栏的标题就四个字「Clara」（`ClaraRail.tsx:113`），
  放大成全屏之后连事务所侧边栏都没有，页面唯一的 `<h1>` 还是「Clara」（`ClaraFullScreenThread.tsx:53`）。
  客户身份只在 URL 里。AC1 第一句「scope 必须挨着输入框」今天**完全没有**。
- **按两次送出会开出两件工作**。数据库其实早就防住了：`begin_chat_turn` 拿 `turn_key` 查回放，
  查到就把原来那件还给你（`0006:954-960`）。可是网页每按一次送出就现场生成一把**新钥匙**
  （`useClaraThread.ts:405` 的 `crypto.randomUUID()`），所以那条回放路径从网页端**根本走不到**。
  唯一挡住重复的是「一个会话同时只能有一轮」那把锁（`0006:165`）——上一轮已经结束了就挡不住了。
- **长对话读到一半，新内容一来就把你推走**。滚动区就是一个 `overflow-y-auto`
  （`ClaraThreadView.tsx:297`），全仓库找不到任何 `scrollTop` / `scrollIntoView` / 「跳到最新」按钮。
  AC5 的「保住阅读位置 + 有名字的跳到最新」今天**一行都没有**。
- **她在干什么，你只看得到一个灰色小方块**，上面印着 `start_accrual_work` 这种程序员词，
  后面跟着「完成 / 失败 / 无结果」三选一（`PartRenderer.tsx:201-214`、`toolStatus.ts:39`），
  而且要等整轮结束、落库之后才看得到。

**这次查出来最要紧的一件事**（两次评审都还没看过）：工具的实时状态**不需要动冻结的 workflow**。
模型的整条 `fullStream` 已经**原封不动**推到浏览器了（`chatTurn.v10.impl.ts:216-221` 逐个 `write`，
`streamRoute.ts:139` 原样转成 `event: chunk`），只是网页只挑了 `clarify` 一种来折
（`liveClarify.ts:57-58`）。也就是说 AC4 是一个**纯前端的折叠**，不是一次 `chatTurn_v21` 切版。

**要请老板拍板的是一件事**：AC2 点名要用 shadcn 的 Message / Message Scroller / Bubble /
Attachment / Marker / Avatar 这一套原生组件。这六个今天**一个都没装**（`apps/web/components/ui/` 只有
30 个），而且装它们要多拉一个 npm 包 `@shadcn/react`（现在不在依赖里），还要把这个产品里
**最敏感的一块无障碍区域**（一个 `role="log"` 加五条互斥的 `role="status"`）整个重写一遍。
装，这票就是 XL；不装、只自己写滚动锚定，是 L。

**Q2 — 「同一条指令」的身份怎么算、活多久？** *(changes what is built)*
**大白话.** 按两次送出只能开一件工作。数据库那道门早就会认「同一把钥匙 = 同一件事」
（`0006:954-960`），缺的是网页端每次都换新钥匙（`useClaraThread.ts:405`）。
**这里有一个坑，是评审替我们踩出来的**：那道门认出「同一把钥匙」之后，是**立刻把原来那件还给你就走**
（`0006:957-960` 的 `return` 在写消息那一步 `:995-996` **之前**），它**根本不看你这次带了什么附件**。
所以如果会计师第一次送出带的是发票 A、没收到回音，然后**把 A 换成改好的发票 B** 再按一次——
用同一把钥匙的话，B 会被**一声不响地丢掉**，屏幕上还写着「这轮已经受理了」。这不是界面难看，是账做错。
**我建议**：钥匙**由内容算出来**——`(会话 + 层级 + 这句话 + 排好序的附件 id)` 哈希一把，而不是随手发一个 uuid。
这样「同一句话、同一批文件，再按一次」自动是同一把钥匙（该回放就回放），
「换了文件或改了字」自动是**新的一把**（该开新的就开新的）——这正是 appendix C §3 那一行自己写的两半：
*重试用同一个身份，新意图给新身份*（`appendix-C-journeys.md:77`）。
至于**要不要熬过刷新页面**：**不用专门熬**——算出来的钥匙根本不需要存，同样的话配同样的文件，刷新之后重打一遍
还是同一把；刷新之后真正的保护仍然是「重新读一次这轮在干什么」，那个今天已经有了
（`thread-rehydrate.test.tsx` 六格）。这跟 appendix C §3 自己的规矩一致：*不要承诺内存状态能扛过刷新*。
**另一选项的代价**：要熬过刷新就得落库 —— 那意味着一条迁移、一次 `begin_chat_turn` 重切，而那把函数
被 `0105` 用 prosrc sha 钉死，还带一道「运行时心跳新鲜就拒绝应用」的静默门（`0105:141`），
本波要专门安排停机窗口。为一个契约上本就不承诺的场景，不值。
**代码名**：`claraThreadStore.getDraft/setDraft/clearDraft`（`threadStore.ts`）、`postTurn` 的 `turnKey`、
`chatRoutes.ts:241`/`:298` 的 202 body、`uq_agent_task_one_live_turn`（`0006:165`）。
