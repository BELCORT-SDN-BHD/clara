## Backend reconciliation

### Useful facts retained after verification

1. **Chat is an orchestrator, not a Workflow launcher for accounting jobs.** The chat turn is itself a durable Workflow run, but its accounting tools call governed `clara.wake_*` database doors directly. The upload, interview, onboarding, and world-start surfaces start their own Workflow runs; the traced chat tools do not start AutoDraft, BankAgent, or close-prep runs. This sharpens the prior report's distinction between a conversational control surface and background agents (`packages/runtime/src/chatRoutes.ts:213-258`; `packages/runtime/plugins/startWorld.ts:180-286`; `packages/runtime/workflows/chatTurn.v14.bankActs.ts:29-138`).

2. **Upload-driven invoice posting is already a live runtime path.** AutoDraft v10 drafts one entry, remembers its id, and can attempt one post in the same run (`packages/runtime/workflows/autoDraft.v10.toolset.ts:116-170`). The manual `request_autodraft` door is a replay/fallback rather than the only trigger. Statements follow statement-fact and bank-line ingestion and are intentionally outside this invoice AutoDraft consumer.

3. **The current unattended-post authority is the 0106/0107 ladder, not a signed vendor rule.** AutoDraft mints a client-pinned `autodraft` credential with no human on-behalf-of identity (`packages/runtime/workflows/autoDraft.v9.infra.ts:55-78`). `wake_post_entry` validates that credential, its client pin, idempotency key, rationale, model snapshot, and books token (`packages/db/migrations/0107_f_a2_posting_grants.sql:175-253`). `_agent_post_entry_core` then requires the agent's own untouched draft and admits a post only when all thirteen rostered rungs are `pass` (`packages/db/migrations/0106_f_a2_posting_core.sql:819-887,937-965,1268-1329`). The runtime registry calls this ladder the sole authority (`packages/runtime/workflows/registry.ts:539-555`).

4. **The old rule machinery is historical, not the live posting gate.** Migration 0106 removes the approval-time `rule_sightings`/`coding_rules` breeding writes and the draft-time live `coding_rules` read plus `rule_decisions` write, while retaining their tables and rows (`packages/db/migrations/0106_f_a2_posting_core.sql:1531-1572,1625-1649`). The prior backend report correctly warns that searches still find retired `autopost_rule`/`execute_rule_post`; the first version of our backend evidence report failed to carry that distinction into fact 5 and has now been corrected.

5. **Human high-stakes checker rules remain, but the current agent post bypasses that branch after passing a different wall.** The ninth `_approve_entry_core` body preserves the human CLR05 distinct-checker/self-attestation arms and changes the condition to `is_high_stakes(...) and not is_agent` (`packages/db/migrations/0106_f_a2_posting_core.sql:1381-1408,1496-1505`). `_agent_post_entry_core` calls it with `is_agent: true` and writes an `agent_unattended` receipt (`packages/db/migrations/0106_f_a2_posting_core.sql:1304-1328`). It is therefore inaccurate to describe current unattended posts as passing the old 0037 maker/checker wall; they pass the client/ownership/books checks and the thirteen-rung ladder instead.

6. **The prior “only one true retry-with-feedback loop” statement is too absolute.** Evidence-index and snapshot failures do have explicit in-run retry classification (`packages/runtime/workflows/autoDraft.v10.errors.ts:237-307`). AutoDraft also has an eight-step model/tool budget that permits bounded pre-post correction (`packages/runtime/workflows/autoDraft.v10.impl.ts:176-209`). A post-tool result, including a refusal, stops the loop; the tool can be called only once and the prompt forbids redrafting after refusal (`packages/runtime/workflows/autoDraft.v10.impl.ts:391-410`; `packages/runtime/workflows/autoDraft.v10.toolset.ts:135-170`). The defensible statement is: there is bounded correction before posting and specific retry handling for evidence-read failures, but no generic post-refusal or posted-error repair loop.

7. **Current error correction does not implement the owner's accepted full-auto repair policy.** A refused AutoDraft post stays a draft or becomes a question/failure depending on the typed result (`packages/runtime/workflows/autoDraft.v10.ts:144-183`). Human reversal exists (`apps/web/lib/journals/api.ts:342-380`), and recurring-adjustment `auto_reverse` is a planned accounting reversal, not a general error detector. The searched production runtime has no tool chain that detects a wrong approved post, reverses it, posts the corrected entry, and notifies the user. Owner decision Q11 therefore adds a product requirement: for full-auto clients and open-period errors, auto-reverse/correct within the original scope and notify.

8. **Classification can race extraction readiness.** `_enqueue_invoice_facts_core` may create a classify task as soon as the filing kind is null (`packages/db/migrations/0123_f_a7_gamma_egress.sql:1086-1128`). The classifier reads the newest completed OCR/parse row; if none exists it constructs an empty string and still calls classification (`packages/runtime/lib/classify.mjs:101-127,154-160`). This is a useful prior finding and should become an explicit ingest ordering/idempotency acceptance test.

9. **Invoice regime selection needs to be distinguished from full evidence admission.** AutoDraft's friendly reader selects the latest legacy or text-witness generation by `extracted_at`; its source says vision rows carry no regions (`packages/runtime/workflows/autoDraft.v10.tools.ts:143-199`). That reader alone does not compare text and vision outputs, and explicitly names the DB as authoritative. The statement lane separately models `readers_disagree` (`packages/db/migrations/0098_f_a1_statements.sql:849-855`). These observations do not by themselves prove that the complete invoice persistence/evaluation/posting path lacks agreement checks. The prior allegation remains a verification question until that entire boundary is traced; do not open a confirmed-defect ticket from this reader alone.

10. **Trial-balance movement is journal-led, while material accounting state also lives in typed ledgers.** Approved journal entries are the GL movement authority, but open-item allocations, bank matches/reconciliations, assets, recurring templates/runs, and close records carry accounting meaning not reducible to a journal header. In particular, applying open items changes outstanding balances without a new GL movement (`packages/db/migrations/0037_wave_c_a_subledger.sql:783-823,3212-3225`). The prior report's broad wording that every money-state change is a journal entry should be narrowed to trial-balance movement.

## Client knowledge-base reconciliation

### Useful facts retained after verification

1. **Knowledge has two durable models.** `client_facts` is an append-only, supersede-never-update typed fact register with actor, basis, time, and provenance (`packages/db/migrations/0055_client_facts_trio.sql:346-424,610-669`). Wiki pages are immutable projected versions consumed through the context pack. This distinction is central to Q10: direct user declarations fit the fact model better than silent promotion of model inference.

2. **The client-fact catalog has five current keys, not exactly two.** The first migration adds `entity_type` and `msic` (`packages/db/migrations/0055_client_facts_trio.sql:370-381`); later migrations add `trade_nature`, `customer_identity_policy`, and `banking_arrangement` (`packages/db/migrations/0056_prior_gl_seeding.sql:1233-1239`; `packages/db/migrations/0062_party_identity.sql:170-184`; `packages/db/migrations/0121_f_a3_pr1b_agent_limb.sql:4820-4831`). The current context-pack splice surfaces only entity type and MSIC from that catalog (`packages/db/migrations/0055_client_facts_trio.sql:735-789`). The Client KB follow-up corrected this note's earlier literal key `msic_code` to `msic`; the industry-code concept is unchanged.

3. **The fact write door exists but is not wired into the searched production callers.** `record_client_fact` is an admin-level human door (`packages/db/migrations/0055_client_facts_trio.sql:499-510`). A scoped direct search of `apps/web` and `packages/runtime` found no caller. This is a bounded source finding; it does not establish hosted out-of-repository integrations.

4. **Chat receives a fixed, bounded wiki prefix rather than query-conditioned retrieval.** `get_context_pack(client, 'wiki_coding')` selects active pages by fixed page-kind priority and recency and inlines content up to configured page/byte limits (`packages/db/migrations/0017_wave_b.sql:5010-5070`). Chat loads the pack once for a client turn, silently falls back to null on failure, and serializes it into system context (`packages/runtime/workflows/chatTurn.v10.impl.ts:108-140`; `packages/runtime/workflows/chatTurn.v17.ts:90-96`). A scoped production search found no list/fetch-wiki model tool; the runtime wiki read found is internal to projection.

5. **Storage is asymmetric across the three publish lanes.** The model counterparty lane calls `putAndVerifyContent` before publishing (`packages/runtime/lib/wiki-projection.mjs:465-525`). Deterministic source ingest calls the database publisher directly, and deterministic seeding explicitly keeps content in the database without Storage egress (`packages/runtime/lib/wiki-projection.mjs:443-450,553-598`). The prior KB report got this right; `docs/ARCHITECTURE.md:210-213` and the first version of our backend evidence report described the Storage model too uniformly.

6. **The cross-reference graph has no current production population path in the searched scope, but orphan impact is lane-specific.** All three current publishers pass empty refs. Source pages are excluded from orphan lint by the later migration, while counterparty and seeding pages remain vulnerable to permanent orphan findings. The KB report's opening “every page” claim is stale; its own corrected appendix records the source-page exemption (`packages/db/migrations/0017_wave_b.sql:2134-2169,2265-2270`; `packages/runtime/lib/wiki-projection.mjs:523-525,593-596`; `packages/db/migrations/0020_typed_consent.sql:1527-1595`).

7. **Contradiction and stale-claim lint depend on citation metadata no current writer emits.** The lint expects `detail.subject_key`; a scoped production search found that token only in the lint implementation (`packages/db/migrations/0017_wave_b.sql:4730-4785`). Current counterparty citations contain `trigger`, while deterministic lanes use their own provenance shapes. The prior report's functional gap is supported, subject to the bounded search coverage.

8. **The deterministic source page is currently a stub, using an opaque ID.** The later 0020 recut changes title/body to fixed text plus the document UUID and refuses fresh non-null caller notes (`packages/db/migrations/0020_typed_consent.sql:1658-1686,1692-1710`). The earlier `Source document: <filename>` description came from the superseded 0017 body. The source page still has no document substance and consumes context budget, but adding extracted prose must use a properly governed synthesis/publication path rather than weakening the deterministic exempt lane's content restriction.

9. **The wiki instruction layer is thin.** The only model-generated page kind in the traced maintainer is a counterparty page, and its synthesis prompt is a short inline instruction (`packages/runtime/lib/wiki-projection.mjs:349-365,465-525`). The prior proposal to make this the first agent-platform replatform workload remains unratified; the evidence about current behavior is useful independently.

10. **`inform_never_decide` is policy metadata, not proof that wiki text cannot affect outcomes.** The context pack carries that label (`packages/db/migrations/0017_wave_b.sql:5067-5069`), and migration/test ratchets forbid named deterministic authority functions from directly reading wiki/pack tokens. The checks are lexical over a maintained roster. Wiki content is intentionally allowed to inform the model judgement that proposes accounting. The prior appendix corrected its own stronger structural-guarantee language.

11. **Derived coding experience already exists alongside the two durable knowledge models.** `approved_coding_patterns` is recomputed on each pack read from current approved, unreversed entries, folded through canonical counterparty identity and capped at 200 rows (`packages/db/migrations/0109_f_a2_pack_splice.sql:257-296`). It remains advisory and is not an accumulated wiki corpus. Q23's broader traceable experience should reuse this useful current signal without promoting successful posting or repeated patterns into confirmed policy.

### Product implications under Q10

- Explicit user statements need a durable fact-capture command with an undo/supersession action and visible provenance. The present fact model supplies history and supersession, but the searched runtime/web paths do not provide this conversational autosave loop.
- Model inferences need a distinct unverified state and a confirmation path before they become accepted client knowledge. Existing wiki synthesis metadata distinguishes deterministic/model generation, but that does not itself represent user verification.
- Conversation reset should preserve confirmed client facts and active wiki versions because both are stored outside chat-session history. The product must make context-pack failure visible enough that a turn does not silently act as though confirmed knowledge is absent.
- Recommendations in the prior report to merge all knowledge into prose pages, require a tick for explicit user declarations, or choose the wiki maintainer as the first replatform target remain design proposals, not accepted scope.

## Workflow and UX reconciliation

### Workflow facts independently checked by the root investigation

- In published `@ai-sdk/workflow@2.0.24`, `needsApproval` writes and closes an approval-request stream and returns; it does not itself await a Workflow hook (`C:\Users\zhant\AppData\Local\Temp\clara-workflow-factcheck-20260908\package\src\workflow-agent.ts:2571-2594`). Resumable streaming does not inherently require Redis because Workflow stream/database alternatives exist.
