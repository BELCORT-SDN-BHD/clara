## 4 · Item 1 — the service-period carrier

### 4.1 The shape, and why it is a table rather than two columns

Two bare date columns on `clara.documents` would be the smaller diff and the wrong answer.
Those rows are UPDATEd by several unattended writers (0026:916, 0009:2104, `persist_witness_facts`
in 0096) with no immutability discipline; a date pair with no basis, no recorded actor and no
supersession story is exactly *"a fact the storage layer asserts on and a professional can
rewrite"* — the sentence 0045:1206-1210 minted for the lineage column. A prepayment term feeds a
number that enters a client's books; it needs the `client_facts` discipline, at document grain.

**`clara.document_service_periods`** — new table, mirroring `clara.client_facts`
(0055:386-424) where the shapes agree:

| column | notes |
|---|---|
| `id`, `firm_id` | `firm_id` FK to `clara.firms` |
| `document_id` | composite FK `(document_id, firm_id)` → `uq_documents_id_firm` (0007:58) — tenancy is structural, the `fk_client_facts_client` idiom (0055:417) |
| `period_start date not null`, `period_end date not null` | `check (period_end >= period_start)` |
| `basis_kind text not null` | **CLOSED, extend-never-rewrite:** `('human_stated', 'extracted')` |
| `basis text not null check (btrim(basis) <> '')` | the justification: not optional, not defaulted (0055:394-396's rule) |
| `evidence_region_id uuid` | composite FK → `clara.document_regions(id, firm_id)` (0007:217). Paired CHECK `(basis_kind = 'extracted') = (evidence_region_id is not null)` — the two-way `ck_client_facts_document_basis` shape (0055:411-414) — **plus §4.1a's congruence trigger (F6)** |
| `recorded_by uuid not null references clara.users(id)`, `recorded_at` | |
| `superseded_by uuid ... deferrable initially deferred`, `superseded_at` | the paired-stamp CHECK (0055:407-408) |

Plus: a partial unique index on `(document_id) where superseded_at is null` — **one live period
per document** · FORCE RLS · an owner policy · a human read policy at
`firm_id = clara.jwt_firm() and clara.actor_role_rank() >= clara.role_rank('bookkeeper')` (the
FIX-6 shape, 0138:424-427 — this table carries a professional's stated basis) · a
supersede-only trigger mirroring `clara._tf_client_facts_supersede_only` (0055:430ff) ·
append-only on DELETE and TRUNCATE.

**`basis_kind = 'extracted'` ships with no writer, deliberately** — the 0138:342-345 idiom
quoted exactly: *"a declared SHAPE, not a live claim — a later PR that unparks the verb extends
nothing."* Annex C is its named writer, and a table comment says so.

#### 4.1a The region-congruence trigger (review finding F6)

**The composite FK proves the firm, and nothing else** — `clara.document_regions` hangs off
`extraction_id`, not off a document (0007:203-221), so a period on document A could cite a region
extracted from document B and every declared constraint would pass. The wall is a BEFORE
INSERT/UPDATE trigger resolving the region to its extraction and asserting that extraction's
`document_id` equals **this row's own**, typed
`service_period_evidence_foreign_document`, firing only when `evidence_region_id` is non-null so
the `human_stated` path is untouched. Derivation and cell W33: **Annex B.0d**.

### 4.2 The door

## 5 · Item 2 — `clara.prepayment_schedule_v1`

Signature and semantics are Annex B.2's
(`docs/plan/active/close-key-1-annexes-1-mechanics.md`:400-432), unchanged:
`clara.prepayment_schedule_v1(p_client uuid, p_source_entry uuid) returns jsonb`, STABLE,
SECURITY DEFINER, `search_path` pinned, **ungranted** (reached only from the agent core; no
consumer exists for a human grant, and law 31 says do not mint one).

**Inputs, all DB-owned and all read inside the body:** the source entry's prepaid-asset leg
(cents + account code from `clara.journal_lines` / `clara.coa_accounts`, entry required
`status='approved'`) · the bound document (`clara.journal_entries.document_id`, 0003:109 —
`ck_je_basis` at 0003:127 permits a memo-only entry, so **absence of a document is a first-class
refusal**, not an error) · the live `document_service_periods` row · the client's FY bounds.

**Output:** `{schedule_version:'v1', period_lines:[{period_start, period_end, debit_cents,
credit_cents, account_code}], total_cents, remainder_placement:'final_period'}`.

**Arithmetic, restated so a reviewer re-derives it:** straight line over whole months, no
day-level pro-rating (law 20's split-month doctrine — a day-1 start gives the month to the
successor, day-2+ leaves it with the predecessor); `base = total_cents / n` truncated toward
zero; the remainder lands **wholly in the final period**, so `sum(period_lines) = total_cents`
exactly.

**Typed refusals**, returned as a jsonb object and never raised (the caller turns them into
rungs): `prepayment_term_underivable` — no live service period, no bound document, or a term
running past the FY the entry sits in with no OPENED successor year (OQ-4's ruled answer, never a
default) · `prepayment_source_unfit` — the entry is not approved, not this client's, or its
prepaid leg is ambiguous (zero or more than one candidate asset leg). **The FY arm is a
self-healable state**, not a dead end: under R6/HIGH-1 the clocked lane may open the successor
year itself through `wake_open_fiscal_year`, so cell **W31** drives the two-phase integration
(refuse → the agent opens the year → the same draft succeeds) rather than assuming it (§13 item 4).

### 5.0 The two owner rulings this section is built on (Tao, 2026-08-27, in-session)

**F1 — OPTION A: extend the CARRIER**, chosen for the one-signature experience: the human signs
once and the whole schedule is what they signed. **The convention ruled with it: whole-CALENDAR-
month straight-line** — the schedule starts at the service-start month, `n` is the term's months,
equal amounts with the remainder in the FINAL period, and **no day-count pro-rata in v1.**
*Extension path, recorded because it is already foreseen:* pro-rata becomes a **second ruled
policy, per-client-selectable and still deterministic** — and §5.2's shape is chosen so that it
lands as an evaluator `_v2` and nothing else.

**F2 — Clara JUDGES the expense account.** The owner overruled the human-keys recommendation, and
correctly: picking which expense account an amortisation charges is the **agent-codes /
human-approves** pattern the estate already runs in `autoDraft` coding, not OQ-4's fact class.
**The governing maxim, recorded here because it is the line every future lane will have to
find: *facts get anchored, judgements get receipted.*** A service period is a **fact** read off a
document — it gets anchored (§4's carrier, human-keyed today, OCR-anchored later). An expense
classification is a **judgement** — it gets receipted, shown, and signed. The two never swap
lanes, and that is why §4 and §5.3 look different.

### 5.1 The freeze, and the closure kept at ONE member

Registering a closure in `clara.evaluator_versions` freezes **every member body estate-wide**:
`verify_evaluator_freeze()` ignores the `deployed` flag and hashes the full
`pg_get_functiondef`, so an N-member registration is N bodies a later lane can never recut
without reding an apply (F-T3's D-16, re-measured at that item's PR-0 as P-10).

**Therefore the evaluator calls no other `clara` function** — it reads tables and does its own
arithmetic inline (no `_adj_period_start`/`_adj_period_end`, no `_hash`). The registration is
then a genuine single-member closure and the freeze means what it says: this body, this version,
this receipt. A changed formula is `_v2`, never an edit (law 9 applied to evaluators). The census
cell is a prosrc scan for `clara.` call sites with **its ceiling stated in the cell** (a prosrc
regex is a spelling instrument, not an identity one — law 3), paired with the structural fact
that the registration carries exactly one `evaluator_version_members` row.

### 5.2 F1's carrier surgery — per-occurrence schedule lines, in a SIBLING column

**The defect the ruling closes.** `clara.adjustment_templates.lines` is ONE line array, and
`_adj_run_occurrence_core` materialises it verbatim for **every** period (0045:5181-5191). A
schedule whose final period carries the rounding remainder cannot be expressed: either every
period posts the base and the remainder is never charged, or every period posts `total_cents` and
the books take `n × total`. Both post wrong numbers, which is why this was an owner question.

**The shape I chose: per-occurrence schedule lines, NOT a final-occurrence override.** The ruled
convention needs only two distinct amounts (base for periods 1..n-1, base+remainder for period n),
so an override is *sufficient for v1* and is the smaller diff. It is still the wrong choice, for
the one reason that decides it: **pro-rata is already ruled as the next policy**, and under
day-count pro-rata every period can differ. An override would then be torn out and replaced — a
**second** surgery on the same live posting bodies and a **second** D1 window, paid later at a
worse time. Per-occurrence lines subsume both conventions: straight-line is a schedule whose
entries happen to be equal-but-one, pro-rata is a schedule whose entries are not. Choosing it now
makes the ruled extension path **an evaluator `_v2` and nothing else** — no carrier change, no
CoR, no window.

**It lives in a SIBLING column, not inside `lines`.** `clara.adjustment_templates.schedule jsonb`
— `[{period_start, period_end, lines:[…]}]`, one entry per occurrence. `lines` keeps its exact
present meaning and `clara._adj_canon_lines` (0045:1930-1939) is **not touched**, which matters
because `lines` is read well outside this train: `_wdb_line_shape` (0045:4629),
`_adj_line_eligibility_breach` (0045:5109), the overlap advisory. Widening the meaning of a
structure many bodies read is how a narrow change becomes an estate-wide one.

**One new resolver carries the whole behaviour change.**
`clara._adj_period_lines(p_template_row, p_period_start, p_period_end) returns jsonb` — returns
`_adj_canon_lines(t.lines)` when `t.schedule is null`, and the matching entry's canonical lines
when it is not. **Null-stability is what makes this safe on a live estate:** every template that
exists today has `schedule is null` and therefore posts byte-identically after the migration.
Asserted, not assumed — cell **W36**.

**`content_hash` covers the schedule, null-stably.** `_adj_template_hash` gains a trailing
`p_schedule jsonb default null` and folds a canonicalised schedule into its object **only when
non-null**, so an existing template's hash recomputes to the bytes it was stored with and the
duplicate guard keeps working across the change (cell **W37**). It has exactly ONE caller,
`propose_adjustment_template` at 0045:3850, which is what keeps this cheap.
`propose_adjustment_template` itself takes `p_schedule jsonb default null` **last**, per
0045:6707-6711's own house rule, so no existing caller moves.

**The widened CoR set and the re-derived D1 inventory — still ONE window:**

| body | why it moves | live today? |
|---|---|---|
| `clara.propose_adjustment_template` | the extraction (§6.1) **plus** the trailing argument and the hash call | **yes, hot** |
| `clara._adj_template_hash` | the schedule joins the signed content, null-stably | yes (one caller) |
| `clara._adj_run_occurrence_core` (0045:4440) | materialises `_adj_period_lines(...)` instead of `t.lines` at 0045:5186 | **yes — the daily unattended belt** |
| `clara._adj_on_approve` (0045:5626) | axis (2d)'s byte-equality assert resolves the ENTRY'S OWN period rather than the flat template lines (0045:5733-5744) | **yes — every approve of an occurrence** |
| `clara._adj_period_lines` · `clara._adj_canon_schedule` | new, additive | — |

**This is a materially bigger window than PR-2a's first cut, and the design says so rather than
letting the ceremony discover it.** Two of the four are on the unattended daily posting path.
What bounds the risk is that all four are **null-stable by construction**: with `schedule is null`
— every row in the estate on the day this applies — each body's observable behaviour is
byte-identical to today's, and the battery proves it before the ceremony rather than after.

### 5.3 F2's three walls — the account is a judgement, and it is receipted

**The wrapper takes the target account as an explicit model judgement.**
`wake_establish_prepayment_schedule` gains `p_target_account text` and `p_target_basis text` — the
judgement and its stated grounds. Three walls, all load-bearing:

1. **Deterministic validation.** The account must exist on this client's COA, be expense-class /
   P&L, and pass `clara._adj_line_eligibility_breach` — the same helper the propose door and the
   poster already use, so a bank-class or otherwise ineligible account refuses by the estate's own
   existing rule rather than a new one. Typed: `prepayment_target_ineligible`.
2. **Receipted.** The account and its basis ride the `agent_act_receipts` row's rationale and the
   acted result payload, through the law-79 machinery that already carries model name, version and
   rationale. A judgement with no recorded basis is what TA-P4 exists to prevent.
3. **Visible and CHANGEABLE at the admin sign door.** The human signs what they see; if the
   account is wrong they change it and sign that. `content_hash` freezes at signature (0045:1151),
   so what was signed is what posts — and after §5.2 the frozen content includes the schedule.

**When Clara cannot pick with confidence she refuses `prepayment_target_underivable`, naming the
gap** — the **no-plausible-account arm, not the default path.** A lane that refuses whenever it is
unsure of a classification would never charge anything, which is over-caution wearing a safety
property's clothes.

**The amounts stay purely DB-derived.** `clara.prepayment_schedule_v1`'s signature does not change
and its output stays amounts-only: the account rides the proposal as **classification**, applied by
the agent core when it assembles `lines`, and never enters the evaluator as an arithmetic input.
That is what keeps §5.1's single-member frozen closure intact and hard constraint 2 satisfied — no
model-generated numeral reaches a durable artifact; a model-generated *classification* does,
receipted, shown and signed.

Pre-rung (c) reads `_adj_line_eligibility_breach` *without* the `client:fa-roles` leaf the

**Pre-rung (a) — DE-PARAMETERIZED, and the P-align/P-carry fork DISSOLVES.** F1's ruling settles

calendar-month** (0045:1881-1884, and 0045:1878-1880 says so in prose). So the template's
`start_date` is the first day of the service-start month, which **IS** a period start by
construction: the two candidate predicates were only ever different answers to a question the

**The rung stays, reclassified.** It can no longer fire on ordinary caller input — it can only

### 6.3 The receipt subject, the op key, and one recut NOT taken

Full derivation in **Annex E**; the three decisions it reaches:

1. **`agent_act_receipts.subject_kind` gains `'adjustment_template'`** — `act_kind` already
   admits `'prepayment_schedule'` (0138:346-348) but `subject_kind` admits no template
   (0138:349-350). Drop constraint, add with the existing six plus one. Extend, never rewrite.
2. **The receipt's subject differs by verdict** — refused → `('journal_entry', p_source_entry)`,
   acted → `('adjustment_template', v_template_id)`. This is not cosmetic: the derived op key is
   per **(task, verb, client)** (0138:1266-1270, :1311-1314), so two source entries in one wake
   task share an op key, and a client-subject refusal on entry B would wear entry A's receipt —
   **FIX-1's exact defect, re-opened by multiplicity.** Differing subjects across verdicts is
   the shipped idiom (fix order §Native F1's *"safe by differing subject"*).
3. **The delegate gets a sub-key**, `p_op_key || ':' || p_source_entry::text`, the depreciation
   catch-up's own idiom (0138:2399 against :2379-2381) — and
   **`clara._close_subject_client` is NOT recut** to add a `journal_entry` arm, because that
   buys a discrimination the receipt subject already provides at the price of a second body in
   the D1 inventory.

**The collision is NARROWER than a loose reading suggests, and that is why it survived review.**
`rung_digest` is in `uq_aar` (0138:396), so two refusals collide only when their **rung vectors
are byte-identical**, not merely when both refused. That is not a corner: the common case
produces exactly that — two prepaid entries on one client, neither carrying a service period,
both refusing with the same single-element `B10` vector. A narrow window that the ordinary path
walks straight into is the worst kind.

### 6.3a Item 10 — the SAME collision is LIVE in `_agent_mint_month_snapshot_core` (F4)

**Conductor decision, 2026-08-27: fixed in PR-2a.** The derivation above is not specific to
wrapper 13. `clara._agent_mint_month_snapshot_core` (0138:2437-2465) takes `p_month_start` — the
act is **month-grain** — but pins its REFUSED receipt to `('mint_snapshot', 'client', p_client)`
(0138:2446-2448) while `_close_wake_ctx` derives the op key per (task, verb, **client**). Two
different months minted in one wake task, both refusing on the same vector (a live hold, say),
therefore collide on `uq_aar`, and the second month's refusal is answered with the first month's
receipt id. Same defect class as FIX-1, shipped and undetected.

**The fix, and why the shape differs from wrapper 13's.** `subject_id` is `uuid not null`, and a
month start is a date — there is no uuid to name, so the subject cannot carry the grain. The
discriminator is therefore the **op_key column**: both receipt calls in that core take
`p_op_key || ':' || p_month_start::text`, the same sub-key idiom the depreciation catch-up
already uses for its delegate (0138:2399). The acted path is already safe by subject (the minted
`snapshot_id`), but it takes the month-scoped key too — a receipt row for this verb should say
which month it was about whichever way it went. Cell: **W32**, two months in one task.

**Window economics.** `_agent_mint_month_snapshot_core` is the same class of body as §H's — created
by 0138, undeployed, reachable only behind the `close_prep` `wake_engine_sources` row at
`enabled = false`. It rides §H's declared-but-idle slot at no additional ceremony cost, which is
what makes fixing it here cheaper than carrying it. Full derivation: **Annex G**.
