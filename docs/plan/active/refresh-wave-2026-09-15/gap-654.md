# Gap map — #654 明确推广事务所默认规则并保留客户例外

_Final map, reconciled against two adversarial reviews (citation lens, design/safety lens). Read-only census: nothing was executed. Every path:line below was opened directly in this pass._

## 大白话

这张票要的是「把一条客户的做法，明确升成整个事务所的默认规则」这件事。规矩是三条：必须有人**明确说**「这适用于全所」并且**他有权限**；已经存在的**客户例外不能被覆盖**；一个客户的**私有凭证不能跟着规则跑到别的客户**那里。

**今天的底子比原稿以为的还厚。** `0192` 迁移已经把数据库这一半做完了：firm/client 两种 scope、client 是默认、firm 必须 admin+ 明确指定（`0192:1114`、`996-1008`）；读的时候客户行**只在同一 key 且同一适用条件下**才遮蔽事务所行（`0192:1348-1363`、`1509-1518`）——所以「保留客户例外」在数据库层已经是对的，而且是精确的。

**差的是什么？** 蓝图自己写得很清楚。`docs/PRD.md:122`：「晋升路径的服务器侧门与客户例外保留规则**都已就绪**，目前缺的是**界面或对话入口**」。也就是说 #654 剩下的是**入口**，不是新引擎。今天 firm-scope 的门一个调用者都没有（`0192:114-116` 自己记为 deferral (3)），而且——这是原稿漏掉的——连 client-scope 的人工登记门 `clara.capture_knowledge` 在整个 web 里也**零调用者**，所以这个对话框没有任何现成 UI 可以改，是从零起。

**两件必须自己修的事：** 一是界面上看不到「事务所规则 vs 本客户例外」的对照（被遮蔽的事务所行 SQL 层直接不返回）；二是跨客户凭证没有墙——`_knowledge_source_pins` 只校验 firm 不校验 client（`0192:782-784`），一条 firm 规则可以引用某个客户的文件，然后那条 basis 和来源钉进**其他每个客户的模型知识包**。注意：这不是「泄露」——`clara.documents` 的人类 RLS 本来就是全所可读（`0003:514`）——是**引用污染**，而模型包那一半才是真正要堵的。

**不该在这张票做的：** 「只重评受影响工作」的引擎。`PRD:123` 明确把它推给 #658/#663，`0192:106-112` 说这个消费者需要 #631 的 trace 和 #658/#663 的模型才能决定「哪些工作受影响」，而且「叫醒全部比不做更糟」。#658/#663 都不在这十二张票里。
