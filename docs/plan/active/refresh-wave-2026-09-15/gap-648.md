## 大白话

**这张票要做什么。** 事务所付钱认领之后，给负责人一张「还缺什么就问什么」的设置清单——答过的不再重问，刷新或别人同时在改也能接着答；确认的事实进同一份可查、可更正、带来源和作者的正式记录；页面上看得见完成到哪一步、下一步该做什么，而且期间整个事务所工作区照常能用。

**今天是什么样。** 认领成功后直接跳首页，没有任何设置入口（`apps/web/app/(entry)/checkout/success/claim/handler.ts:143-144`）。数据库确实给每个事务所开了一份 `scope_kind='firm'` 的计划（`0145:492-494`），但**这份计划可能是空的，也可能已经装满了**：认领这条路（`claim_paid_firm` → `_create_firm_core`，`0186:1652`）开出来是空的；而「入伙前」那条 `create_firm` + `firmInterview_v3` 的路会把最多十四道题连答案一起写进同一份计划（`firmInterview.v3.ts:163-166`）。所以「种题目」这一步必须是**对账**，不能是盲插——`uq_onboarding_plan_items_key unique(plan_id,item_key)`（`0017:1056`）会直接撞上。

**卡在哪。** 能往计划里写题的门 `update_onboarding_plan` 只发给 runtime 角色（`0017:5125-5135`）；唯一的提交门 `commit_client_onboarding` 强制要有 client（`0017:2751-2771`），所以事务所计划永远出不了 `'open'`；`promote_plan_answers_to_knowledge` 的 firm 那条臂要求计划已 committed（`0192:1654-1657`），至今不可达。前端完全是空的：`/settings/firm` 只剩两段说明文字，首页没有设置进度，导航注册表里没有 setup 这一节（`tree.ts:245-285`）。

**最要命的一件事（复审挖出来的）。** 晋升那张映射表 `knowledge_plan_item_map` 只有一个**全局的 item_key 命名空间**，晋升循环 `join ... on m.item_key = i.item_key`（`0192:1685`）**完全不区分 firm 还是 client**，而且这张表是 append-only（`0192:286-289`），写错了删不掉。所以「把 legal_name 映射到 firm_legal_name」这种做法会让**每一份已提交的客户计划**也跟着把答案晋升出去。这条岔路必须先定，不能留给实现时随手选。

**建议怎么切。** 一支 0199 迁移（事务所题目目录 + 人用的作答/跳过/对账种题/提交门 + `get_firm_setup` 读）、一个 `/settings/setup` 页面加首页入口、一套真角色 DB 电池加 web 单测与 Playwright 走查。确认事实**用已经活着的 `capture_knowledge(p_scope_kind=>'firm')`**（`0192:1112-1147`，且 `kn.11/kn.12` 已有真角色证据），**不动晋升映射表、不新铸身份键**——那两件事各自需要 owner 裁定。按 #640/0193 的先例走，完全不必碰冻结正文。

## Risks

1. **晋升映射是单一全局 item_key 命名空间。** `promote_plan_answers_to_knowledge` 的循环 `join clara.knowledge_plan_item_map m on m.item_key = i.item_key`（`0192:1685`）**不区分 scope**，而该表无 scope 列（`0192:279-284`）、append-only（`0192:286-289`），十条种子里七条注明 “client + firm interviews”（`0192:300-308`）。往里加一行 `('legal_name','firm_legal_name')` 会让**每一份已提交的客户计划**也把 legal_name 晋升出去，而且删不掉。**推荐切片正是为避开这条岔路才改用 `capture_knowledge`。** 若 brief 改走晋升路线，必须显式选定三条出路之一：(i) 共用 item_key（会串道，不可接受）、(ii) 给映射表加 scope 列并改 join（**受控函数重切，须在 0199 prestate 以 pre-image sha256 钉住**）、(iii) 另铸 firm 专属 item_key（不重切，但与 `firmInterview_v3` 已写入的 `legal_name` 等键分叉，会重问 AC1 禁止重问的事实）。
2. **种题必须对账。** firm 计划有两种到达状态：认领路径空（`0145:492-494`；`0186:1652`），`create_firm` + `firmInterview_v3` 路径已装最多十四条（`firmInterview.v3.ts:163-166`，路由挂载于 `src/index.ts:111`）。盲插会撞 `uq_onboarding_plan_items_key`（`0017:1056`）。
3. **`claim_paid_firm` 已在静默误解析重复 firm 计划。** 其 replay 臂是裸 `select … into`，无 `LIMIT` 无 `STRICT`（`0186:1555-1557`），PL/pgSQL 会静默取第一行；`uq_onboarding_plans_one_open` 建在 `(firm_id, client_id)` 且 firm 计划 `client_id` 为 null（`0017:1038-1039`），NULL 互不相同所以不去重。这是**现存活门的缺陷**，不只是新门的护栏。
4. **`defer` 的 reason 无处安放。** `onboarding_plan_items`（`0017:1040-1064`）没有 `reason` 列，其 `deferred` 分支只要 `answered_by`/`answered_at`。必须在迁移里明确落点（`answer` jsonb 或 `_audit` detail），不得假设一个不存在的列。
5. **目录表的 grant 会自相矛盾。** `knowledge_plan_item_map` 的写法把 SELECT 一并给了 `clara_agent_ro` 与 `clara_runtime`（`0192:296-297`），而本切片 §5 要求本文件内无 runtime/agent 授权。照抄 idiom 就会自打脸——grant 矩阵在文件里只写一次且自洽。
6. **firm-scope 行会进每个客户的登记册**（`0192:1338-1356`）。那是 #654 的既定契约，但由 #648 先触发；键集必须先与 #654 议定，因为 `knowledge_keys` append-only（`0192:185`），铸错不可删。见 Q1。
7. **`capture_knowledge` 今天全库无调用方**（只有 `capture_knowledge_for` 在 `chatTurn.v19.tools.ts:50` 被接线）。把人用 capture 门接上是一个全新的写面，其拒绝——未知键（`CLR10 knowledge_key_unknown`）、`knowledge_already_live`、admin 底线、取值形状校验——都需要设计过的面，否则会以裸门错误抵达用户。
