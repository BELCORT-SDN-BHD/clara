## 大白话

这张票要的是：客户首页 `/clients/:id` 上用 A 风格卡片，直接显示三个按 **Work 件数去重** 的关注面——
需要你回答的、正在跑的、最近七个马来西亚日历日做完的；每个数字点进去就是筛好的 Work 列表；再给
「关账准备度」留一个诚实的占位（真正的度量归 #677）。

今天的实际情况比原来的地图写得好一些，也比它写得难一些。

**好的那一半**：三个面里的第一个其实已经上线了。#629 的 0180 把一段 `work_question_rows` 直接缝进了
活的 `clara.list_review_queue`（`packages/db/migrations/0180_work_questions.sql:1065-1080`），
并加了一个整体人口的 `counts.work_questions`（`:1105`、`:1118`）；网页端
`apps/web/components/firm/needs-you-counts.tsx:30` 已经在这个页面上把这个数字渲染成一枚 chip，
门槛是 **viewer**。所以「需要你」不是空白，而是已有一个按 Work 去重（近似）、整体人口、按客户收窄的数字。

**难的那一半**，也是原地图没看见的三件事：

1. **没有 Work 生命周期事件**。`clara._append_event` 是全库唯一的事件出口
   （`0005_event_spine.sql:477-491`），而 0178 / 0180 / 0182 / 0189 / 0194 对它的调用次数是 **零**；
   全库唯一的 `work.%` 事件是 `work.taken_over`（`0184:1455`）。所以原计划那个
   「`max(domain_events.seq)` 当 watermark」的设计，对受理、认领、结算、完成、挂问题、答问题
   **全部看不见**——它会满足 AC4 的字面用词，却正好背叛这张票「不要假数字」的主题。
2. **`clara._work_run_attempts` 硬性拒绝超过 101 个 id**（`0189:262-274`，CLR10 `invalid_work_ids`）。
   「处理中／重试」的整体人口计数原计划走这个已有 helper，但一个有 102 个在跑 Work 的客户会让
   整包读直接被拒，三张卡一起黑掉。而 `clara.agent_tasks` 对 `clara_authenticated` **没有任何 grant**
   （0189 自己的注释说明了为什么它必须是 DEFINER）。这件事必须先定，再写 SQL。
3. **迁移号不是本票自选的**。`WORK-ORDER.md:8` 明写「use ONLY the migration number your brief
   assigns」，这一波十二张票并发，0199 不能自己认领。

「最近做完」确实没有现成字段：`clara.accounting_work` 只有 `created_at`/`updated_at`
（`0178:324-325`），真正的完成时刻在 `clara.operation_receipts`（`outcome='committed'`）那一行——
这一点原地图是对的，而且 0194 已经把 receipt 的 `purpose` 一并放宽到三个值（`0194:233-234`），
所以覆盖面比原来以为的更完整。不动任何冻结 workflow。

### One invariant note, corrected in both directions

`0189:474-476` attributes "at most one pending question per Work" to `ix_agent_interruptions_work_pending` — which is a **plain** index (`0180:214-216`); the UNIQUE index is `uq_agent_interruptions_work_version` on `(work_id, question_version)` (`0180:211-212`) and permits two pending rows at different versions. **But** the single open-question verb refuses outright when any pending row exists for the Work — `if exists (select 1 from clara.agent_interruptions where status='pending' and (task_id = p_task or work_id = w.id)) then raise … question_already_pending` (`0180:~651-653`). So the invariant is **verb-enforced, not structurally enforced**. Consequence: `count(distinct work_id)` remains the correct defensive spelling, but a DB cell that "proves" it with two pending versions is **not constructible through the verbs** — it needs owner-level fixture DML and must be labelled a defence-in-depth cell, not a verb-reachable one.
