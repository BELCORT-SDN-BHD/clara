# Gap map — #633 上传或附加文件后自动受理并开始处理

Reconciled at `4464e471` (2026-09-15) against two adversarial reviews. Every path:line below was opened in this session.

## 大白话

这张票要的是：人把文件丢进来（客户文档页、聊天附件、或事务所层面的来料），系统自己就开始处理，不需要谁再按一次「开始处理」；每个文件都有自己的进度、回执、取消与重试，并且能看见它牵出了哪件 Work。

**今天后端已经是全自动的**：上传 → 封存 → OCR/结构化解析 → 分类（0177 要求抽取成功才分类）→ 类型化事实 → autodraft 消费者自动受理编码任务，全程没有人工闸门；`request_autodraft` 早在 #614 就被改写成「重新开始处理」的补救动作，不是闸门。

**真正缺的在前端的渲染面，不在数据库。** 两轮 review 把原先的判断砍掉了一大块：回执读取（`readIntake`）、处理任务计数（`listProcessingTasksForDocument`）、未归属来料（`list_unassigned_documents`）、文件↔分录绑定（`entry_evidence_links` 直接 select 授权）——这四样**今天都已经存在并且已经授权**。缺的是：上传队列是个纯客户端 `<ul>`（不是 Data Table），没有真实字节进度，刷新就丢回执（因为这些读只在轮询里调、队列活在一个 React ref 里），没有独立的「取消」，20 种 document_kind 以 snake_case 原样显示，9 种失败码没有各自的下一步，文件看不到对应的 Work，事务所层面没有界面。

**所以这张票是 Web 为主 + 迁移可选（最多一个函数）+ 一条真 Postgres World 的「上传到自动受理」e2e。不动任何冻结正文。** 浏览器上传步道**已经存在**（聊天口），扩展它即可，不是从零搭 harness。
