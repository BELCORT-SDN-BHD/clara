## 大白话

这张票要的是：让「交易对方（供应商／客户）的身份」跟客户资料一样，有一个统一、可追溯、可更正的地方 ——
改名、别名、合并、识别码（SSM／TIN）都要记下来源、是谁写的、是人写的还是 Clara 写的，
并且在界面上能看见历史和冲突，不用先做一套「绑定仪式」才能开始干活。

今天数据库其实已经做了大半：稳定的 counterparty UUID（`0009:812`）、按 vendor/customer 分开的唯一键
（`0015:187`、`0176:319`）、改名自动留旧名别名（`0011:1807`）、合并有血缘表 `clara.counterparty_merges`
且报表读会同时给出「记账时的对方」和「合并后的对方」（`0149:585-600`）、客户自己的识别码有唯一键（`0155:402`）。

差的是三件事：

1. **没有出处**。别名只记了 `created_by`（一个人）和一个三值 `origin`（`0011:658-659`），没有来源文件／抽取版本，
   也没有「这是 Clara 写的」这一位；`clara.tick_seeding_proposal` 甚至把别名硬写成 `origin='human'`（`0118:315-319`）。
   识别码根本没有历史 —— `set_counterparty_identifiers` 就地覆盖，旧值只进 `_audit`（`0174:846-849`）。
2. **人看不到**。`clara.counterparty_aliases_visible` 从 `0145:960` 就存在，但 web 里没人用它
   （`counterparty.ts:94-105` 的注释还停在 0140 说「没有读」，是过期注释）；合并血缘表零消费者；
   aging/statement 把 DB 给的 `recorded_counterparty_id` 在前端类型里丢掉了（`aging.ts:30-49`、`counterparty.ts:218-226`）；
   `set_counterparty_identifiers`（`0174:785`）根本没有界面。
3. **没有一条带版本的更正路径**。改名／加别名／改识别码都不发领域事件，所以没有任何东西知道「身份变了」；
   #644 的 Knowledge 登记册（`0192:102-103`、`:269-278`）也明确把身份留给了这张票。

**两轮评审改了什么最要紧**（细节见末节）：

- 我原本写的「两个闭世界列普查会被视图加宽打红」是**错的** —— 那两个 cell 一个查授权矩阵、一个查视图名单，
  加列都不红。真正会红的是另外一件事：**新建任何一个 masked human-read 视图**都会自动加入 debt-BAR1 的名单而打红，
  所以三个新读**必须是 SECURITY DEFINER 函数，不能是视图**。
- 真正会被这一刀打红、而我原来没列的是 `knowledge-onboarding-promotion.test.mjs` 的 **kp.01**：
  它对 `knowledge_plan_item_map` 做十行 `deepEqual`，多插五行立刻红。
- 我援引的「非冻结 runtime 模块」先例 **`periodic-adjustment-basis.ts` 本身就在冻结清单里**（按闭包冻结）。
- 我提的新详情页地址 `/knowledge/counterparties/:id` **在导航树里解析不出 leaf**，面包屑会骗人。
- AC1 按原方案落地后**一条活的写路径都不会带出处** —— web 门还指着不带出处的五参数签名。
