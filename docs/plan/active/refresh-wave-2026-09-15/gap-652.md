## 大白话 summary

这张票要让用户能用会计界面、对话或上传的资料说清一笔「应计」——金额依据、科目和业务用途、生效／服务期间、算法、授权来源和指令出处——
系统据此在本期开出正确分录，并把获准的「转回」和原来那笔应计牢牢绑住。

今天已经有的，比原始 gap map 说的多。#640 交付的 `reversing_journal` 计划**本身就是「应计 → 转回」两条腿的排程**：到期日入账应计，
下月一日自动反冲，转回在数据上指名它反冲的那张分录（`reverses_entry_id`，0193:652），并且没有已入账的应计就拒绝转回（0193:1326-1360）。
产品文案自己也是这么写的：`en.json:4832` 说的是「reversing journal 在到期日入账它的 accrual」，被排除的是折旧、预付款和结账——
**原始 map 把这句话读反了**。#643 交付的 `periodic_adjustments`（0194）则给出了「带类型的明细 + 分录 + 回执同一事务落地」的完整模板。

真正缺的是中间那一层：**带类型的应计明细**（服务期间、算法、「期限不明就拒绝」）、**应计自己的持久记录**、**一个前端入口**。
另外两个已核实的坑：计划车道的 `_plan_admit_occurrence` 是用 `admit_journal_work` 收案的（0193:1368），
所以照原方案做，计划开出来的应计不会留下应计记录；而入账核心那段 `if w.adjustment_basis is not null`（0195:2165）
写死了写入 `periodic_adjustments`，那张表的 purpose CHECK 只认两种用途——第四种用途一提交就会被 CHECK 打回。

服务期间也不是从零开始：0140（F-A4 PR-2a）已经有 `clara.document_service_periods` 这根「文件级期间载体」和
「模型推导的期间不得进入持久记录」这条**已确认为法律**的规定——但它今天在 runtime 和 web 里一个引用都没有。

1. **Does the accrual ride `kind='reversing_journal'` or get a new `accounting_plans.kind`?** *(changes what is built)*

2. **One relation or two: a NEW `clara.accrual_adjustments`, or widen `clara.periodic_adjustments`' purpose CHECK?**
