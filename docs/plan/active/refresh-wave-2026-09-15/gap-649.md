## 大白话

这张票要做的是：从「新建一个客户」开始，到「确认企业身份、财年、报告口径」，再到「有没有期初要带进来」，
最后「回到客户首页继续做账」，这一整条路要走得通、走得顺、断了能续上。

今天这条路的骨架已经很完整：`/clients` 上有「新增客户」按钮，DB 里 `begin_client_onboarding`
一笔事务生出客户+开户计划，runtime 有一条真正持久化的访谈工作流 `clientOnboarding_v4`（断线、杀进程都能续），
提交后 `promote_plan_answers_to_knowledge` 把答案写进 Knowledge 登记簿，客户首页也已经有身份带、开户进度、需要你等区块。

差的是四件具体的事：

1. **重名只挡「一模一样」**。真正能查「像不像」的函数 `name_family_candidates` 存在，但**按迁移法规定不许授权给任何应用角色**
   （0103 的尾部有一道活的权限普查，谁拿到 EXECUTE 就报错），而且它的判定是「**两个以上**才算模糊」——
   只有一个同名家族的对手方时它根本不响。所以「给人看候选」和「DB 挡住」这两件事今天对不上口径。
2. **访谈的答案没有落到客户档案本身**。财年只进了 Knowledge 登记簿，没进 `clients.fy_end_month/day`
   ——而且**访谈根本没问「哪一天」，只问了「哪个月」**，而那张表的 CHECK 要求月和日要么都空要么都有，
   所以这个写入今天**根本写不出来**，不是没接线，是缺一个问题或者缺一条业主裁定。
3. **访谈不会「只问缺的」**。已答「未注册 SST」仍然接着问 SST 号（H-52），而问题清单在冻结的
   `clientOnboarding_v4` 正文里，要改必须发 `clientOnboarding_v5` 新正文。
4. **期初那边「第一年不用带」和「该带但资料没到」已经分开了，但没有一条链接指过去**，
   0170 在 DB 里加的那个键 Web 端也从没读过。

**两轮评审改了什么最要紧**：结算门原本设计的「机器车道孪生函数」是**走不通**的（`set_client_fy_end`
只授权给人类角色，机器身份会直接 CLR04）；财年那一格**今天写不出来**；而且我自己查出一件两位评审都漏了的事——
方案里当作「安全出口」的那个「非冻结 lib」**并不存在**：它援引的先例 `periodic-adjustment-basis.ts`
本身就在冻结清单里，注记写明是「**按闭包冻结**」。工作流一 import，它就跟着冻。

## Frozen-body verdict

**Touches a frozen closure: yes — but not the two the brief names.**

Not `claraWork_v3` and not `chatTurn_v19`. The closure this ticket collides with is **`clientOnboarding_v4`**.
AC2's "ask only for missing facts" and row H-52 are both changes to the question inventory and the ask loop,
which live in `clientOnboarding.v4.ts`, `interview.v3.questions.ts`, `interview.v2.{questions,core,segments,rules}.ts`
and `interview.v1.{steps,writer,questions,core}.ts` — every one `deployed:true`, and
`check-frozen-workflows.mjs` freezes **the transitive relative-import closure** of each frozen workflow, with
check 3 a hard REJECT vs `origin/main`. Editing body and manifest together is the exact bypass it blocks.

**The successor is therefore `clientOnboarding_v5`**, minted the way v4 was minted over v3: a new
`clientOnboarding.v5.ts` + a new `interview.v4.questions.ts` exporting `CLIENT_SEGMENTS_V4` built by `.map`ping
over V3 and replacing only the changed segments **by reference** (the discipline `interview.v3.questions.ts:107`
states and `coa-interview-v4.test.mjs` asserts), plus a new sibling step module — siblings, never an added export
to a frozen file. v1–v4 stay byte-identical, exported and registered; `registry.ts:264`/`:908` repoint;
`workflowBodies` grows by one. `registry.ts` is not itself frozen, and check (d) forbids only a downgrade or a
removed class, so the repoint is legal. `interview-e2e.mjs` inherits it with no edit.

> **One alternative worth naming and rejecting rather than asserting away**: the `/answer` route or the web could
> auto-deliver `skip` for `sst_no` (`v4.ts:157` — a skipped outcome leaves no plan item either). Reject it: that
> puts an accounting applicability rule in a presentation layer and the park is still announced. But it is a real
> option and the spec should say why it loses.

### ⚠ The "non-frozen lib" escape hatch does not exist as drafted

*Found in this pass; neither review caught it.* The original slice proposed putting every new rule in a
**non-frozen** `packages/runtime/lib/onboarding-known-facts.ts` on the `periodic-adjustment-basis.ts` precedent,
and keeping v5's delta thin so future changes stay editable. That is self-defeating:

- `packages/runtime/lib/periodic-adjustment-basis.ts` **is in `frozen-workflows.json`**, `deployed:true`, with the
  note: *"#643 — frozen BY CLOSURE, not by marker: chatTurn_v19 imports the adjustment schemas and basis builders,
  so check-frozen-workflows.mjs's import closure hash-locks this file (the web form imports the same module and is
  NOT frozen — only this closure membership locks it)."*
- `packages/runtime/lib/knowledge.mjs` is frozen the same way.
