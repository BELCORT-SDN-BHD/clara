## 大白话

一份已经进了系统的文件，事后发现「金额读错了／类型分错了／归到了错的客户」时，用户要能改：原件和原来的账都留着，改完之后受影响的待办、知识和已入账结果都要被重新处理，而不能悄悄沿用旧结论。

今天系统做到了两件半。**改类型**有正规门（`0169 set_document_kind`：要理由、写回执、还会自动关掉那条分类问题）。**改客户归属**有一整套成熟流程（`0125` 预览影响 → 提案锁哈希 → 双人批准 → 冲销镜像分录 → 退休原归档 → 建新归档）。原件字节、来源版本、字段路径和区域出处都可读（`0190`/`0191`）。

差的是三块。**第一，改「事实值」根本没有人类门**——只能让机器重跑一次抽取（`0026 request_reextraction`），人不能直接改一个读错的金额。**第二，文件改了之后没有任何东西去回看知识记录和待答问题**；知识虽然用外键指着抽取和区域（`0192`），但没有消费者。**第三，更正没有产生一件真正的 Work**——今天只产生一条 `coding_task` 加一条通知，而 Work 列表只读 `accounting_work`。

**这一轮复核翻掉的最大一块**：原来的方案把「更正 Work 放进 `clara.accounting_work`」当成已经定了的事。实际上 `_admit_accounting_work_core` 无条件调用 `_assert_journal_basis`——**每一行 `accounting_work` 都必须在受理那一刻就带上一套完整、借贷相等、至少两行、真的在动钱的分录**。也就是说，要把更正 Work 放进 `accounting_work`，#646 就得在受理时算出冲正分录——而那正是 AC4 自己交给 #676 的活。这个选择必须先由 Owner 裁掉，才能动 migration。
