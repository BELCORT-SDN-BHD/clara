# Wave B adversarial memo

1. **[SHIPPING-STOPPER] The “wiki never selects an account” guarantee is currently only prompt discipline.** — Draft P1 and Gate W2 require structural non-influence (`wave-b-contract-draft.md:24-26,207-210`). Yet `chatTurn_v6` injects the whole context pack into the same model invocation that owns `draft_journal_entry` (`chatTurn.v6.ts:77-85`); the model supplies every `account_code` (`chatTurn.v6.prompt.ts:202-222`), and the DB accepts those lines before merely recording whether a live rule happened to match (`0016_a21_compliance_watch.sql:4065,4100-4105,4170-4195`). A stochastic “conflicting wiki text did not move one draft” probe proves nothing. **Fix:** define a structural account-basis/data-flow boundary: coding segments must not receive account-selecting wiki prose, or every proposed non-control account must bind to a typed Layer-2 authority/human choice that the DB revalidates.

2. **[SHIPPING-STOPPER] Onboarding open questions will client-wide block unrelated approvals.** — T9 merely adds `origin='onboarding'` and possibly firm scope (`draft:144-146`). As built, every open client-scoped question except `rule_proposal` blocks every entry for that client (`0012_consent_optional_and_rule_proposal.sql:98-107`), and approval raises CLR26 (`0016:1347-1353`). An incomplete onboarding checklist could therefore freeze legitimate daily work—the exact A2.1 collision class. **Fix:** add explicit `blocking_capability`/`blocking_scope`, or a separate onboarding-task type. Only identified prerequisites may block onboarding commit; ordinary incomplete items must not enter `_open_question_blocks`.

3. **[SHIPPING-STOPPER] There is no coherent onboarding commit or partial-state model.** — T12 says nothing reaches books/wiki before one commit, while B3 creates identity, CoA, and identifiers before B4/B5 (`draft:163-186`). `create_client` immediately creates an active client (`0004_governed_fns.sql:343-359`); `clients.status` has only active/archived (`0003_books_core.sql:34-39`), and belts already iterate active clients (`0016:866`). A half-onboarded client can therefore enter coding, SST evaluation, and queue machinery with incomplete CoA. Firm onboarding also cannot durably run inside a firm before `create_firm`, whose admission token is single-use rather than receipt-idempotent (`0004:315-340`). **Fix:** ratify either isolated staging objects or an `onboarding` lifecycle state excluded structurally from every operational consumer, then define exactly when activation occurs.

4. **[SHIPPING-STOPPER] “Pack v4 and chatTurn_v7 in one ceremony” does not protect frozen runs.** — P5 assumes co-deployment solves framing (`draft:38-40`). But old workflow exports deliberately remain resumable (`registry.ts:1-7,46-51`), and v6 will still call global `get_context_pack(...,'chat')` after v4 lands (`chatTurn_v6.ts:77-85`; `0016:4262-4351`). Parked v1–v6 runs will therefore receive unframed wiki data even after v7 deployment; rollback may strand new interview versions. **Fix:** capability/version-gate wiki exposure, for example a new v7-only purpose literal, and require non-terminal-run export checks for deploy and rollback.

5. **[SHIPPING-STOPPER] T5 knowingly accepts a false tie-out assurance.** — It accepts post-tie-out backdating as a lint-only gap (`draft:121-127`). Nothing prevents a later ordinary entry dated before takeover, and the existing reversal path posts the mirror at `current_date`, not the original/takeover date (`0004:576-579`). Thus the dated TB can become invalid and a “supersede” using today’s reversal cannot repair the historical position. **Fix:** add a minimal takeover cutoff now—not Wave E’s full lock system—and a specialized atomic opening correction that reverses/replaces at the governed opening date and reasserts the external TB tie-out.

6. **[SHIPPING-STOPPER] One-shot/idempotent and batch approval semantics are not concurrency-safe yet.** — P7 names receipts plus a seeded-once registry but no lock/state machine (`draft:44-46`). Receipts dedupe only identical `(firm,fn,op_key)` calls (`0002_foundation.sql:290-302`); two distinct keys can race. Current dashboard batching is explicitly independent, partial-success, and high-stakes-excluding (`BatchApprove.tsx:3-9,57-74,103`). **Fix:** one DB transaction must lock the client/seed row, verify plan revision/source hashes/all entry revisions/checker separation, approve the complete set, and finalize the seed registry atomically. Gate K must distinguish same-op retry returning its receipt from a second semantic seed with a different key raising.

7. **[SHIPPING-STOPPER] LLM wiki synthesis has no egress ruling.** — B1 mandates an LLM projection, but the contract never says what happens without client authorization. Existing external document processing is held at the claim boundary when consent is absent or revoked (`0011_daily_loop.sql:2315-2359`), and PRD invariant 16 governs client-data egress (`PRD.md:131`). **Fix:** specify provider/local execution, consent scope, revocation behavior, held/dead-letter state, and whether deterministic ingest without synthesis remains available.

8. **[WRONG SHAPE] “Confirmed @1.000” is not representable in the live rule schema.** — P10, T2, and Gate R2 import the frozen confidence idiom (`draft:57-62,94-102,213-215`), but `coding_rules` has no confidence or evidence-count column; authority is `status='live'` plus `signed_by/signed_at` (`0011_daily_loop.sql:753-789`). **Fix:** do not smuggle confidence back into live rules. Put prior-GL metrics and cited provenance in a separate advisory proposal object; a live rule’s authority should remain the human signature alone.

9. **[WRONG SHAPE] The pinned opening model lacks required as-built primitives.** — P8 requires OBE resolution by marker, but current `special_acc_type` permits only rounding, SST output, and SST purchase cost (`0016:121-125`). `fixed_assets` permits only straight-line depreciation and has no immutable baseline-event row (`0003_books_core.sql:155-180`). **Fix/questions:** add explicit OBE/retained-equity markers; decide non-straight-line policy; require account bindings and acquisition-entry linkage; atomically tie each asset’s cost/accumulated depreciation/NBV to opening lines and an immutable baseline event.

10. **[WRONG SHAPE] T11 ignores the Storage/Postgres atomicity gap.** — “Durable artifacts, replay only re-indexes” (`draft:158-161`) fails if object upload succeeds but index/event commit fails, or vice versa. **Fix:** deterministic immutable keys, content hashes, upload→verify→publish states, projection receipts, orphan repair, and events containing enough immutable metadata to rebuild the index. A query’s optional file-back must dispatch the audited ingest writer; the read function itself should remain pure.

11. **[MISSING TENSION] Lint findings have no lifecycle or usable dashboard surface.** — T8/B2 says daily findings enter the queue (`draft:139-142,176`), but the queue knows only five row kinds (`reviewTypes.ts:28-58`) and unknown rows fall into a no-action placeholder (`QueueDetail.tsx:79-88`). No dedupe key, reopen/supersede rule, resolution verb, or exactly-once notification policy is defined. Daily lint will spam or produce dead work. **Fix:** specify finding identity, state transitions, recheck semantics, hydration card, and owner actions.

12. **[EVAL-GATE GAP] O/K/W2/L/R2 are insufficient to close the wave.** — They omit concurrent seeds/answers, failure after N items, cancellation/expiry, stale plan revision after a 48-hour park, firm onboarding, consent loss, cross-firm SECURITY DEFINER probes, large-corpus token ceilings, old-run resume after upgrade, and rollback preflight (`draft:194-215`; runtime rollback law `packages/runtime/README.md:233-244`). Gate L’s “seeded contradiction” must use genuinely conflicting real sources, not contaminate live knowledge with a fabricated source. Add these as falsifiable live gates, with destructive/fault-injection variants confined to the rig where necessary.

## Five questions missing from G1–G10

1. What structural data-flow rule—not a prompt or repeated model probe—makes it impossible for wiki prose to determine an account code?

2. What are the exact onboarding lifecycle states and activation boundary, and which unfinished questions block only onboarding versus ordinary client work?

3. What single serializable transaction governs prepare, checker approval, retry, concurrent seed, failure recovery, and dated supersede of an opening set?

4. How do wiki synthesis, Storage publication, consent/revocation, projection lag, and books/knowledge freshness fail closed as one protocol?

5. Which mandatory close gates cover cross-tenant ACLs, concurrent races, 48-hour stale-resume, cancellation/expiry, workflow upgrade/rollback, real-corpus token ceilings, and firm—not merely client—onboarding?
