# Wave A — daily-loop design review (NATIVE lane)

VERDICT: FLAWED

Reviewer: native lane, design-stage (pre-code), independent of the Codex lane.
Targets: `docs/plan/wave-a-daily-loop-contract.md` v1.0 DRAFT + `docs/plan/wave-a-migration-0011-design.md` v1.0 DRAFT.
Grounded against: PRD §6 invariants; ARCHITECTURE Appendix A; slice6-thin-e2e-contract v1.3 + companion 0009 + as-built AB-1..22 + delegated-decisions S6-D1/D2; `packages/db/migrations/0009_coding_floor.sql` (read in full), `0006_runtime_core.sql`, `0007_document_pipeline.sql`; `packages/runtime/lib/matcher.mjs`, `lib/drain.mjs`, `workflows/registry.ts`, `workflows/documentIngest.impl.ts`, `workflows/invoiceFacts.v1.impl.ts`; audit `01-findings-report.md`.

The rulings WA-R1..R12 are treated as ratified. Every finding below attacks whether the design *realizes* them correctly, completely, and consistently with binding law — not the decisions themselves.

Verdict rationale: the confidence-ladder is the load-bearing centrepiece of the wave and its lane function (§2 / companion §3) is specified as a security-INVOKER read that calls three ungranted SECURITY-DEFINER helpers — a structural impossibility the 0009 code deliberately avoids (F2). The multi-client egress registry (WA-R2, the wave's biggest expansion) is specified to gate a lane (OCR) that runs *before* client attribution exists, so the per-client consent it rests on cannot be evaluated there (F1). And the auto-draft execution lane (§3) collides with the existing `agent_tasks` insert-trigger, status machine, and wake-drain projection in ways no build lane could resolve without inventing mechanism (F3). Each is fixable at the design table; none is safe to hand to a build lane as written.

## Findings (most-severe-first)

### [CRITICAL][§8 / companion §10] The per-client egress registry cannot gate the OCR lane, because OCR egress happens before any client is attributed — so WA-R2's multi-client model has no lawful first-egress gate.

Defect. §8 moves the egress gate "from the firm-wide flag to a per-client lookup: egress for a client's documents requires a live consent row," and companion §10 says the rewire covers "`claim_document_processing_task`'s held_egress logic" — which spans **both** lanes (`lane in ('ocr','invoice_facts')`, 0009:2201). But in the S6 pipeline the OCR lane runs on an **unassigned** document, *before* the human files it to a client (contract §2 flow: `… → OCR (egress gate) → matcher → HUMAN FILES the bill → [invoice-facts]`). At OCR-claim time there is no filing and no client, so "the document's client" — and therefore any per-client consent row — does not exist yet.

Failure scenario. In a firm serving clients A (consented) and B (not consented), a document is uploaded. `documentIngest.impl.ts:48` computes `egressApproved` and calls `claim_document_processing_task`. Under "=1 no longer grants anything by itself — rows do" (§8) there is no client to look up, so OCR either (a) blocks forever — the intake pipeline deadlocks, because the matcher needs OCR regions to help the human attribute the doc, and filing can't happen until the doc is attributed; or (b) egresses ungated — defeating the whole consent regime. There is no third option available at OCR time. Worse, this is a genuine *compliance* tension, not only an implementation one: the point of per-client consent (PRD §6 invariant 16 / Gate-1 C6) is not to process a client's data without authorization, yet the very first egress (OCR to Azure) is structurally forced to occur before you know whose data it is.

Exact text at fault. §8: "The document-egress claim gate moves from the firm-wide flag to a per-client lookup: egress for a client's documents requires a live consent row." Companion §10: "egress requires (global kill-switch != 0) AND a live consent row for the document's client."

Proposed fix. Carve the lanes explicitly: (1) the **OCR** lane stays gated by a firm/global baseline (the kill-switch, and optionally a firm-level "any-processing" consent), because it is pre-attribution by construction; (2) the **invoice_facts** lane (enqueued at filing, client known) gets the per-client consent gate. State this split in §8 and companion §10, and resolve the shared-document case (a doc filed to A and B, only A consented — facts egress is document-level and would expose B's document) — likely: facts egress requires *every* active filing's client to have consented, or the doc is single-consent-gated with cross-filing egress refused. Without the split, WA-R2's "full multi-client product" claim has no coherent egress foundation.

### [CRITICAL][companion §10] "The egress semantics change is runtime-config only" contradicts "the claim gate rewires" — the per-client check is impossible in the runtime and must move into the definer DB function; the companion asserts both.

Defect. Companion §10 says two incompatible things: the claim gate "rewires" (a DB-fn change), and "`CLARA_DOC_EGRESS_APPROVED` semantics change is **runtime-config only**." The runtime cannot perform the per-client check: `documentIngest.impl.ts` / `invoiceFacts.v1.impl.ts` compute a bare `process.env.CLARA_DOC_EGRESS_APPROVED === "1"` boolean and pass it as `p_egress_approved` (0009:2201 consumes it). The runtime holds **no** SELECT on `clara.documents` (AB-6, explicit), let alone `document_filings` or `client_egress_consents`, and does not know the client at claim time. So a per-client decision cannot be a "runtime-config" boolean.

Failure scenario. A build lane reading "runtime-config only" wires the check in the workflow, discovers the runtime can't read consents, and either grants the runtime new SELECTs (violating the AB-6/AB-13 grant-hygiene discipline and the §13 grants delta, which grants `clara_runtime` nothing on `client_egress_consents`) or stalls. The only lawful realization is a definer-internal consent read inside `claim_document_processing_task`, with the env var passed through as a global kill-switch.

Exact text at fault. Companion §10: "`CLARA_DOC_EGRESS_APPROVED` semantics change is runtime-config only — =0 halts all (unchanged), =1 now DELEGATES to rows instead of granting firm-wide."

Proposed fix. State that the consent check is **definer-internal** to `claim_document_processing_task` (which already reads `clara.documents` as a definer, 0009:2192), joining document → active filing → client → `client_egress_consents`; the runtime keeps passing only the kill-switch boolean. Update the §13 grants delta accordingly (no runtime SELECT on consents; the read is inside the definer). Reconcile with F1 (OCR has no client to join).

### [HIGH][§2 / companion §3] `coding_lane` is specified as SECURITY INVOKER yet reads `_resolve_counterparty`, `_invoice_fact_state`, and `is_high_stakes` — all ungranted SECURITY-DEFINER helpers that an invoker running as `clara_agent_ro`/`clara_authenticated` cannot execute; the 0009 code deliberately inlines instead of calling them, for exactly this reason.

Defect. Companion §3: "`clara.coding_lane(...)` — STABLE read fn, security INVOKER, RLS-scoped; granted `clara_authenticated`, `clara_agent_ro`. … Reads: … `_resolve_counterparty` preview, `_invoice_fact_state`, near-dup …, `is_high_stakes` on the would-be amount." But 0009 REVOKEs EXECUTE from PUBLIC on every function and grants these three to **nobody** on the app lanes: companion §9 states "NOT granted: `_validate_entry_lines`, `_assert_supplier_bill_shape`, `_resolve_counterparty`"; `_invoice_fact_state` and `is_high_stakes` are equally absent from every `grant execute` list (0009:2893-2929). A security-invoker `coding_lane` executes with the caller's role, so calling any of them as `clara_agent_ro` raises 42501.

This is not hypothetical — the 0009 authors hit exactly this and worked around it: `get_draft_review` (invoker, 0009:2687) **re-derives** the counterparty "current outcome" inline (0009:2706-2735), computes high-stakes inline (0009:2743-2750), and computes near-duplicates inline off the facts tables (0009:2752-2792) with a load-bearing comment: "get_draft_review is security-invoker and **must not call the ungranted definer `_invoice_fact_state`**, and exposing that unscoped helper to the read lanes would **leak cross-firm facts**" (0009:2753-2756). `_invoice_fact_state` selects by `document_id`/task alone with **no firm scoping** (0009:2139-2202) — granting it to the agent lane is a cross-firm oracle.

Failure scenario. A build lane implements `coding_lane` per the companion, ships it, and every agent-lane call raises 42501 (or, if the lane fn is "fixed" by granting the helpers, it becomes a cross-firm facts oracle). Either way a core, DB-gated invariant surface (WA-L1, the thing that "kills the A-5/Ggr-13 model-asserted-gate class") is broken.

Exact text at fault. Companion §3, the "Reads:" clause naming `_resolve_counterparty preview`, `_invoice_fact_state`, `is_high_stakes`.

Proposed fix. Either (a) `coding_lane` **inlines** every predicate as RLS-scoped invoker reads (mirroring `get_draft_review`'s v_current / v_high / near-dup blocks) and calls **no** ungranted definer — accepting the resulting duplication of the resolution-preview and corroboration logic, and pinning it to `get_draft_review`'s inline forms so the two cannot drift; or (b) make `coding_lane` SECURITY DEFINER with an explicit firm scope + the `CLR03`-on-null-`wake_firm` guard + an oracle-safety proof (identical not-found shape across firms). The companion currently specifies the one combination that cannot exist.

### [HIGH][§3 / companion §4] The `autodraft` task lane collides with the existing `agent_tasks` machinery on three axes — the insert trigger, the update status-matrix, and the wake-drain projection — none of which the design addresses; a build lane cannot realize it without inventing mechanism.

Defect. §3.2 wants "a held `agent_tasks` row (drain-pattern) of a NEW task kind `autodraft`," executed by `autoDraft_v1` calling `wake_draft_entry` with `p_coding` pointing at that task. But `_draft_entry_core`'s coding-eligibility branch requires `t.kind='chat_turn' and t.status in ('queued','running','awaiting_input')` (0009:1279-1283); the companion §4 widens the kind set to `{chat_turn, autodraft}`. Three existing structures break under an `autodraft` kind:

1. **Kind CHECK + insert trigger.** `agent_tasks.kind` is `check (kind in ('chat_turn','wake'))` (0006:142). `_tf_agent_task_insert` hard-branches: `chat_turn` (forbids `origin_intent_id`, 0006:395-408) vs `wake` (requires `origin_intent_id`, 0006:409-420). An `autodraft` row satisfies neither branch — the trigger has no path for it.
2. **Update status-matrix.** `_tf_agent_task_update` allows a **wake** task only `held → cancelled` (0006:471) — there is no held→running/queued lifecycle for a non-chat_turn task. But eligibility needs the autodraft task in `queued/running/awaiting_input`. So the design's "held … (drain-pattern)" task can never reach an eligible status under the existing matrix; a new status machine for `autodraft` is required and unspecified.
3. **Wake-drain projection pins the wrong kind.** `drain.mjs` inserts `kind='wake'` (`lib/drain.mjs:78-80`) and the derivation trigger pins it. So "inserts held tasks via the existing drain/held-task projection with wake kind" (companion §4) yields a **wake** task (`kind='wake'`), which the widened eligibility (`chat_turn|autodraft`) still rejects. The companion is internally contradictory: a wake task is rejected by eligibility; an autodraft task cannot come from the wake drain.

Plus: the `document.invoice_facts_completed` event carries **no client_id** (`persist_invoice_facts` appends it with the client arg NULL, 0009:2146-2148), yet the autodraft task must be client-bound (its `coding_attempts` FK is `(task_id, firm_id, client_id)`, 0009:979) and eligibility checks `t.client_id=p_client`. The consumer must resolve document → active filing → client itself, and handle the shared-document (multiple active filings) case — unspecified.

Plus: the wake credential the workflow runs under must present a `wake_kind` allowlisted for `wake_draft_entry` + the read fns (`assert_wake_allowed(w.wake_kind, 'wake_draft_entry')`, 0009:1446). That is a NEW wake_kind with new allowlist rows (structural invariant 2c). The §13 grants delta enumerates no such wake_kind/allowlist rows.

Failure scenario. The build lane cannot create an `autodraft`-kind held task (insert trigger rejects it), cannot transition it to an eligible status (update matrix has no edge), cannot reuse the wake drain (wrong kind), and has no enumerated wake_kind/allowlist to run the workflow under — so it either invents all of this silently (guessing at the security-critical allowlist and lifecycle) or the sweep never drafts.

Exact text at fault. §3.2 ("a held `agent_tasks` row (drain-pattern) of a NEW task kind `autodraft`"); companion §4 ("inserts held tasks via the existing drain/held-task projection with wake kind on the allowlist").

Proposed fix. Specify the full `autodraft` task model as its own lane: (i) the kind-CHECK widening + a new `_tf_agent_task_insert` branch (no `origin_intent_id`, own required fields); (ii) a new `_tf_agent_task_update` status machine (created→running→done/failed) that reaches an eligible status; (iii) the projection **writer** (not the wake drain) that creates the task with the resolved client_id, including the shared-doc rule; (iv) the new `autodraft` wake_kind and its exact allowlist rows in §13. This is the single largest under-specification in the packet.

### [HIGH][§3 / §6 / companion §4,§7] How a READY bill's expense account is actually chosen by the unattended sweep is unspecified — and the rule-application path contradicts itself ("the runtime passes nothing" vs "when the proposal cites a rule"). This is load-bearing (it is the whole point of the sweep) and it is where old-build defect C-10 re-enters.

Defect. WA-R3 permits READY (hence swept) bills **without** a signed rule ("a rule is not required for READY in v1"). §3.2 says the consumer "NEVER runs a model in-loop," and `autoDraft_v1` "perceives via the existing read tools and calls the `draft_journal_entry` write path." For a rule-less READY bill, *something* must select the expense account. Two unstated possibilities, both material:
- If `autoDraft_v1` runs a **model** to propose the account (the natural reading of "perceives … proposes"), then the sweep *does* run a model per bill — which is fine under S6-R4/the draft-only ceiling, but must be stated because it drives the token-budget reserve (WA-L5) and the "no model in-loop" claim is only about the *consumer*, not the *workflow*. The contract never says the workflow runs a model.
- If the account is meant to come **only** from a rule, then rule-less READY bills cannot be drafted, contradicting WA-R3.

Compounding, the rule-application mechanism is self-contradictory. Companion §7: "the runtime passes **nothing** — `_draft_entry_core` snapshots (rule_id, content_hash) into the coding attempt metadata **when the proposal cites a rule**." "The runtime passes nothing" (DB looks the rule up) and "when the proposal cites a rule" (runtime/model chose it) are mutually exclusive. For Gate-1 **C-10** compliance ("Rule matching in the rebuild must be a deterministic DB-side operation keyed on the normalized/alias-resolved canonical — never model-side fuzzy matching"), the rule must be looked up **in the DB** by `(client, resolved counterparty)`. But `_draft_entry_core` today does no such lookup, and adding it is a non-trivial body change (query `coding_rules`, snapshot into the attempt) that the companion mentions only as an aside.

Failure scenario. The build lane guesses. If it lets the model pick the rule ("proposal cites a rule"), C-10 re-enters — auto-lane consistency rests on model fuzziness the schema claims is deterministic (the exact old-build failure). If it makes the DB look up the rule but leaves account selection for rule-less bills to the model, the design works but the contract never authorized a model in the sweep, and the token budget was sized against an unstated cost.

Exact text at fault. §3.2 ("The consumer NEVER runs a model in-loop"); companion §7 ("the runtime passes nothing … when the proposal cites a rule").

Proposed fix. State explicitly: (a) `autoDraft_v1` runs the coding model to propose lines for a READY bill (draft-only, S6-R4 authority), OR the sweep drafts only rule-backed bills (and READY-without-rule is not swept) — pick one; (b) rule matching is a deterministic DB lookup inside `_draft_entry_core` on `(client, resolved counterparty, rule_type)` returning the live rule, which is snapshotted (rule_id + content_hash) — the runtime passes nothing and the model never selects the rule. Align WA-L5's budget with whichever (a) is chosen.

### [HIGH][companion §2] `merge_counterparties` re-keys an incomplete child set and ignores three unique-constraint collisions — reintroducing the exact C-9 "rename/merge silently strands history" class the rebuild's first-class counterparty exists to kill.

Defect. Companion §2 says merge "re-keys children (`journal_lines.counterparty_id`, `coding_rules`, `aliases`, `sightings`) to the survivor in ONE transaction." Three gaps:

1. **`open_questions.counterparty_id` is not in the re-key set.** A vendor-scoped open question on the merged (now-retired) vendor is left pointing at a retired row. The lane fn's open-question-block predicate matches on the entry's *resolved* counterparty (the survivor), so a question that was about the merged vendor no longer demotes the survivor's bills or blocks their approval — the block silently evaporates on merge. (open_questions carries a nullable `counterparty_id`, companion §8.)
2. **`coding_rules` one-live-per-vendor unique collides.** The partial unique is "one LIVE rule per `(client_id, counterparty_id, rule_type)`" (companion §7). Merging two vendors that each have a live `vendor_account` rule re-keys both to the survivor → 23505. The merge has no conflict resolution (retire one? refuse? which account wins?).
3. **Alias unique collides.** Aliases are `unique (client_id, alias_normalized) among unretired` (companion §2). Merge "auto-creates a former-name alias from the merged vendor's name" **and** re-keys the merged vendor's existing aliases — either can collide with an alias the survivor already holds → 23505.

Failure scenario. A bookkeeper merges "TNB Berhad" into "Tenaga Nasional Berhad"; both have a live vendor→account rule and an overlapping alias. `merge_counterparties` throws 23505 mid-transaction (unhandled), the merge fails opaquely, and (worse, if the open_questions gap ships) a fraud/clarify question raised against the merged vendor stops gating the survivor. This is precisely audit finding **C-9** ("correcting a name mid-life silently splits history — old rules/evidence/open items keep the old canonical … and can block settlements"), which the rebuild promised to fix by making rename/merge "one governed mutation that atomically re-keys."

Exact text at fault. Companion §2: "re-keys children (`journal_lines.counterparty_id`, `coding_rules`, `aliases`, `sightings`) to the survivor in ONE transaction."

Proposed fix. Extend the re-key set to `open_questions.counterparty_id` (and audit every other table that will carry `counterparty_id`). Specify merge-time conflict resolution for the `coding_rules` one-live unique (e.g., retire the merged vendor's live rule, or refuse with CLR27 when they disagree) and for the alias unique (on-conflict-do-nothing / dedupe on the auto-alias and re-keyed aliases). Add a rig case for merging two rule-bearing, alias-overlapping vendors (companion §15 second-run ledger already runs merge twice, but not the collision case).

### [MEDIUM][§4] Batch-approve claims high-stakes rows are "re-refused at the DB," but `approve_entry` has no high-stakes block for agent-drafted entries — the exclusion is UI-only, so the contract's stated defense-in-depth does not exist.

Defect. §4: "high-stakes rows are structurally excluded from the selection model AND re-refused at the DB (approve_entry's existing per-item gates run unchanged)." But `approve_entry`'s high-stakes gate fires only when `is_high_stakes(entry) AND e.last_human_editor = c.actor AND eligible>=2` (0009:1663-1669). An AUTO-drafted bill has `maker_actor=agent`, `last_human_editor=NULL` (0009:1306 stamps it only for human drafts / editors), so the distinct-checker gate is vacuous — a single bookkeeper can approve a high-stakes agent draft with no attestation and no distinct checker. `approve_entry` never refuses on "high-stakes" per se; it refuses on maker==checker. So the "re-refused at the DB" backstop is illusory for exactly the rows batch-approve is drafting.

Failure scenario. A UI bug (or a payload crafted by a demoted-but-still-scoped session) slips a high-stakes AUTO draft into the batch; `approve_entry` accepts it with a single bookkeeper. WA-R7's "High-stakes rows excluded — always per-item" then rests entirely on the client-side selection filter, contrary to the contract's claim of double-enforcement.

Exact text at fault. §4: "high-stakes rows are structurally excluded from the selection model AND re-refused at the DB."

Proposed fix. Either add an explicit DB check (batch entry point, or an `approve_entry` argument/mode, refuses high-stakes) so the double-enforcement is real, or soften the contract to state honestly that high-stakes exclusion is enforced in the selection model only and the DB gate is maker/checker-conditional. Given WA-R7's "always per-item," a real DB backstop is the safer choice.

### [MEDIUM][companion §12] The taxonomy plan mislabels the "0009 pattern" and over-specifies a v3 version repoint that additive-insert makes unnecessary — introducing a routing-repoint hazard the design does not handle.

Defect. Companion §12: "Taxonomy v3 version rows … Repoint via a new `taxonomy_versions` row + `taxonomy_active` update in-migration (the 0009 v2 pattern)." But 0009 did **not** repoint. It inserted the new event_type + `trigger_taxonomy` rows into the **ACTIVE** version and asserted the coupled pair exists in the active version (0009:2978-2988, joining `taxonomy_active` and `trigger_taxonomy t on t.version=a.version`); S6 companion §1 states this explicitly ("inserted into the ACTIVE taxonomy's coverage set — **additive, no repoint**"; probe P5). A new version + `taxonomy_active` repoint is a *different, heavier* operation: it re-points routing for the whole event stream, which the router reads live, and needs the version-migration/HALT machinery — none of which §12 describes. It is also unnecessary: the new Wave-A event types have never been emitted, so their `trigger_taxonomy` rows (including the two `notification`-routed ones) can be additive-inserted into the active version with their desired decisions, keeping coverage whole exactly as 0009 did.

Failure scenario. The build lane follows "repoint via new version," performs a `taxonomy_active` flip mid-stream, and either (a) trips the router's version-migration guards it didn't account for, or (b) changes routing semantics for in-flight events — a class of bug the additive pattern was chosen to avoid. Or it discovers the "0009 v2 pattern" was additive and is left guessing which the companion actually meant.

Exact text at fault. Companion §12: "Repoint via a new `taxonomy_versions` row + `taxonomy_active` update in-migration (the 0009 v2 pattern)."

Proposed fix. Use the true 0009 pattern: additive-insert each new `event_type` + its `trigger_taxonomy` row (decision `ignore`, except `kb_rule.proposed` + `open_question.opened` → `notification`) into the **active** version, with a coupled-pair coverage assertion in the tail — no new version, no repoint. If a genuine new version is intended, specify the full repoint/HALT handling.

### [MEDIUM][companion §8] The shared `_open_question_blocks` predicate has the same invoker-vs-definer grant tension as `coding_lane`: `open_questions` is fn-fronted with no SELECT grant to the agent/human lanes, so an invoker `coding_lane` calling it cannot read the table.

Defect. Companion §8 wants "ONE shared predicate fn `_open_question_blocks` so the two sites [`approve_entry`, the lane fn] cannot drift." `approve_entry` is SECURITY DEFINER (runs as owner) so it can read `open_questions`; but the lane fn is (per companion §3) SECURITY INVOKER, and §13 states all new TABLES have "zero direct DML/SELECT grants — fn-fronted only." So an invoker `coding_lane` calling an invoker `_open_question_blocks` cannot SELECT `open_questions` (no grant, and RLS alone doesn't help without a SELECT privilege). If `_open_question_blocks` is instead SECURITY DEFINER, the invoker lane fn needs an EXECUTE grant on it and it must be firm-scoped + oracle-safe.

Failure scenario. Same 42501 / cross-firm-oracle fork as F2. The "cannot drift" goal is unmet at the type level.

Proposed fix. Make `_open_question_blocks` a firm-scoped SECURITY DEFINER granted to the app lanes with a null-`wake_firm` CLR03 guard, and have both the lane fn (F2's fix (b)) and `approve_entry` call it — or give `open_questions` a masked view/RLS SELECT and keep everything invoker. Resolve jointly with F2 (the lane fn's security mode is the pivot).

### [MEDIUM][companion §7] `rule_sightings` "unique per entry" cannot represent a multi-account (split) bill's several `vendor→account` sightings, and the sighting-writer mechanism is left as "build lane decides" for a load-bearing idempotency/ordering choice.

Defect. Companion §7: "`rule_sightings`: … `(client, counterparty, account, entry_id, document_id, sighted_at)` **unique per entry** — the ≥3 congruent threshold is computed over DISTINCT approved entries." A single approved bill can debit several expense accounts (the INF 7-page bundle is one entry with a 3-way split, S6 §9). "Unique per entry" records only one `(vendor→account)` sighting per entry, dropping the other accounts — so a genuinely recurring `(vendor→account_B)` pattern buried in split bills never reaches the ≥3 threshold, and the proposal engine under-learns. Separately, "Written by a spine consumer hook on `entry.approved` events (or in approve receipts path — build lane decides; either way DB-idempotent)" punts a mechanism that determines idempotency, ordering, and whether a *new consumer* is introduced (more concurrency surface) vs a body change to `approve_entry`.

Failure scenario. The build lane picks unique-per-entry (as written), and split-bill vendors never propose rules. Or it picks a new spine consumer and adds an unreviewed concurrency lane.

Proposed fix. Make the sighting grain `(client, counterparty, account, entry_id)` unique (allowing multiple accounts per entry) and compute the threshold as ≥3 DISTINCT entries per `(vendor, account)`. Decide the writer in the design (recommend: inside the `entry.approved` path or a named consumer, with the idempotency key stated), not "build lane decides."

### [MEDIUM][§10 / companion §13] The error map is not per-layer (S6 C-20 bar): the new native-constraint → CLR mappings are unenumerated, and the grants delta omits the autodraft wake lane and the CLR03 guard on the agent-granted lane fns.

Defect. S6 §12 shipped a per-layer table (SQLSTATE/constraint → CLR → runtime result → card), and 0009's header realizes it (0009:11-44). Wave A §10 lists only CLR26-29 as prose. The new uniques each need a mapping: `coding_rules` one-live (23505 → CLR27), `open_questions` scope/CHECK breaches, `client_egress_consents` one-live (23505 → CLR28), `counterparty_aliases` unique (23505 → CLR23 per §10's alias clause but not stated at the constraint level), and the composite-FK tenant breaches → not-found collapse. Companion §13's grants table also omits (a) the new `autodraft` wake_kind + allowlist rows (F3), (b) any statement that `coding_lane`/`list_coding_lanes`, being granted `clara_agent_ro`, carry the `CLR03`-on-null-`wake_firm` guard every other agent-readable 0009 fn has (e.g., 0009:2594-2598), and (c) `list_review_queue`'s exclusion of `clara_agent_ro` is stated but `review_queue_counts`'s lane is only implied.

Proposed fix. Add a per-layer error table naming every new native constraint; enumerate the autodraft wake_kind/allowlist and the CLR03 guard for the agent-granted lane fns in §13.

### [LOW][companion §3] "Admission recheck … no TOCTOU" is overstated — a non-locking lane read narrows but does not close the window; the real guard is the one-open-draft unique + double_coded no-op.

Defect. Companion §3: the sweep "re-evaluates it at execution time (admission recheck) so a lane computed at event time never authorizes a draft later (freshness law; no TOCTOU)," and §14 states "the lane fn takes NO locks (pure read)." A lock-free recheck cannot eliminate a race between the recheck and the subsequent `wake_draft_entry`.
