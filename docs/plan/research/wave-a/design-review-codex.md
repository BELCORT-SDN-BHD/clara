VERDICT: FLAWED

1. [SEVERITY CRITICAL] [companion §10; `0009_coding_floor.sql` claim path] — Consent revocation is not enforced at the last irreversible egress boundary. Scenario: a task becomes `running`, consent or the global switch is revoked, then WDK replays the memoized claim or `claim_document_processing_task` returns its existing `running/replayed` receipt before rechecking consent, allowing the vendor call after revocation. Fault text: “The egress claim gate … rewires” and “revocation mid-pipeline holds queued egress” cover only admission/queued tasks. Fix: recheck the global switch and live client consent immediately before every external call, including running/replayed paths; define cancellation semantics for in-flight calls and make the egress-dispatch lease itself consent-bound.

2. [SEVERITY CRITICAL] [contract §8; companion §10; Slice-6 contract §2] — A per-client consent lookup cannot govern the existing pre-filing OCR flow because the document has no client yet. Scenario: upload creates an unassigned document, but OCR—needed to produce matcher evidence—precedes human filing, so “the document’s client” is unknowable; the implementation must either leak under a guessed client or hold every genuinely unassigned document forever. Fault text: “egress for a client’s documents requires a live consent row” conflicts with the binding flow “OCR → matcher → HUMAN FILES the bill.” Fix: define a pre-egress client-binding act with structural attribution and consent proof, or keep unassigned documents held and provide a non-egress human filing path; state mixed-consent behavior for documents with multiple active filings.

3. [SEVERITY CRITICAL] [contract §11; companion §2] — The companion expressly permits a merge that the contract expressly forbids. Scenario: a bookkeeper supplies the “governed conflict override” and collapses two distinct registered legal entities, re-keying their historical postings and rules into one identity. Fault text: contract: “never merge across differing registrations”; companion: “registration conflict … unless `p_reason` is the governed conflict override.” Fix: delete the override; differing non-null registrations must always refuse, with correction handled through alias/rename adjudication that does not merge identities.

4. [SEVERITY CRITICAL] [companion §§2,14; PRD invariant 8; `0003_books_core.sql` line-immutability trigger] — The proposed merge cannot re-key approved `journal_lines` and preserve posted-line immutability. Scenario: the merge’s `UPDATE journal_lines SET counterparty_id=…` hits `t_jl_immutable`/CLR08; weakening that trigger would instead mutate posted history, while re-keying signed `coding_rules` and provenance `rule_sightings` would also alter governed historical meaning. Fault text: “re-keys children (`journal_lines.counterparty_id`, `coding_rules`, aliases, sightings)” and “retires the merged row,” although no retired/merged counterparty state is specified. Fix: add an immutable `merged_into`/identity-equivalence state and canonicalized reads rather than rewriting approved lines or sightings; retire and reissue conflicting live rules; enumerate every child, including vendor-scoped `open_questions`.

5. [SEVERITY CRITICAL] [companion §§3,6,9,13] — The proposed SECURITY INVOKER reads cannot access tables that have zero SELECT grants. Scenario: `coding_lane`, `list_coding_lanes`, `list_review_queue`, or counts touch `coding_rules`, aliases, questions, consent, or sweep state and fail 42501; calls from those INVOKER functions to revoked internal helpers such as `_resolve_counterparty` or `_invoice_fact_state` fail for the same reason. Fault text: the functions are “security INVOKER, RLS-scoped,” while “All new TABLES [have] zero direct … SELECT grants.” Fix: either grant the minimum SELECT surface under FORCE RLS, as 0009 does for existing INVOKER reads, or use tightly scoped DEFINER read functions with explicit firm/client checks and a non-BYPASSRLS owner; keep unscoped internal helpers ungranted.

6. [SEVERITY CRITICAL] [contract §3; companion §4; `0002`, `0006`, `0009` runtime schema] — Widening only the `agent_tasks.kind` CHECK does not create a viable `autodraft` task lane. Scenario: the first insert is rejected by `_tf_agent_task_insert` as an unknown kind; even if that is patched, `_tf_agent_task_update`, cancellation, reconciliation, settling, model snapshotting, status constraints, and health queries know only `chat_turn|wake`, while a synthetic chat session requires an active human author and the facts event carries neither client nor human author. Fault text: “`agent_tasks.kind` CHECK widens” and “autodraft tasks get their own synthetic session per bill.” Fix: specify the complete task parent/state machine, admission RPC, creator/actor semantics, durable model snapshot, cancellation/recovery paths, and all affected triggers/views/reconcilers—or define autodraft as a separate task table without a fictitious chat session.

7. [SEVERITY CRITICAL] [contract §§4,11; companion §14; `0009 approve_entry`] — Concurrent approvals can defeat the exact-duplicate bill control. Scenario: two filings for the same vendor/invoice number are approved concurrently, both plain `EXISTS` checks see no approved duplicate, and both commit; Wave A’s N-call batch path makes this schedule more reachable. Fault text: the design tests “a duplicate bill” but the lock order adds no lock or uniqueness point for `(client, counterparty, invoice_id)`. Fix: acquire a deterministic advisory/registry-row lock on that key before the duplicate check, or materialize an approved-bill key with a partial unique constraint; test both winning orders.

8. [SEVERITY CRITICAL] [contract §6; companion §§8,14] — CLR26 is check-then-act rather than a serialized approval gate. Scenario: `approve_entry` locks the filing, observes no blocking question, then a concurrent `open_question` inserts and commits before approval commits; the entry is approved despite a question that covers it. Fault text: “approve_entry gains the CLR26 check” and “reads open_questions AFTER taking its existing filing lock,” but the question writer is not required to take the same serialization lock. Fix: make question open/resolve/dismiss and approval share a documented client/filing/counterparty lock protocol, including client-scope questions, with both commit orders and deadlock bounds rig-proved.

9. [SEVERITY HIGH] [companion §§8,13; ADR-015] — `open_question` is incorrectly designed as one human-and-agent writer, recreating the proven-impossible SECURITY DEFINER lane-detection shape. Scenario: a shared function cannot distinguish the SET ROLE lane internally; without an explicit human floor a viewer can block an entire client, while granting it to a wake role broadens agent write authority. Fault text: “`open_question` (human + runtime lanes — … opening is not a gate change)” and the matrix grants the same writer to authenticated and “via allowlist.” Fix: acknowledge that opening is a gate mutation; use an ungranted core plus separate `open_question` and `wake_open_question` entry points, bookkeeper+ on the human path, exact scope pinning on the wake path, and explicit allowlist rows.

10. [SEVERITY HIGH] [contract §4; companion §14] — The DB cannot “re-refuse” high-stakes batch approvals when the batch invokes the unchanged general approval function. Scenario: a buggy or malicious batch client submits a high-stakes row through `approve_entry`; the DB lawfully approves it after ordinary maker/checker checks because it cannot know the call came from a batch. Fault text: “high-stakes rows are … re-refused at the DB” and “confirm fires N individual `approve_entry` calls.” Fix: add a narrowing `approve_routine_entry` entry point that refuses `is_high_stakes`, use it exclusively for batch calls, and retain `approve_entry` for per-item review.

11. [SEVERITY HIGH] [contract §2 WA-L1/§3; companion §§3,14] — Re-evaluating a pure lane read immediately before a separate write does not close lane TOCTOU. Scenario: after the READY read, consent is revoked, a question opens, a rule retires, a near-duplicate is approved, or the counterparty landscape changes; `_draft_entry_core` does not reassert the whole READY predicate and still creates the unattended draft. Fault text: “re-evaluates it at execution time … no TOCTOU.” Fix: introduce an audited autodraft composite writer that recomputes/locks every authorizing predicate and drafts in one transaction, or pass a DB-issued lane token that the writer validates under the same locks.

12. [SEVERITY HIGH] [companion §9; contract §7; current `revise_entry`] — `get_entry_diff` has no persisted line history from which to construct the promised revision walk. Scenario: `revise_entry` deletes and reinserts lines, while its audit/event payload carries only IDs/op_key; after the second revision, earlier legs are irretrievable. Fault text: “revision walk from persisted history (receipts/events + line snapshots),” but migration 0011 adds “no new state” for snapshots. Fix: add an append-only revision table containing entry header, complete ordered line snapshot, actor, reason, rule snapshot, evidence references, and revision token in the same transaction as every revise/facts rotation.

13. [SEVERITY HIGH] [contract §3 WA-R5; companion §5] — Sweep-run receipts cannot be complete or atomic under the proposed asynchronous topology. Scenario: the consumer enqueues several workflows and commits its checkpoint; one draft commits and the process dies before its item/aggregate settle, or a user acknowledges the run before late items arrive, leaving an acknowledged batch with missing outcomes/counts. Fault text: items are “written … in the drafting transaction’s settle path,” although companion §14 says execution occurs in the workflow, never the consumer transaction. Fix: pre-create a run with expected items and lifecycle state, pass `run_id` into an atomic draft-and-item writer, enforce unique `(run_id, filing_id)`, reconcile committed drafts after crashes, finalize totals once, and permit acknowledgement only after finalization.

14. [SEVERITY HIGH] [contract WA-L5; companion §5] — The sweep budget check is a raceable observation, not a reservation, so it cannot reserve interactive headroom. Scenario: multiple autodraft workflows all observe spend below 60%, concurrently incur model tokens, and collectively cross both the share and daily limit before any settle updates usage. Fault text: “before each draft the workflow checks metered daily spend” and refuses only when spend is already at the threshold. Fix: reserve worst-case sweep tokens atomically under the existing per-firm budget advisory lock, settle/refund from durable checkpoints, cap concurrent sweep runs, and specify missing-limit rows, NULL limits, UTC rollover, and human one-click treatment.

15. [SEVERITY HIGH] [contract §3.3/§2 NEEDS REVIEW; companion §§4,15] — No durable admission protocol prevents the event consumer, catch-up pass, and one-click action from creating competing tasks for one filing. Scenario: event and catch-up each run a model; their same `autodraft:<filing>` key carries different generated arguments and produces CLR10 request-hash mismatch, while the one-open-draft index prevents duplicate rows only after duplicate token spend. The same design also gives no storage for “failed twice” across catch-up restarts and names no human RPC for one-click drafting. Fault text: “one bill per task BY CONSTRUCTION,” “attempt cap … twice,” and “same `autoDraft_v1` path” for one-click. Fix: add a filing-keyed active-attempt registry/unique admission writer, durable attempt counters and park state, and distinct origins/op-key namespaces and lane/budget rules for sweep versus human one-click.

16. [SEVERITY HIGH] [companion §7] — The coding-rule schema references a nonexistent account key. Scenario: migration authors attempt the specified `account_id FK`, but `coa_accounts` has no `id`; its key is `(client_id, account_code)`, so the DDL cannot be implemented without an unapproved identity migration. Fault text: “`account_id FK [must exist + postable]`.” Fix: use `(client_id, account_code)` with a composite FK and firm/client congruence, or explicitly design and migrate a stable account UUID across every existing caller.

17. [SEVERITY HIGH] [contract §6; companion §7] — The rule-application and C-14 snapshot path has no input or deterministic binding that proves a rule actually produced the proposed account. Scenario: a workflow chose account X before a rule was signed, but `_draft_entry_core` sees the newly live rule and labels it “per your rule”; conversely a retired rule used earlier leaves no snapshot because “runtime passes nothing.” Fault text: “runtime passes nothing — `_draft_entry_core` snapshots … when the proposal cites a rule.” Fix: resolve and lock the live rule in the draft transaction, prove the selected line/account matches it, and persist a full immutable fired snapshot—not merely id/hash—in a decision table linked to the entry revision.
