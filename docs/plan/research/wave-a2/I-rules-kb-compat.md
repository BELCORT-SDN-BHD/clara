## (1) What the gist actually says

`https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2` ("LLM Wiki v2") proposes a generic LLM-agent knowledge-management pattern — it is NOT accounting-domain-specific and never discusses posting/money authority. Structure: a three-layer pattern (raw sources → wiki pages → schema), with `index.md` as a human-readable catalog (viable to ~100-200 pages, replaced by hybrid search at scale) and a `CLAUDE.md`/`AGENTS.md`-style **schema document** that the author calls "the most important file" — it encodes *what* to ingest, *when* to create pages, *what* quality standards apply, and *how* to handle contradictions.

Update discipline — **"automation with human curation"**:
> "The human should still be in the loop for curation and direction. But the bookkeeping... should be fully automated."

Automatic hooks: on new source → auto-ingest/extract/update graph; on session end → compress into observations; on schedule → periodic lint/consolidation/retention decay; on memory write → check contradictions, trigger supersession. Humans co-evolve the schema; the LLM executes against it.

Philosophy: knowledge has a *lifecycle*, not equal validity forever — confidence scores (source count, recency, contradiction status) decay over time and strengthen with reinforcement; **supersession, never deletion** (old claims marked stale, linked to replacements, archived to "bottom drawer," version preserved); full audit trail (timestamp, what changed, why). Explicit don'ts: don't auto-write without quality gates or human override; don't treat numeric confidence as final truth over the evidence chain. "Crystallization" = distilling a completed chain of work into a structured, reusable digest — "explorations become sources."

**Overall: COMPATIBLE**, with one structural condition that must be held explicitly rather than assumed.

## (3) Self-growth design: propose → human-sign lifecycle extended to auto-POST authority

The existing as-built lifecycle (cited in full in `C-sweep-rules-autopost-law.md` §1.3-1.4) is the base to extend:
`rule_sightings` (append-only, per vendor→account→entry, `0011:843`) → 3 congruent approved-unreversed sightings auto-opens a `proposed` `coding_rules` row + a non-blocking `rule_proposal` open_question (`0011:3165-3192`; made non-blocking by `0012:88-108`, WA-R9 "a proposal is a suggestion, not a stop") → human calls `sign_coding_rule` (`0011:2144`) → `status='live'`, `signed_by`/`signed_at` stamped, `ck_coding_rules_terminal` enforces both NOT NULL, one-live-per-(client,counterparty,rule_type) uniqueness enforced → `pinned` rules refuse retirement without a matching conflict question (WA-R9, `0011:2220-2227`).

**Recommended lifecycle for POSTING-tier rules (higher ceremony than account-choice):**

1. **A distinct rule tier, not a reuse of `vendor_account`.** A rule that grants standing auto-POST authority is categorically higher-stakes than one that only resolves which account to debit — the signature *is* the authority itself (per the owner's framing), not advisory metadata on a draft. Give it its own `rule_type` (e.g. `vendor_autopost`) or an explicit tier column, so the CHECK-constrained bound fields (amount cap, frequency window, expiry) are structurally specific to this power tier and cannot be satisfied by signing a lesser-purpose rule. This is the same fork the C-brief already left open (its open question 8, `C-sweep-rules-autopost-law.md:172`) — worth resolving here as "yes, a new tier," given the ceremony delta.
2. **A higher sign-rank than the current bookkeeper+ floor.** `sign_coding_rule` today requires only bookkeeper+ (`_human_ctx(role_rank('bookkeeper'))`-class floor per §1.3). Signing away POSTING authority is closer to "firm administration" than "day-to-day bookkeeping" — PRD's own RBAC ladder already places "approve KB" at **admin** (`PRD.md:43`: "admin — firm administration (approve KB, invite/manage members, firm settings, create clients)"). Recommend requiring admin+ specifically to sign (not just author-propose) a posting-tier rule.
3. **Widening a cap or extending expiry = a new signature, never an edit — enforced structurally.** Mirror the existing immutability pattern (posted journal lines are immutable via trigger, ARCHITECTURE §3.3): make a posting-tier rule's bound fields (`amount_cap_cents`, `frequency_window`, `expires_at`) immutable once `status='live'` (a trigger or CHECK refusing UPDATE on those columns for live rows), symmetric to how `pinned` retirement already requires a fresh conflict question rather than a silent status flip (`0011:2220-2227`). Any widening must retire the old signed row and insert a brand-new row with its own `content_hash` and a fresh signature — an append-only genealogy, the same shape `rule_decisions.snapshot` already uses to join an entry-revision to the exact rule state that authorized it (`0011:490-493`, `864-884`).
4. **Decay/expiry as a hard DB bound, not a fuzzy confidence score.** The gist's "confidence decays with time" is a soft heuristic; Clara's own doctrine (ARCHITECTURE §0: hard constraints, not model discipline) argues for a crisp, DB-checked `expires_at NOT NULL` instead — which the owner's own framing already names ("amount cap, frequency, expiry"). Add a scheduled sweep (mirroring the wiki Layer-1 "lint" cadence, ARCHITECTURE §5) that flips expired posting-tier rules to a terminal state and raises a notice through the existing trigger-taxonomy/exception-inbox mechanism (ARCHITECTURE §2.4, PRD item 18) rather than letting them lapse silently. A rule signed but rarely/never triggered should similarly surface a renew-or-retire nudge — never auto-renew.
5. **Sighting-evidence attached to the proposal.** Extend the existing `rule_sightings`-threshold precedent: a posting-tier proposal (new rule, or a widening "re-proposal" per point 3) should cite the specific sighting rows/count/date-range that justify it, the same way `rule_decisions.snapshot` already carries a structured join of entry-revision to rule-state — giving the admin signer an evidence trail instead of a bare ask.

**Risks + structural mitigations:**
- **Proposal fatigue** — gate posting-tier proposals behind a higher evidence bar than the existing 3-sighting floor (e.g., a larger N and/or a minimum observation window), since the ceremony cost is also higher.
- **Bound-creep via repeated small widenings** — since point 3 forces every widening through a brand-new signature, add a structural rate-limit at sign time (e.g., a new cap may not exceed some multiple of the prior cap without a higher rank, functioning as a circuit-breaker on how fast authority can expand).
- **The agent gaming its own sightings** — already structurally resisted today: `rule_sightings` are written as a side effect of `approve_entry`, a human-invoked writer (the agent cannot approve — ADR-002/003/015, `C-sweep-rules-autopost-law.md:121-126`). Any posting-tier evidence mechanism must preserve this: evidence must derive from human-approved entry history only, never from agent-drafted-but-unapproved entries or the agent's own running commentary. Worth stating explicitly rather than assuming it's inherited, since a faster (draft-time) signal would be tempting and weaker.
- **High-stakes bypass** — independent of rule tier or signature ceremony, `is_high_stakes` must remain a hard, non-bypassable exclusion for any auto-post executor (T3 in the C-brief, `C-sweep-rules-autopost-law.md:131-132`); this is not a KB-design question but the design must not let a signed posting-tier rule become a backdoor around it.

## (4) Open questions only the owner can answer

1. New `rule_type`/tier for posting authority, or a flag on the existing `vendor_account` type? (mirrors C-brief open question 8)
2. Sign-rank for a posting-tier rule: keep bookkeeper+ (current `sign_coding_rule` floor) or raise to admin+ (matches PRD's "admin approves KB")?
3. Actual default bounds — amount-cap ceiling, frequency window, expiry duration — are business-policy calls only the owner can set.
4. On expiry or non-use: hard auto-expire, or notify-and-wait-for-a-human-decision? (silent lapse vs. required renewal signature)
5. Should Wave B's Layer-1 wiki pages be allowed to *cite* a live posting-tier rule as informational cross-reference (inert), and if so, is that worth specifying now so Wave B doesn't have to relitigate the "wiki never decides" boundary?
6. Whether to fold the "no auto-approve ever" wording fix (open question 3 in the C-brief) into the same ratifying ADR as this KB-compatibility ruling, since both surface in the same ceremony.
