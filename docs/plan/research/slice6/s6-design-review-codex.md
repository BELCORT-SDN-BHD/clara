2. **CRITICAL — `approve_entry` v3 restores the filing/entry AB-BA deadlock; the token rotation itself is not the defect**

   - **Sections:** contract §5; companion §3 and §10 (“approve order”).
   - **Evidence:** the as-built approval deliberately reads identity, locks the active filing, and only then locks the entry (`packages/db/migrations/0007_document_pipeline.sql:1289-1299`). The correction writer declares the global order “filings ASC → originals ASC” and implements it (`packages/db/migrations/0007_document_pipeline.sql:2533-2553`). The line immutability trigger permits draft-line changes and the AFTER trigger rotates the draft parent's token (`packages/db/migrations/0003_books_core.sql:311-347,468-473`; live immutability replacement at `packages/db/migrations/0007_document_pipeline.sql:1058-1075`). The prior Slice-3 fix documents why consistent original/slot ordering is load-bearing (`packages/db/migrations/0005_event_spine.sql:846-851`).
   - **Finding:** companion §3 step 1 changes approval to `entry FOR UPDATE`, then step 3 locks/re-affirms the filing. A concurrent correction can hold the filing and wait for that entry while approval holds the entry and waits for the filing. That is the exact lock inversion the as-built body avoided. **VERIFY-ON-RIG:** force the schedule approve(entry lock) ↔ correction(filing lock), including correction adoption of a pending reversal.

     The claimed mid-transaction token rotation in step 5 is otherwise sound: after the expected token is checked under the entry row lock, a governed revise/correction cannot interleave; the line UPDATE sees a draft parent; its AFTER trigger's parent UPDATE is re-entrant in the same transaction; and an abort rolls the new token back.    - **Fix direction:** retain the 0007 sequence: unlocked identity read → active-filing lock/re-affirmation → entry `FOR UPDATE` → status/token check → reversal-original lock → vendor resolution/line stamp/floor → status flip. Preserve original-before-slot ordering. Add forced-schedule rigs for approve vs correction, approve vs revise, approve of an adopted reversal vs `reverse_entry`, and abort after line stamping.

   - **Sections:** contract §0 S6-R7 and §5; companion §2 (“constraint trigger”) and §3 steps 5–7.

A reversed entry on a retired filing must not block the destination task. Add shared-document A+B, correction A→B, withdrawn draft, reversed approved, and concurrent same-filing draft rigs.

16. **CRITICAL — the reviewed RPR chart cannot be loaded through the current schema**

   - **Sections:** contract §0 S6-R9 and §9; companion §2 (`account_class`) and §9(6).
   - **Evidence:** `coa_accounts.account_code` accepts only 4–8 digits and account type only `asset|liability|equity|income|expense` (`packages/db/migrations/0003_books_core.sql:47-56`). Every RPR code contains a hyphen, and several contain letters (for example `100-000`, `900-A01`); the brief also uses extraction classification `expense_cogs` (`.tmp/slice6-briefs/6-rpr-corpus.md:28-48`).
   - **Finding:** the operator script cannot insert even one reviewed RPR code through `upsert_account`; 0009 does not propose altering the code CHECK. A literal pass-through of the reviewed CSV classification also fails the account-type CHECK. This makes the live onboarding and every context-pack/account lookup promised by Gate 3 impossible, independently of runtime code.
   - **Fix direction:** 0009 must deliberately migrate the account-code domain to a bounded canonical format that covers the real chart (with tests against every reviewed code and hostile inputs), and the reviewed CSV must contain an explicit mapping from extraction classification to Clara's five account types. Preserve the exact display code used by entries; do not silently renumber. Run the deploy-onto-existing drill and all FK/context-pack/coverage tests after altering the CHECK.

17. **HIGH — onboarding would silently convert a reconciliation plug into a postable AP account and its claimed idempotency does not cover firm creation**

   - **Sections:** contract §0 S6-R7/R9 and §9; companion §2 and §9(6).
   - **Evidence:** the RPR brief says `400-000 TRADE CREDITORS` appears only in a reconciliation footer, does not foot to visible postings, and must be treated as a non-postable control plug (`.tmp/slice6-briefs/6-rpr-corpus.md:69-79,272-279`). `create_firm` consumes an admission and refuses an actor already in an active firm; it does not reserve an op receipt despite accepting `p_op_key` (`packages/db/migrations/0004_governed_fns.sql:318-341`). As-built clients have no FY model and retention records the conservative `missing-fy-conservative-0007` state (`docs/plan/slice5-as-built-amendments.md:22-25`).
   - **Finding:** declaring 400-000 postable/payable is not “loading the real reviewed chart”; it changes the semantics of live books exactly where the source says not to post. A new rounding account is also an augmentation, not extracted chart truth. Separately, deterministic op keys cannot make `create_firm` idempotent because that writer has no `_reserve_op`; a rerun against BELCORT can consume/fail admission or collide with existing membership. Confirming an FYE cannot alter retention in Slice 6 because no FY field exists.
   - **Fix direction:** stop before live onboarding until the owner approves an explicit additive Clara AP account (or an authoritative source establishes 400-000 as postable); label all augmentations separately from imported RPR rows and checksum the exact plan. The script must discover/reuse the existing BELCORT firm and RPR client, call create only when absent, persist a manifest/checksum, and verify every receipt rather than assuming op-key magic. Keep retention honestly conservative; do not claim FYE anchoring until the FY model exists.

18. **HIGH — the third-pool design omits several binding P4/credential details and contradicts the safe-login precedent**

   - **Sections:** contract §5; companion §9(1).
   - **Evidence:** the current migration creates login identities as `NOLOGIN` safe defaults and enables LOGIN/password out of band (`packages/db/migrations/0006_runtime_core.sql:51-79`). Production boot asserts exactly the two current DSNs (`packages/runtime/lib/pools.mjs:65-81`), the pool budget is explicitly 5/5 + listeners (`packages/runtime/lib/pools.mjs:25-27,41-44`), checkout always ROLLBACKs and RESET ALL and destroys only on connection/cleanup failure (`packages/runtime/lib/pools.mjs:152-181`), and shutdown closes only two pools (`packages/runtime/lib/pools.mjs:272-279`). The task loader omits the initiating actor (`packages/runtime/workflows/chatTurn.impl.ts:145-157`).
   - **Finding:** Shape 1 itself does not widen book authority: a login with exactly one `clara_wake_interactive` membership can reach the existing draft-only allowlisted entry and still cannot approve. COMMIT mode and `globalThis` injection are also compatible with the secret law if mint+bind+write happen inside one step. But companion §9 says 0009 “creates the LOGIN via the 0006 pattern,” while that pattern explicitly creates NOLOGIN. It also leaves the third DSN out of fail-closed boot, the connection budget, lazy pool lifecycle, shutdown, and actor plumbing. “P4 destroy-on-error” is imprecise: healthy SQL errors are rolled back/reset and reused; connection or cleanup errors destroy. Without `created_by`, the promised OBO mint cannot be implemented.
   - **Fix direction:** create `clara_wake_write_login NOLOGIN`, grant exactly one membership with SET true/INHERIT false, and enable/password it only in the operator ceremony. Add `CLARA_WRITE_DATABASE_URL` to production boot assertions; define a small max within the Supavisor budget; include the pool in teardown/health tests. Return `created_by` from the v2 task loader, mint OBO per execution attempt, BEGIN→parameterized local secret→SET ROLE→write→COMMIT, and let shared cleanup ROLLBACK/RESET. Test demotion, COMMIT-response loss, connection failure, and secret non-leak on the next checkout.

19. **HIGH — the design does not define how a tool result becomes exactly one top-level `je_review`, and it ignores the per-segment tool cap**

   - **Sections:** contract §3 (“Result part” and “Wire”), §10.2, and §14/N-F16; companion §9(2,4).
   - **Evidence:** current `toTypedParts` maps every non-clarify tool result to `{type:'tool_result', output:...}`; it never promotes an object inside `output` to a new part (`packages/runtime/workflows/chatTurn.prompt.ts:67-104`). The live reducer does the same (`apps/dashboard/app/chat/parts.tsx:25-89`), and unknown parts silently disappear (`.tmp/slice6-briefs/5-dashboard-parts.md:39-59,269-275`). The model segment stops after eight steps, independently of `MAX_SEGMENTS=12` (`packages/runtime/workflows/chatTurn.impl.ts:197-213`; workflow loop at `packages/runtime/workflows/chatTurn.v1.ts:37,71-79`).
   - **Finding:** returning `{type:'je_review',...}` from tool execution produces a nested tool-result today, not a top-level durable card. The contract says both `applyChunk` and persisted rendering gain branches, but §14 records N-F16 as saying a live-chunk branch is not required. Lanes can therefore implement promotion in the executor, in `toTypedParts`, in the dashboard, in multiple places (duplicates), or nowhere (invisible card). Also, a coding request can consume the eight-step segment cap on perception/context/tool work and end without clarify or card; `MAX_SEGMENTS=12` does not help when no clarify hook opens.
   - **Fix direction:** specify one canonical runtime transformation: a successful `draft_journal_entry` tool result emits its ordinary `tool_result` plus exactly one keyed `je_review(entry_id)` durable part, with deterministic de-duplication on replay. Specify whether live UI promotes the streamed result or intentionally waits for the authoritative terminal message, and make §3/§14 agree. Add a coding-intent terminal invariant: card, typed clarify, or typed refusal—never silent completion at `stepCountIs(8)`. Test live, persisted hydration, replay, and cap exhaustion.

20. **MEDIUM — the error map is incomplete at the SQL/runtime boundary and contains an internal currency contradiction**

   - **Sections:** contract §4 and §12; companion §2–§7 and §10.
   - **Evidence:** invalid wake credentials raise CLR03 (`packages/db/migrations/0005_event_spine.sql:1100-1104`); human authentication failures raise CLR04 (`packages/db/migrations/0004_governed_fns.sql:322-335`); immutability triggers raise CLR08 (`packages/db/migrations/0007_document_pipeline.sql:1021-1055`); processing transitions/limits use CLR16/CLR18 (`packages/db/migrations/0007_document_pipeline.sql:2100-2126`).    - **Finding:** §12's “every S6 writer failure” list omits CLR03/04/08 and does not say which native `23503/23505/23514/42501` paths are prevalidated or translated. The one-open-draft index only maps to CLR21 if `_draft_entry_core` catches the precise unique constraint; malformed proposal/account-class CHECKs and task/result FKs otherwise escape the map. `write-tool called without a client-bound session` is a runtime refusal, not a DB writer error, but is mixed into the same CLR bucket. §4 allows non-MYR to fall to Tier B while §12 says non-MYR is a CLR21 refusal.
   - **Fix direction:** publish a per-layer table: DB SQLSTATE and exact constraint/writer source → stable CLR code → runtime tool result → HTTP/card behavior. Name every caught constraint. Keep expected 42501 for structural agent-approve denial distinct from business refusal. Resolve non-MYR to one outcome (for this currency-less ledger: clarify/refuse), and add negative tests that assert no unmapped native SQLSTATE reaches the user.
