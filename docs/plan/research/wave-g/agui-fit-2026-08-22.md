# AG-UI 能不能接进 Clara？—— 给业主的研判

*研究车道（只读，未改动 repo 任何文件）· 日期 2026-08-22 · 所有外部结论都在下面标了 URL + 访问日期 + 原文引用（house law 75）。*

---

## 0. 一句话结论（先看这个）

**AG-UI 是一条"传输管道 + 前端事件约定"，不是会计权威。它能标准化的东西，Clara 现在已经用自己的方式全部做了，而且做得比它严。**

我的建议是 **(B)：不整体采用 AG-UI 作为传输层，但把它的三个具体想法偷过来**，放进 Wave G 的 OS surface 里做。理由有三个硬的：

1. **它给 Vercel AI SDK 的适配器根本没发布到 npm，而且只支持 `ai@4`** —— 我们跑的是 `ai@7.0.31`（`packages/runtime/package.json:18`），差三个大版本。等于要我们自己从零写并长期自己养一个协议适配层。
2. **它的 human-in-the-loop 模型和我们的相反**：AG-UI 的中断是"这一轮 run 结束掉，前端再开一轮新 run 带着答案回来"；Clara 的 clarify 是"workflow 挂在 hook 上零算力停住，人从**另一条通道**（Supabase RPC）回答，run 原地醒过来"。硬接会出现**第二道审批门**，这是我们明令禁止的（一个动作只能有一道门）。
3. **它的招牌功能 generative UI（模型决定长什么样、模型把参数流进组件里）正是我们 PRD §6 第 1 条和 fail-closed card catalog 明确要挡掉的东西**。我们可以用它，但必须把它阉割到只剩"模型选卡片 ID"，那时候剩下的价值已经很小了。

不采用 ≠ 白研究。它的**事件分类法**、**shared state 的 JSON Patch 思路**、**前端定义工具（frontend-defined tools）**这三点，是真能改善你问的"提问、审计、人机协作"的，而且可以在我们现有的 SSE 上直接做，不用引入任何新依赖。

## 1. AG-UI 到底是什么 vs Clara 已经有什么

### 1.1 AG-UI 是什么（外部事实）

> "An open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications."
> —— <https://docs.ag-ui.com/introduction>（访问 2026-08-22）

它的出身：

> "AG-UI originated from CopilotKit's partnership with LangChain and CrewAI. CopilotKit now functions as a first-party client and infrastructure provider."
> —— 同上（访问 2026-08-22）

许可证 MIT，协议标准化的是"约 16 种标准事件类型"：

> "Agent backends emitting events compatible with approximately 16 standard event types"
> —— <https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/README.md>（访问 2026-08-22）

完整事件枚举（TypeScript SDK 源码）：

```typescript
export enum EventType {
  TEXT_MESSAGE_START, TEXT_MESSAGE_CONTENT, TEXT_MESSAGE_END, TEXT_MESSAGE_CHUNK,
  TOOL_CALL_START, TOOL_CALL_ARGS, TOOL_CALL_END, TOOL_CALL_CHUNK, TOOL_CALL_RESULT,
  STATE_SNAPSHOT, STATE_DELTA, MESSAGES_SNAPSHOT,
  ACTIVITY_SNAPSHOT, ACTIVITY_DELTA,
  RAW, CUSTOM,
  RUN_STARTED, RUN_FINISHED, RUN_ERROR, STEP_STARTED, STEP_FINISHED,
  REASONING_START, REASONING_MESSAGE_START, REASONING_MESSAGE_CONTENT,
  REASONING_MESSAGE_END, REASONING_MESSAGE_CHUNK, REASONING_END,
  REASONING_ENCRYPTED_VALUE,
  // THINKING_* 系列已 DEPRECATED，1.0.0 移除
}
```
—— <https://github.com/ag-ui-protocol/ag-ui/blob/main/sdks/typescript/packages/core/src/events.ts>（经 Context7 取得，访问 2026-08-22）

编码方式就是**普通 SSE**：

> `encodeSSE(event: BaseEvent): string { return \`data: ${JSON.stringify(event)}\n\n\`; }`，`getContentType()` 返回 `"text/event-stream"` 或 protobuf 的 `AGUI_MEDIA_TYPE`
> —— <https://github.com/ag-ui-protocol/ag-ui/blob/main/sdks/typescript/packages/encoder/src/encoder.ts>（经 Context7，访问 2026-08-22）

**注意这一点很重要：AG-UI 的"传输"就是 SSE over HTTP，跟我们现在用的一模一样。它给的不是新管道，是管道里的一套 JSON 事件命名约定。**

### 1.2 Clara 现在有什么（repo 事实）

| 层 | Clara 的实现 | 位置 |
|---|---|---|
| 传输 | 自己写的 SSE reader（`fetch` + `ReadableStream` 手工切 `\n\n` 帧，因为浏览器 `EventSource` 送不了 `Authorization` header） | `apps/dashboard/app/chat/api.ts:178` |
| 服务端帧 | 只有 4 种：`chunk`（AI SDK fullStream 原始块）、`message`（终局持久化 parts）、`done`、`detached` | `packages/runtime/src/streamRoute.ts:55-56, 75-76, 117, 148, 160` |
| 消息模型 | 持久化的 `ClaraPart[]` 联合类型，**21 个成员**（text / tool_call / clarify / je_review / refusal / doc_review / diff / 各种 receipt / …） | `apps/dashboard/app/shared/parts.ts:144` |
| 渲染注册表 | `PART_CATALOG` —— 每个 part type 必须有渲染分支 + 至少一个 fixture；编译期 `_covered` 断言强制穷尽 | `apps/dashboard/app/chat/partCatalog.ts:25, 167` |
| Fail-closed | 未知 part type **不是**静默丢弃，而是显式渲染 `Unsupported part: <type>` 芯片 | `apps/dashboard/app/chat/parts.tsx:134, 274-275` |
| HITL | workflow 用 WDK `createHook` 挂起（零算力停住，可停数天），人的回答走 **Supabase RPC `answer_interruption`**，**不经过 runtime** | `packages/runtime/workflows/chatTurn.v12.ts:118, 121` · `apps/dashboard/app/chat/api.ts:321` |
| 治理法 | 两条车道严格分离："Governance NEVER transits the runtime (§4.2)" | `apps/dashboard/app/chat/api.ts:8` |
| 前端形态 | **Next.js 静态导出**（`output: "export"`），跑在 Cloudflare Pages，`/api/*` 由一个 Pages Function 代理 —— **前端没有服务器** | `apps/dashboard/next.config.mjs:3, 14` |
| 前端依赖 | `next` + `react` + `pdfjs-dist`，**没有装 `ai` 也没有 `@ai-sdk/react`** —— 我们没用 AI SDK UI，是手搓的 | `apps/dashboard/package.json` |

### 1.3 逐项对照表

| AG-UI 提供 | Clara 现状 | 判定 |
|---|---|---|
| `TEXT_MESSAGE_*` 文本流事件 | `chunk` 帧里的 `text-delta`，由 `applyChunk` 折进 `text` part（`parts.tsx:41`） | **完全重叠**，只是命名不同 |
| `TOOL_CALL_START/ARGS/END/RESULT` | `tool_call` / `tool_result` / `tool_error` 三个 part type + `toolStatuses()` 芯片状态机（`parts.tsx:138`） | **完全重叠**，我们的还多一个"resolver 类型只解析状态、自己不渲染"的显式声明（`STATUS_RESOLVER_TYPES`） |
| `RUN_STARTED / RUN_FINISHED / RUN_ERROR` | `agent_tasks.status`（queued/running/awaiting_input/completed/failed/cancelled/expired）+ `done` 帧 | **完全重叠**，而且我们的是**持久化在 DB 里的**，不是只活在流里 |
| `STEP_STARTED / STEP_FINISHED` | WDK `'use step'` 的 checkpoint（`checkpointStep`，`chatTurn.v12.ts:88`） | 重叠，但我们的 step 是**耐久执行单元**，不只是给 UI 看的进度条 |
| `STATE_SNAPSHOT / STATE_DELTA`（JSON Patch RFC 6902 增量同步一份 agent state） | **无对应物** —— 我们刻意没有"共享可变状态"。每张卡片拿到的只有**标识符**，靠自己 hydrate 从 DB 读权威值（`shared/parts.ts:38-40` 注释："identifiers only; the card re-derives authoritative state via get_draft_review on hydrate, never trusting the persisted snapshot"） | **真差异 —— 而且是我们故意的** |
| `MESSAGES_SNAPSHOT` | `getMessages()` 全量读 `chat_messages`（`api.ts:135`） | 重叠 |
| 前端定义工具（frontend-defined tools） | **无** —— 工具全在 runtime 侧、在 frozen closure 里（`chatTurn.v12.tools.ts`） | **真差异**（见 §2c） |
| Generative UI（模型选/生成组件） | **明令禁止的方向**。设计法是 "text-to-hydration, never text-to-code"（`docs/design/PRODUCT_DESIGN.md`） | **正面冲突** |
| 中断 / HITL | 有，但机制完全相反（见 §2c） | **正面冲突** |
| `RAW` / `CUSTOM` 逃生口 | 无对应物（我们的 part 联合是封闭的，加一个类型要过编译期断言 + parity test） | 差异，但我们的封闭性是**特性不是缺陷** |
| `REASONING_*` 思维链事件 | 无 —— 我们从不把模型的 reasoning 流给用户看 | 差异，且不打算要 |

**一句话总结这张表：AG-UI 里跟 Clara 重叠的部分（文本、工具、生命周期），我们已经有了且更严；不重叠的部分（shared state、generative UI、frontend tools、reasoning），要么和我们的法冲突，要么需要单独判断。**

## 2. 契合度分析

### 2a. 能不能只在边缘加个 adapter，不动 frozen workflow？

**技术上：能。法律上：不用改 workflow。但成本远比想象大。**

好消息先说。Clara 的 workflow 冻结律（`.claude/rules/runtime-workflows.md`：*"A deployed workflow body is immutable... a behavioural change is never an edit"*）只管 **workflow body 及其 import closure**。而 SSE 的成帧发生在 `packages/runtime/src/streamRoute.ts` —— 这是 **Express route，不是 frozen 文件**。所以理论上可以：

```
chatTurn_v12 (FROZEN, 不动)
      ↓ 写 engine readable
streamRoute.ts (非冻结) ── 在这里把 chunk/message/done 翻译成 AG-UI 事件 ──▶ 浏览器
```

`chatTurn.v12.ts` 一个字都不用改。这条路是成立的。

**坏消息 —— 三个硬成本：**

**(1) 官方 AI SDK 适配器不存在。** 这是最要命的一条：

- npm 上 `@ag-ui/vercel-ai-sdk` **返回 HTTP 404** —— <https://registry.npmjs.org/@ag-ui%2Fvercel-ai-sdk>（访问 2026-08-22）
- repo 里那份的 `package.json` 写着：`"name": "@ag-ui/vercel-ai-sdk"`, `"version": "0.0.2"`, 依赖 `"ai": "^4.3.16"`, `"zod": "^3.22.4"` —— <https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/integrations/vercel-ai-sdk/typescript/package.json>（访问 2026-08-22）
- 官方 issue 自己承认：*"the existing integration targets an older version of vercel ai sdk (v4, latest version is v6)"*，标签 Roadmap / In review —— <https://github.com/ag-ui-protocol/ag-ui/issues/933>（访问 2026-08-22）
- AG-UI 的官方 integrations 页列了 LangChain、Microsoft Agent Framework、Google ADK、AWS Strands、Mastra、Pydantic AI、Agno、LlamaIndex、CrewAI、AG2、Langroid、Claude Agent SDK …… **Vercel AI SDK 完全没有出现在这个列表上** —— <https://docs.ag-ui.com/integrations>（访问 2026-08-22）

对照我们：`ai` 的 npm latest 是 **7.0.77**（<https://registry.npmjs.org/ai/latest>，访问 2026-08-22），我们锁 **7.0.31**（`packages/runtime/package.json:18`），zod 锁 **4.4.3**（同文件 `:26`）。也就是说那个未发布的适配器落后我们 **3 个 `ai` 大版本 + 1 个 zod 大版本**。

**结论：这不是"装个包"，是"我们自己从零写一个协议翻译层，并且永远自己维护它"。**

**(2) 前端要重写，而且我们没有服务器。** CopilotKit 的官方接法是在 Next.js 里开一个 route handler 跑 `CopilotRuntime`：

```typescript
const runtime = new CopilotRuntime({ agents: {...}, runner: new InMemoryAgentRunner() });
const app = createCopilotHonoHandler({ runtime, basePath: "/api/copilotkit" });
export const GET = handle(app); export const POST = handle(app);
```
—— <https://github.com/copilotkit/copilotkit/blob/main/skills/copilotkit-integrations/references/integrations/langgraph.md>（经 Context7，访问 2026-08-22）

但我们的 dashboard 是 **`output: "export"` 纯静态**（`next.config.mjs:14`），托在 Cloudflare Pages 上，没有 Node 服务器可以跑这个 handler。要么塞进 Pages Function（多一跳、多一个信任边界），要么塞进 Fly 上的 runtime（那 CopilotRuntime 就只是个多余的中间层）。

**(3) 两次翻译，两次失真机会。** 我们的 21 个 `ClaraPart` 里，只有 `text` / `tool_call` / `tool_result` / `tool_error` 能干净地映到 AG-UI 标准事件。剩下 17 个（`je_review`、`doc_review`、`refusal`、各种 `*_receipt`、`open_question`…）只能塞进 `CUSTOM` 事件 —— 而 AG-UI 自己说 CUSTOM 是 *"explicitly part of the protocol but with application-defined semantics"*（<https://docs.ag-ui.com/concepts/events>，访问 2026-08-22），也就是**协议对它一无所知，语义还是我们自己定**。

那我们付出的代价换来什么？把 17/21 的负载塞进一个协议不理解的信封里，只为了让 4/21 用上标准名字。**这笔账算不过来。**

### 2b. Generative UI / shared state 会不会撞我们的法？

**会，而且撞得很正。**

**撞点一：Generative UI vs "DB 拥有每一个数字"。**

PRD §6 第 1 条（LAW）：

> "**The DB owns every AUTHORITATIVE number; the agent only orchestrates.** ... no model-generated numeral enters a durable report unless a versioned deterministic evaluator reproduces it from DB-owned inputs. ... A model numeral is never an evaluator input"
> —— `docs/product/PRD.md` §6.1

AG-UI 的 tool-based generative UI 是这样跑的：模型发 `TOOL_CALL_START` → 参数以 JSON 片段**流式**进来（`TOOL_CALL_ARGS`）→ 前端把这些参数**当组件的 props 渲染出来**。

> "ToolCallArgs — Arguments stream incrementally as JSON fragments... The frontend accumulates these delta events to reconstruct complete tool arguments"
> —— <https://docs.ag-ui.com/concepts/tools>（访问 2026-08-22）

**如果那个参数里有一个 `amount_cents: 452000`，那就是一个模型写的数字直接被画成了 UI —— 这正是 §6.1 禁止的事。** 我们的做法反过来：part 里**只有标识符**，卡片自己去 DB hydrate。`shared/parts.ts:38` 的注释把这条写死了："identifiers only; the card re-derives authoritative state ... never trusting the persisted snapshot"。

**怎么约束才能用？** 只能收紧到这个程度：

- 模型只能输出一个**注册过的 card ID + 一组 ID 参数**（entry_id / client_id / run_id），不能输出任何数值、任何金额、任何名称；
- 前端只从 `PART_CATALOG` 里查表拿组件，未注册的一律走 `FALLBACK_UNSUPPORTED_PREFIX` 芯片（`parts.tsx:134`）；
- 编译期 `_covered` 穷尽断言保持不变（`partCatalog.ts:167`）。

**但你注意 —— 收紧到这个程度之后，剩下的东西就正是我们现在已经在做的事。** generative UI 的"generative"部分被完全阉割掉了。所以答案是：**能约束，但约束完就没有净收益**。

**撞点二：shared state vs 单一真相源。**

AG-UI 的 shared state 是前后端共同持有一份可变 state，用 JSON Patch (RFC 6902) 增量同步：

> `case EventType.STATE_DELTA: { const result = applyPatch(state, delta, true, false); state = result.newDocument; ... }`
> —— <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/state.mdx>（经 Context7，访问 2026-08-22）

> state is "Accessed by both the agent and front-end"
> —— <https://docs.ag-ui.com/concepts/agents>（访问 2026-08-22）

**这是一份"浏览器里的第二本账"。** 一旦它里面出现任何金额，我们就有两个真相源，而且浏览器那份是模型 patch 出来的。这在会计产品里是不能接受的。

**可以安全用的变体：** shared state 只装**非权威的会话工作态** —— 当前 scope（哪个 client / 哪个期间）、进度百分比、"我正在读第 3 张发票 / 共 12 张"、当前打开的 plan 步骤。这些东西**没有一个进账**，patch 错了最多是 UI 显示不对，刷新即修复。这确实能改善你说的"用户能看见 Clara 在干嘛"。**这一点我建议偷（见 §5 选项 B）。**

### 2c. HITL 原语能不能映到我们的 receipts / open questions / approval doors？

**不能干净映射。这是我判断"不采用"的第二根硬骨头。**

**AG-UI 的中断模型（终止式）：**

> "the run ends with an interrupt outcome, and the client starts a new run carrying per-interrupt responses"
> "Run 2 begins; `resume[].interruptId` links back to run 1's interrupts."
> "the agent must emit any state required for resume via `StateSnapshot` and `MessagesSnapshot` events **before** the `RunFinished` event"
> —— <https://docs.ag-ui.com/concepts/interrupts>（访问 2026-08-22）

**Clara 的中断模型（挂起式）：**

```typescript
const hook = createHook<{ kind: "answer" | "expired" | "cancelled"; answer?: unknown }>({ token: hookToken });
await openInterruptionStep(taskId, hookToken, { question: seg.clarify.question, context: seg.clarify.context });
const resolution = await hook; // PARK — zero compute until answered/expired/cancelled
```
—— `packages/runtime/workflows/chatTurn.v12.ts:118-121`

**同一个 run 原地停住**，DB 里 `agent_tasks.status` 变成 `awaiting_input`，可以停几天不烧一分钱算力，人回答后 `markRunningStep` 让它醒过来继续（`chatTurn.v12.ts:125`）。ARCHITECTURE §4.0a 第 2 条把这条列为运行时硬要求：*"a run pauses at zero compute and resumes on the answer, days later, without double-posting"*。

**三个具体的不匹配：**

| | AG-UI | Clara |
|---|---|---|
| run 边界 | 中断 = run 结束，resume = **新 run** | 中断 = run 挂起，resume = **同一 run 继续** |
| 状态归属 | 客户端持 `resume[]` 数组，负责带回来 | DB 持 `agent_interruptions` 行，客户端只是**触发者** |
| 回答通道 | 前端 POST 回 agent endpoint | **Supabase RPC `answer_interruption`，绕开 runtime**（`api.ts:321`） |

第三行是最致命的。`api.ts:8` 那行注释是一条法：

> `// Governance NEVER transits the runtime (§4.2).`

治理动作（回答 clarify、取消任务、共享会话）走 **HUMAN lane** —— 带用户自己的 session JWT 直连 PostgREST，由 DB 的 RLS + audited function 记账。**runtime 全程不碰、也碰不到这个动作。** 这样设计的意义是：一个人的批准是在 DB 层被记录和授权的，agent 服务连"假装人批准了"的能力都没有。

**如果按 AG-UI 的形状接，前端就得把答案 POST 给 agent，agent 再去写 DB。** 那就凭空多出**第二条审批路径**，而且这条路径的授权主体从"人的 JWT"变成了"agent 服务的凭据"。**这直接违反"一个动作一道门"，也把 §4.2 的治理隔离拆了。**

**关于 receipts（今天 TA-P4 那条新裁决：每个 agent 判断动作都要留一张机械绑定的回执）：**
我在 repo 里 grep 过 `TA-P4`，`docs/` 和 `PROGRESS.md` 都还没有 —— 它是今天 sitting 上的口头裁决，尚未落库，所以下面这段是按你转述的语义推的，落 ADR 时请复核。

按那个语义看：AG-UI **完全没有 receipt 概念**。它的事件流是**瞬态的 UI 消息**，不是审计记录。它甚至明说 state 只要能在 resume 前重建出来就行（"resume-mode-agnostic"）—— 这是给 UI 用的一致性，不是给审计用的不可否认性。

我们的回执是 DB 行（`sweep_receipt` / `rule_post_receipt` / `depreciation_run_receipt` / `adjustment_run_receipt` …，见 `shared/parts.ts:83-140`），part 里只放 `run_id`，卡片 hydrate 时从 DB 读。**AG-UI 在这一层不但没帮助，还引入了一个"事件流里显示的东西"和"DB 里记录的东西"可能不一致的新缝。** 我们现在没有这条缝，因为 `streamRoute.ts:75` 在终局那一帧发的就是**从 DB 读回来的 `parts`**（`fetchParts()`），流里的 `chunk` 只是活体预览、不是权威。

## 3. 具体能买到什么 / 买不到什么

### 会买到

1. **一套现成的事件词汇表**，以及别人（Google、LangChain、AWS、Microsoft、Mastra、PydanticAI）也在用这套词汇（<https://raw.githubusercontent.com/CopilotKit/CopilotKit/main/README.md>，访问 2026-08-22）。如果哪天要把 Clara 的 agent 暴露给**第三方前端**（客户自己的门户、Slack、Teams、React Native），说 AG-UI 就省了写文档。
2. **现成的客户端 UI 组件**（CopilotKit 的 chat/popup/sidebar，`renderAndWaitForResponse` 审批弹窗那一套 —— <https://github.com/copilotkit/copilotkit/blob/main/packages/react-ui/README.md>，经 Context7 访问 2026-08-22）。省一点前端工。
3. **进度可见性的现成套路**（`ACTIVITY_SNAPSHOT` / `STEP_STARTED`）。这一条对你说的"用户看得见 Clara 在干什么"是真有用的。

### 不会买到（这些是你真正关心的东西）

1. **不会买到更好的审计。** 审计的强度来自 DB 的 append-only 事件日志、audited SECURITY DEFINER 函数、回执行 —— 全在 Postgres 里。AG-UI 是浏览器和服务器之间的事，**够不到那一层**。
2. **不会买到更好的会计协作。** 我们协作的难点从来不是"消息怎么传"，是"哪个动作需要哪一级人签、签完留什么证据、revision token 对不对得上"。这些是 DB 的 `assert_can_*` floors 和 maker/checker 在管（ARCHITECTURE §3.4）。协议不解决这个。
3. **不会买到更好的提问体验。** 我们的 clarify 现在已经是：typed part + 可见性 framing（"This question and its answer are visible to your firm."）+ 持久化 `agent_interruptions` 行 + 可停数天 + expired/cancelled 有专门的 `clarify_closed` part。AG-UI 的 confirmAction 模式**比这个弱**（它是瞬态的、客户端持状态的）。
4. **不会买到任何会计权威。** 它是传输/UI 协议。再说一遍是因为这条最容易被销售话术模糊掉。

## 4. 成本与风险

### 4.1 成熟度与版本churn —— **高风险**

- `@ag-ui/core` 的 npm `latest` 是 **`0.0.58`**（<https://registry.npmjs.org/@ag-ui%2Fcore>，访问 2026-08-22）。**还没到 1.0，连 0.1 都没到。**
- GitHub releases 页最近十次发布：2026-08-20、08-18、08-17、08-16、08-14、08-12、08-11、08-07、08-04、07-31 —— **每周 2 到 4 次发布，没有 1.0**（<https://github.com/ag-ui-protocol/ag-ui/releases>，访问 2026-08-22）。
- 协议里已经有一批 DEPRECATED 事件（`THINKING_*` 系列，标注 "removed in 1.0.0"），还有一批标为 "Draft Events — proposed extensions under development"（<https://docs.ag-ui.com/concepts/events>，访问 2026-08-22）。**interrupts 那套（我们最需要的部分）在社区里还在 discussion 阶段**（GitHub Discussion #827 "Questions about the draft proposal on interrupts"）。
- README 对协议版本/稳定性**没有任何承诺**（我读了整篇 README，找不到 versioning policy）。

**对我们的意义：** Clara 的 workflow body 一旦部署就冻结（`.claude/rules/runtime-workflows.md`），我们的整个工程纪律建立在"契约稳定"上。**把一个每周改 2-4 次、pre-0.1、HITL 部分还在草案阶段的协议放进传输层，是把 churn 引到一个我们刻意设计成不能 churn 的地方。**

### 4.2 供应商耦合 —— **中等风险，可控**

- 协议本身 MIT（<https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/README.md>，访问 2026-08-22），CopilotKit 也 MIT（<https://raw.githubusercontent.com/CopilotKit/CopilotKit/main/README.md>，访问 2026-08-22）。**许可证没问题。**
- CopilotKit Cloud / Intelligence 是可选的：*"Cloud services are optional, not required"*（同上）；文档也强调 *"Build production chat, generative UI, shared state, and human-in-the-loop workflows on any AG-UI compatible backend"*（<https://docs.copilotkit.ai/>，访问 2026-08-22）。
- **但要小心一个措辞**：一份索引页写道 *"platform credentials and message delivery are handled by CopilotKit Intelligence — a hosted service, not part of the protocol"*（搜索结果引自 ag-ui.ai 技术页，访问 2026-08-22 —— 我没有直接 fetch 到那一页，标为**未逐字核实**）。如果真要用 CopilotKit，**必须逐条确认没有任何客户数据流向他们的托管服务** —— 这直接撞 PRD §6 第 16 条（egress 治理：C6 checklist = DPA + firm disclosure + PDPA 跨境依据）。
- **治理上的真正代价不是许可证，是"协议不是我们定的"。** 我们的 21 个 part type 是被 ADR 和 owner ruling 一个个定下来的；AG-UI 的事件表是别人的路线图。哪天他们改了 interrupt 的形状，我们的 clarify 就要跟着动 —— 而 clarify 是 judgement logic（review law 1 管辖），每动一次都要走完整的独立评审。

### 4.3 安全面 —— **中等，但有一个具体的新洞**

- **传输层本身不新增风险**：AG-UI 就是 SSE，我们已经在跑 SSE，CSP 的 `connect-src` 没有变化。
- **静态站点的问题**：dashboard 是 `output: "export"`（`next.config.mjs:14`），没有服务器可以跑 CopilotRuntime。要么加 Pages Function（新的可执行边界 + 新的凭据存放点），要么在 Fly 上加一层（多一跳）。**两个选择都在系统里加了一个原本不存在的组件。**
- **真正的新洞 —— frontend-defined tools**：AG-UI 的核心设计是"工具由前端定义并传给 agent"：

  > "Tools are defined in the frontend and passed to the agent during execution."
  > —— <https://docs.ag-ui.com/concepts/tools>（访问 2026-08-22）

  **这个方向对我们是反的。** Clara 的工具目录在 runtime 侧、在 frozen closure 里（`chatTurn.v12.tools.ts`），并且 ARCHITECTURE §4.1 要求 *"The catalog is generated from the DB function registry and lint-checked against it"*。**让浏览器往 agent 的 loop 里注入工具定义，等于让一个不可信客户端参与决定 agent 能干什么。** 就算实际实现里我们把它限制成"只能是前端渲染动作、不能触发 DB 写"，这条通路本身也变成了一个必须永远守住的信任边界 —— 而我们现在**根本没有这条通路**。
- **`CUSTOM` / `RAW` 事件是未类型化的逃生口**（*"application-defined semantics"*）。我们现在的 part 联合是编译期封闭的（`partCatalog.ts:167` 的 `_covered` 断言）。引入一个协议级的"什么都能塞"信封，会**软化 fail-closed catalog 的保证** —— 因为未知的东西不再是"未知 part type"（会被显式渲染成 `Unsupported part:` 芯片），而是"一个合法的 CUSTOM 事件，只是我们不认识它的 name"。

### 4.4 迁移路径 —— 如果真做，会动到哪些文件

按影响从大到小：

| 文件 | 改动 | 是否 frozen |
|---|---|---|
| `packages/runtime/src/streamRoute.ts` | 新增 AG-UI 事件编码器（chunk/message/done → 27 种事件）；或并行开第二个端点 | 否，可改 |
| `apps/dashboard/app/chat/api.ts` | `streamTask()` 换成 AG-UI client；`answerInterruption` 的路由**面临被改成走 agent 的压力** ← **这一条是红线** | 否，但 §4.2 治理法保护 |
| `apps/dashboard/app/chat/parts.tsx` | `applyChunk` 整个重写（现在吃 AI SDK fullStream 块，要改成吃 AG-UI 事件） | 否 |
| `apps/dashboard/app/chat/partCatalog.ts` | 要么保留（映到 CUSTOM 事件 name），要么被 AG-UI 的注册机制替代 ← **保留才安全** | 否 |
| `apps/dashboard/app/shared/parts.ts` | 21 个 part type 要定义到 AG-UI 事件的映射 | 否 |
| `apps/dashboard/app/chat/page.tsx` | SSE 消费循环重写 | 否 |
| `apps/dashboard/next.config.mjs` / Pages Function | 若走 CopilotRuntime，要加服务端 | 否 |
| `packages/runtime/workflows/chatTurn.v*.ts` | **不需要动**（翻译在 route 层） | **是，frozen** |

**好消息确认一遍：frozen workflow 不用动。** 坏消息是 `apps/dashboard/app/chat/` 基本上要重做一遍，而且改的是 `applyChunk`、`toolStatuses`、fallback 分支这些**已经被 parity test 和编译期断言钉死的 judgement logic** —— 每一条都要走独立评审（review law 1）。

## 5. 建议

### 选项 A —— 在 Wave G OS surface 里整体采用 AG-UI 作为传输层

**约束条件（缺一不可）：**
- 只在 `streamRoute.ts` 做边缘翻译，frozen workflow 一律不动；
- 中断/回答通道**保持 HUMAN lane 不变**（`answer_interruption` RPC 直连 PostgREST），AG-UI 的 `resume[]` 只用于**通知**"答案已落库、请醒过来"，**绝不承载授权**；
- generative UI 阉割到"模型只输出注册过的 card ID + ID 参数"，`PART_CATALOG` 的编译期穷尽断言保留；
- shared state 只装非权威工作态（scope、进度），**任何金额一律不进 state**，加一个 lint 挡住；
- frontend-defined tools **完全禁用**；
- 自己 fork + 维护 AI SDK 7 适配器（官方那份未发布且停在 v4）。

**我的评价：技术上做得到，但这是"为了兼容一个我们并不需要兼容的生态，去重写我们最严谨的一段前端代码"。**

### 选项 B —— 只偷三个想法，在现有 SSE 上做 ✅ **我推荐这个**

不装任何 AG-UI 包，不引入协议依赖。把下面三条作为 **Wave G OS surface 的设计输入**：

**B1. 补一类"进度/活动"帧（借 `STEP_STARTED` / `ACTIVITY_SNAPSHOT` 的想法）。**
现在的 SSE 只有 `chunk` / `message` / `done` / `detached`（`streamRoute.ts`）。一个跑 90 秒的 sweep，用户看到的只有沉默。加一个 `activity` 帧（"正在读第 3 张 / 共 12 张"、"正在核对银行流水"），**纯展示、不带任何金额、不进 DB 权威路径**。这条直接改善你说的"交互"。成本：约一天工，一个非冻结文件。

**B2. 补一份"会话工作态"（借 shared state 的想法，但只装非权威数据）。**
当前 scope（client / period）、当前打开的 plan 步骤、待办计数。让工作台和聊天栏对齐 —— 这正是两窗格 Agentic OS 的核心体验（`docs/design/PRODUCT_DESIGN.md` §1 的 agent-native 验收测试："remove the chat rail — the workbench must still show what Clara did"）。**用不用 JSON Patch 无所谓，关键是"金额永远不进这份 state"这条纪律。**

**B3. 把工具调用的渲染从"芯片"升级成"可展开的证据条"（借 tool-call rendering 的想法）。**
我们已经有 `tool_call` / `tool_result` / `tool_error` 三态芯片（`parts.tsx:138`）。AG-UI 生态里做得好的是：工具调用可以展开看输入输出。这**对你说的"审计"是真有用的** —— 会计师能看见 Clara 到底读了哪份文件、调了哪个 DB 函数。而且我们的数据已经在 part 里了（`tool_result.output`），只差一个展开 UI。**这是三条里性价比最高的。**

**为什么推荐 B：** 三条都在非冻结文件里、都不引入外部协议依赖、都不碰治理车道、都不撞 §6.1，而且**直接命中你问的三件事（提问、审计、协作）**。风险接近零，收益是实的。

### 选项 C —— 现在不做

也是合理的（Wave F Track-A 还在跑，OS surface 本来就排在 Wave G）。但 B 里的 B3 便宜到不值得单独排期，我建议至少把它写进 Wave G 的 backlog。

### 落在计划哪里

- **不是 Wave-F Track-A 的宪法问题** —— 确认。这里没有任何东西触及 ADR-0071 的授权模型、posting 权威或 digest laws。
- **正确的位置是 Wave G 的 OS surface 项**：`PROGRESS.md:298` 记的 *"**Wave-G:** the OS surface + the UX-debt backlog (E-R10) + design trio population"*，以及 `docs/design/PRODUCT_DESIGN.md` 列的 Wave-G 待写内容里明确有 **"generative-UI completion"** 和 **"⌘K Ask/Do/Go + ActionPanels"** —— B1/B2/B3 天然属于那一批。
- **F-A7b（interview layer）有一处相关但独立**：`PROGRESS.md:331-335` 记着 *"the concurrent-submitter receipt gap — a RUNTIME CONTRACT change... the real fix is a server-authored per-(run, park, submission) receipt"*。这条和 AG-UI **无关**（AG-UI 没有 receipt 概念，帮不上忙），但它和 TA-P4 的"每个判断动作留机械绑定回执"是同一族问题，值得放在一起想。
- **chat parity**：B3（工具调用展开）如果要做，应该和 chat parity 一起做，因为它改的是 `parts.tsx` 的渲染分支，会碰 parity test。
